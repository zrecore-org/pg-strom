# PG-Strom on Vulkan: Apple Silicon first, CUDA removed (branch `vulkan-gpu`)

> The branch was created as `apple-silicon` and renamed `vulkan-gpu` after A2 (it is the Vulkan port, validated on Apple Silicon only). Older text below keeps the old name where it describes history.

## Context and decisions

The goal changed from "add Vulkan next to CUDA" to "no longer depend on NVIDIA; port the acceleration to Vulkan for cross-platform GPU use". Your decisions, and how I read them:

| Decision | Reading in this plan |
|---|---|
| Clean replacement: remove CUDA, no CUDA fallback or oracle | Applies to the new branch only. The oracle for tests is PostgreSQL with `pg_strom.enabled=off`. |
| Drop GPUDirect Storage and `heterodb-extra` | Dropped. Storage is read through the CPU. |
| Work lives on a new git branch `vulkan-gpu` (created as `apple-silicon`) | Created from `master` when implementation starts. **`master` stays the CUDA line (`cuda-legacy`) and is not touched by this work.** |
| Maintain `cuda-legacy` releases | The CUDA line continues on `master`; you do not test it (see next row). It is never ported or modified here. |
| "I do not want to test NVIDIA / AMD / Intel hardware" | **Apple Silicon is the only validated platform.** The code stays Vulkan-portable by construction, but other vendors are labelled *unvalidated* in docs and `pgstrom.gpu_device_info`. The earlier request for Linux NVIDIA/AMD/Intel as CI platforms is reduced to "designed for, not tested". |
| Scan up to 1.5x and aggregation up to 2x slower than CUDA is acceptable | Recorded as the acceptance criterion **if anyone later measures on NVIDIA**. It cannot be a gate on this branch, because it needs NVIDIA hardware. The gate here is PostgreSQL's own parallel scan on the same Mac. |
| First Vulkan release scope: core (scan, aggregate, join), Arrow_Fdw and Parquet, jsonb, GpuSort/window and GPU-Cache | All four are in scope, sequenced by difficulty. jsonb comes last and is the most uncertain. |

**Consequences of these choices (stated plainly)**
- **This is a permanent hard fork** of the CUDA product for the `vulkan-gpu` branch. Upstream CUDA changes can still be merged into `master`, but not into the branch once CUDA files are deleted.
- **Nothing in this plan proves performance or correctness on NVIDIA, AMD or Intel.** That risk is accepted and written down, not mitigated by hardware.
- **PostGIS is partly back (A11):** the 2D bounding-box operators and point-in-polygon (`ST_Contains` / `ST_Covers` / `ST_Intersects` / `ST_Within` / `ST_CoveredBy` of a polygon and a point) run on the GPU; the rest was dropped (about 6k lines of device code and a spatial join that the hash-only GpuJoin cannot run). The other reason first given, "Apple has no fp64", no longer holds: exact binary64 can be done in integer code, see the A10 status and correction 5 below.

## Corrections to earlier conclusions (verified in code)

1. **PG-Strom never lets the GPU read live `shared_buffers`.** `src/relscan.c:439-500` reads each page with `ReadBufferExtended`, takes `BUFFER_LOCK_SHARE`, copies the 8 KB page into `xcmd_buf`, runs the visibility check on the CPU (invisible tuples are marked unused in the copy), and unlocks. `src/executor.c:171-195` then writes the buffer over a UNIX socket. So the torn-read risk I flagged does not apply, the "copy under content lock" that macOS forces is how PG-Strom already works everywhere, and the spike's "visibility checks not implemented" limitation is moot for the kernel path.
2. **The zero-copy end-to-end figures were optimistic.** 7.2 ms (specialized) and 35 ms (VM) leave out the mandatory backend copy (about 21 ms per 823 MB). Realistic figures on this Mac are **about 28 ms and 56 ms**, against 163 ms for 8-worker PostgreSQL (5.8x and 2.9x faster). Zero-copy still helps on the service side, by replacing the socket copy with a shared-memory ring.
3. **Zero-copy only holds on unified memory** (Apple, integrated GPUs). On discrete GPUs every byte crosses PCIe. That path is designed for but not validated here.
4. **The live-`shared_buffers` module and kernel (`zcscan/`, `heap_live.slang`) are no longer needed.** The Metal-in-forked-process and multithreaded-postmaster findings still stand and are why the service must be an exec'd process on macOS.
5. **"No fp64 emulation, because it is not IEEE-exact" was wrong for integer emulation (corrected in A10).** It holds for double-float pairs (two float32), whose results differ from binary64. IEEE-754 binary64 written in 64-bit integer arithmetic (unpack, align, operate, normalize, round to nearest even, repack) is bit-identical to a hardware double for add, subtract, multiply, divide and square root; the approach is described by the ArrowMetal project (https://theaivibe.org/blog/metal-has-no-double-float64-on-the-apple-silicon-gpu, read through a summarizing fetch tool, so only its claims, not its code, were used). `src/gpuserv/kernels_vm/f64_soft.inc` implements it here and `f64soft_check` verifies it bit for bit against the host's hardware double on the host and on this Mac's GPU (16 million cases per operation). Comparison, `min`/`max` and sort keys need no arithmetic at all (an order-preserving integer key).

## Target architecture

### Branch and repository policy
- Create `vulkan-gpu` (first named `apple-silicon`) from `master` HEAD. `master` keeps CUDA.
- Delete CUDA, `heterodb-extra`, GPUDirect and PostGIS only on this branch (milestone A2).

### Platform scope and capability tiers
- **Base tier (implemented and validated):** Vulkan 1.2 with MoltenVK on Apple Silicon. int64 arithmetic, 8/16-bit storage, 32-bit subgroup ballot and arithmetic, 32 KiB shared memory, unified memory with host-memory import. **No fp64, no 64-bit buffer atomics, and no Vulkan memory model** (MoltenVK reports `vulkanMemoryModel` false; found in A1). The base tier therefore must not rely on acquire/release atomics: lock-free structures in A3 need explicit barriers (`GroupMemoryBarrier`/`DeviceMemoryBarrier` plus relaxed atomics). The desktop tier requires the memory model.
- **Desktop tier (implemented after A3 as milestone A3b, experimental and unvalidated):** adds 64-bit atomics and fp64. The kernel source keeps two small shim modules (`xpu_atomics.slang`, `xpu_fp64.slang`) behind `#if PGSTROM_CAP_*`, so adding it later is additive. (The fp64 shim now has a base-tier implementation, the integer software binary64 of A10, so `float8` does not need the desktop tier; a hardware-double variant of the same interface would be the optimization there.) I recommend writing the base variant only now, rather than shipping untested desktop code.
- **Capability probe (`devcaps`):** at service start, each capability is on only if the feature flag, the extension **and a probe kernel** all agree. The spike showed MoltenVK reports int64 subgroup operations that Metal then rejects, so flags alone over-report. Results are cached per device UUID and driver version and published to a shared segment so the planner can read them.
- **Planner gating:** each `devtype`, `devfunc` and aggregate in `codegen.c` gets a `required_caps` field, and pushdown is refused when the device lacks one. On Apple: `float8` operators and `sum(float8)` stay on the CPU; integer sums and counts are pushed down; `min/max(int8)` in GROUP BY stay on the CPU until a design exists (partial results plus a reduce pass is the leading option). ~~No fp64 emulation, because it is not IEEE-exact.~~ Corrected (A10, correction 5): the base tier can run `float8` through the integer software binary64 of `f64_soft.inc`; hardware double stays an option on the desktop tier. The gating (`required_caps`) is not wired yet.

### Process model: an exec'd GPU service
- **Why:** a forked process cannot use Metal's shader compiler, and PostgreSQL 17 aborts if the postmaster becomes multithreaded (both reproduced earlier). So the GPU service becomes a separately exec'd binary, `pgstrom-gpuserv`.
- **Launcher:** a small background worker that never touches Vulkan spawns the service with `posix_spawn`, watches it and restarts it. A crash or hang of the GPU driver then kills only the service, not PostgreSQL.
- **Shared state:** `gpuServSharedState`, the GPU-Cache shared head and the error level move to a named POSIX shared-memory segment created by the postmaster with `shm_open` (no threads).
- **PostgreSQL internals:** the roughly 79 `elog`/`ereport`/interrupt sites in `gpu_service.c` (the architect's count; I did not re-count) go through a small shim.
- **Page ingest:** backends keep copying pages under the share lock (unchanged `relscan.c`) but write them into a per-session shared-memory ring instead of a `StringInfo` sent over the socket. The socket then carries only headers and offsets. The join inner buffer already uses this pattern (`.pgstrom_shmbuf_*`, `gpu_service.c:2217`).

### Memory model
Every allocation becomes an explicit buffer (VMA) with a placement class; nothing is managed memory.
- **Unified memory (Apple, validated):** host-visible, device-local, persistently mapped; the ingest ring is imported with `VK_EXT_external_memory_host`.
- **Discrete GPUs (designed for):** device-local buffers, explicit copies on a transfer queue. A debug GUC `pg_strom.gpu_memory_model=discrete` forces this path on the Mac so its *correctness* can be tested locally (not its speed).
- `cuMemPrefetchAsync`-style growth of the final buffer becomes suspend, grow, device-to-device copy, resume, reusing the existing suspend/resume logic. `cuMemcpyPeer` (`gpu_service.c:3627`) becomes a host-staged copy.
- Pointers become offsets (GPU-Cache's `hslots`/`next`, `kern_multirels` pointers). Buffer device address is used only for buffers above `maxStorageBufferRange`.

### Kernels
- **One Slang source.** A single op library, `xpu_ops.slang`, implements every opcode once; both the VM's `switch` and generated specialized kernels call it. `xpu_opcodes.h` is included unchanged (spike-verified). The `TypeOpCode`/`FuncOpCode` enums move out of `xpu_common.h` into a shared header.
- **VM first, specialization second.** The prebuilt VM SPIR-V ships with the product (`slangc` pinned, build-time only). Runtime specialization (spike: 8-13x faster, cold compile 0.2-6 s, pays back after about 7-9 scans) loads `libslang` with `dlopen`, compiles in a background thread while the VM serves the first scans, and caches SPIR-V on disk by program hash plus a persisted `VkPipelineCache`. If `libslang` is absent, everything runs on the VM.
- **Sizing:** no assumption of 32-thread warps or 512-thread blocks. `WaveGetLaneCount()` and `uint4` ballots, workgroup size as a specialization constant, dispatches split to stay well under about 1 s. `KVEC_UNITSZ` (`xpu_common.h:1834`) becomes a fixed constant.
- **Concurrency rule: no inter-workgroup spin-waits anywhere** (Vulkan guarantees no forward progress across workgroups).
  - *PreAgg NoGroups* (`cuda_gpupreagg.cu:1041-1107`): one-workgroup init dispatch creates the final tuple; later workgroups reduce in shared memory and merge with one atomic per accumulator.
  - *PreAgg GroupBy* (`:1632-1713`, `:1138-1185`): insert-only lock-free hash; reserve space, write key and initial accumulators, publish the tuple offset with a 32-bit CAS and release semantics; losers compare keys and either reuse the winner's tuple or probe on; a full table raises a suspend flag, the host grows and resumes. 64-bit sums use the 16-bit-limb technique verified in the spike.
  - *Join and scan row-count lock* (`cuda_gpujoin.cu:841-878`): per-subgroup atomic reservation.

### Renames and removals (branch only)
- **Delete:** `src/*.cu`, `src/Makefile.cuda`, `src/extra.c`, `src/heterodb_extra.h`, `pg_strom.gpudirect_*`, `pg_strom.extra_ereport_level`, `pgstrom.license_query()`, `estimate_cuda_stack_size` and the EXPLAIN line "CUDA Stack Size" (`executor.c:3185`), `docs/ssd2gpu`.
- **Rename or replace:** `pg_strom.cuda_visible_devices` → `pg_strom.gpu_visible_devices`; `pg_strom.cuda_toolkit_basedir` and `cuda_stack_limit` removed; `DEVKIND__NVIDIA_GPU` → `DEVKIND__VULKAN_GPU`; `pgstrom.gpu_device_info()` gets a Vulkan attribute set (device name, UUID, driver, tier, devcaps bits, memory heaps) instead of CUDA attributes from `gpu_devattrs.h`.
- **Replace without the closed module:** device validation (dropped) and optimal-GPU selection (single device for now; PCI-bus-info based selection is a later option). Without the module PG-Strom today keeps only one GPU anyway.
- **Expected outputs:** about 4 files per PostgreSQL version (15-19) contain CUDA/GPU strings (`CUDA Stack Size` numbers, `GPU Cache: GPU0 ...`); edit mechanically.
- **Build and packaging:** `src/Makefile` loses `-lcuda` and the nvcc rules and gains slangc, Vulkan loader and MoltenVK detection; spec and deb files drop the `heterodb-extra` Recommends and `CUDA_PATH`.

## A1 status (core done)

Verified on this Mac (Apple M1 Pro, MoltenVK) and in the arm64 Linux container (lavapipe, a CPU Vulkan device, enabled with `pg_strom.gpu_allow_cpu_device`).

**What exists**
- **`src/gpu_launcher.c`:** the postmaster runs the probe (`pgstrom-gpuserv --probe`, with a timeout) at start-up, creates the control segment (named POSIX shm `/pgsctl.<port>`), and registers a launcher background worker. The worker fork+execs `pgstrom-gpuserv --serve`, passes a lifeline pipe on fd 3, restarts the service with back-off (1 s to 30 s, reset after 60 s of uptime) and stops it on shutdown (SIGTERM, SIGKILL after a grace period). GUCs: `pg_strom.gpuserv_path`, `pg_strom.gpu_allow_cpu_device`, `pg_strom.gpuserv_probe_timeout`.
- **`src/gpuserv/`** (libc and Vulkan only, no PostgreSQL headers): `gpuserv_proto.[ch]` (control segment layout, probe text format, socket handshake), `gpu_vk.[ch]` (device open, buffers, host-memory import, pipelines, dispatch with fence timeout), `devcaps.c` (probe kernels and tiers NONE/BASE/DESKTOP), `gpuserv_main.c` (`--probe`, `--serve`), `vm_selftest.[ch]` and `kernels_vm/` (the opcode-switch VM scaffold, built from the real `xpu_common.h` enums by `gen_opcodes.sh`), `kernels/` (14 probe kernels). SPIR-V is embedded as C arrays by `gen_kspv.sh`.
- **SQL (`pg_strom--6.2--7.0.sql`, default version 7.0):** `pgstrom.gpu_devcaps()`, `pgstrom.gpu_service_state()`, `pgstrom.gpu_service_ping()`.
- **Build:** `src/Makefile` builds the service through `WITH_GPUSERV` hook rules (warns and skips when `slangc` or Vulkan is missing, unless `WITH_GPUSERV=1`) and installs it into `$(pkglibdir)`.
- **Startup self-test:** before saying "ready" the service runs the VM kernel on 65,536 synthetic rows (a four-term qual with int64 arithmetic and NULLs, plus an `int4div` by zero case) and compares the match set and error code with a CPU three-valued-logic reference. **Findings**

**A2.3 result (Apple M1 Pro; `test/gpuserv/scan_test.sh`)**

What runs on the GPU: one workgroup per heap page, one thread per line pointer. Each thread deforms the columns the program needs (null bitmap, alignment, varlena skipping), runs the qual program of the scan VM (bool, int1/2/4/8 and float4 with PostgreSQL's overflow, zero-divide and NaN rules; int casts; three-valued AND/OR/NOT; IS [NOT] NULL on any column type), and for qualifying tuples evaluates the computed projection expressions. The service then forms the result tuples on the CPU, copying pass-through columns (any type, varlena and external TOAST pointers included, ctid and tableoid) straight from the source tuple.

- **Differential test:** 14 + 2 query shapes on three tables, each GPU result set compared with the CPU's by md5: a table whose pages are all-visible (pages mapped from the file), one with UPDATEs and DELETEs and no vacuum (pages loaded and visibility-checked by the backend), and a mix. NULLs, NaN and Infinity, 200-byte text, int2/int4/int8 mixed arithmetic, casts, division and modulo, `IS NULL` on text, 10 and 24 computed columns (the 16- and 32-register kernels), a division-by-zero error on both sides, and parallel workers. **All pass on the M1 Pro, with and without the zero-copy path (`PGSTROM_GPUSERV_NO_MAP=1`), and on arm64 Linux with lavapipe (desktop tier, subgroup size 4, copy path).** UPDATE and DELETE (planned as GpuScans projecting `ctid`) work.
- **Plan gating for now:** GpuPreAgg, GpuJoin, GPU-Cache and SELECT INTO direct are not registered in the Vulkan build (their init is compiled out), so aggregate and join queries run on the CPU instead of failing. Each comes back with its milestone (A3, A4, A7).
- **Page ingest:** the pages the backend loaded go into a small buffer; the relation file's own pages are not copied: a 512 MB window of the file is `mmap`ed and imported as a Vulkan buffer (`VK_EXT_external_memory_host`) and **kept between tasks**. Importing a fresh mapping per task was no faster than `pread` (the GPU pays the page-in on first touch, about 15 ms per 64 MB); a persistent window is what the spike measured. A per-page table tells the kernel where each page is. If a window is not usable (pages past the end of the file, a buffer limit smaller than a window as on lavapipe) every page is copied.
- **Kernel findings:** workgroup size (32 to 256) makes no difference; **register-file size does** (32 registers 3.6 ms, 8 registers 2.1 ms per 64 MB), so there are three kernel variants (8, 16 and 32 registers) chosen by the program. Loads are 32-bit words (tuples are 8-byte aligned). The kernel writes one flag per line pointer instead of compacting with atomics, so the service reads matches in heap order with no sort (a `qsort` of 8.4M records had cost 1.5 s).

**Performance against the gate (16.8M rows, 964 MB, 8 CPU cores, server-side execution time of `EXPLAIN ANALYZE`)**

| Query | GPU (VM) | PostgreSQL, 8 processes | PostgreSQL, 1 process |
|---|---|---|---|
| `SELECT id ... WHERE v < 10 AND w + 1 > 5` (0.9% of rows) | **about 90 ms** (first run 175 ms: file windows paged in) | 124 ms | 621 ms |
| `SELECT id, v, w, e ... WHERE v < 500` (50% of rows) | 980 ms | **195 ms** | 671 ms |

**The A2 gate (scan at least 2.9x faster than 8-worker PostgreSQL) is not met: the selective scan is 1.4x faster.** Where the time goes for the selective query, per 64 MB task: GPU 2.2 ms (about 30 GB/s; the spike's VM kernel on the same data class was about 35 ms for 863 MB, the same figure), flag scan and tuple forming 1.7 ms, and about 25 ms of the 90 ms is the backend (checking blocks, sending tasks, receiving results). The service is single-threaded, so tasks do not overlap. Specialized kernels (A6) take the GPU part to about a fifth, and the service can pipeline (form tuples for task N while the GPU runs task N+1) and form tuples on several threads. ## A3 status (in progress)

**Design: PostgreSQL finalizes, the service produces partial states.** The planner now always builds the two-phase shape the CUDA code used only when `pg_strom.cpu_fallback` was on: `Aggregate (CPU) -> Custom Scan (GpuPreAgg)`. The GpuPreAgg node returns PostgreSQL-format partial aggregate states (`kagg_state__*` in `bytea`, `int8` for counts), and PostgreSQL's own Agg node combines and finalizes them with the existing `pgstrom.fsum_int`, `fcount`, `favg_*`, `fminmax_*` functions. So the service needs no final buffer, no finalization and no `MERGE_FINAL_BUFFER`; the one-row-per-session partial result is returned in the reply to `XpuTaskFinal`, as the CUDA service did for this shape. (The planner's "complete aggregation" path, where the service finalizes, is not used.)

**Done: aggregation without GROUP BY** (count(*), count(x), sum/avg/min/max of int1/2/4/8, including `FILTER (WHERE ...)` and expression arguments):
- **Planner:** `pg_strom.enable_gpupreagg` is registered again; the aggregate catalog offers only the actions the service implements (`scan_vm_agg_action_supported()` in `scan_caps.c`: NROWS, PSUM/PAVG INT and INT64, PMIN/PMAX INT32 and INT64). float8, numeric, text and so on stay on the CPU.
- **Kernel (`kernels_vm/agg.slang`)** shares the row evaluation with the scan kernel (`scan_common.slang`: page loads, deform, VM, `eval_row`). One workgroup runs over 32 pages; each thread accumulates the qualifying tuples of its line pointers in registers, the workgroup reduces in shared memory (no atomics, nothing shared between workgroups, nothing that needs the Vulkan memory model, so it is valid on the base tier) and writes one partial record per aggregate. Sums are carried as the sum of the low 32 bits and the sum of the high 32 bits, and the service adds them up in 128 bits, so `sum(int8)` is exact beyond 64 bits (checked against PostgreSQL's numeric).
- **Service:** `scan_prog.c` has an aggregation mode (SaveExpr arguments compiled to registers, an aggregate table in the program); `scan_exec.c` runs the tasks, keeps a per-session `agg_state` (counts, `__int128` sums, min/max) and `scan_exec_agg_final()` builds the partial-state row for `XpuTaskFinal`; each parallel worker has its own session and PostgreSQL combines the workers' rows.
- **Tests:** `scan_test.sh` has 28 aggregate checks per run: NULLs, empty input, NULL-only columns, expression arguments, FILTER, sums beyond 64 bits, float aggregates (stay on the CPU), parallel workers; all pass on the M1 Pro and on arm64 Linux with lavapipe.
- **Performance (16.8M rows, server-side time of `EXPLAIN ANALYZE`, 8 CPU cores):**

| Query | GPU | 8-process PostgreSQL |
|---|---|---|
| `count(*), sum(w), max(v), avg(v) ... WHERE v < 500` | **67 ms** | 172 ms |
| `count(*), sum(id), min(w)` (no WHERE) | **40 ms** | 159 ms |
| `count(*) ... WHERE v < 10` | **35 ms** | 115 ms |

  That is 2.6x to 4.0x faster than parallel PostgreSQL; the A3 criterion ("faster than parallel PostgreSQL on the same table") holds for this shape. The GPU takes about 2 ms per 64 MB task. Two measured lessons: **the size of the per-thread accumulator arrays dominates** (12 entries 8.2 ms per task, 4 entries 4.3 ms; dynamically indexed arrays spill), so the kernel has variants by aggregate count (4, 8, 12) and register count (8, 16, 32), 9 SPIR-V modules; and **one workgroup per page is too small a unit** (the reduction cost about as much as the work), now 32 pages per workgroup.

**Done: GROUP BY** on up to two integer key columns (int1/2/4/8; bool keys are not offloaded because the planner's device-equality lookup for `bool` finds nothing, which looks like an upstream limitation), with the same aggregates as above.
- **Kernel (`kernels_vm/gagg.slang`):** one workgroup of 64 threads runs over 32 pages and keeps a hash table of its groups in shared memory (128 slots for up to 4 aggregates, 64 for more). It works in rounds of 64 rows separated by barriers, and **no thread ever waits for another** (no spin-waits; nothing needs the Vulkan memory model): (A) each thread evaluates its row and stages the key and the aggregate arguments; (B) each thread finds or claims its key's slot with one compare-and-swap that stores the claiming thread's index, and a thread that meets a claimed slot compares with the claimer's *staged* key, so nobody waits for a key to be written; (C) each row's thread adds its values to the slot with 32-bit shared atomics (counts; sums as four 16-bit limbs of the value biased by 2^63, so limb sums cannot overflow 32 bits; min/max on a value biased by 2^31) while the slots' owners turn fresh slots into committed ones. A row that finds no slot within 8 probes, or whose min/max argument does not fit 32 bits, is flagged and **aggregated on the CPU** by the service (`cpu_vm.c`, a C port of the VM's row evaluation, which also gives the project a CPU reference of the VM and the basis for a CPU fallback).
- **Service:** `scan_prog.c` compiles the key expressions (the SaveExpr arguments of the key hash) and maps output columns to keys or aggregates (`VREF` actions are keys); `scan_exec.c` keeps a per-session group table (open addressing, 128-bit sums), merges the workgroups' tables and the CPU rows, and answers `XpuTaskFinal` with one partial-state row per group.
- **Planner:** key types and key count gated by `scan_caps`; `pg_strom.gpupreagg_max_groups` (default 16) keeps queries with more estimated groups on the CPU; GPU-Sort is off by default (`pg_strom.enable_gpusort`) until A7.
- **Tests:** 36 GROUP BY checks per run (one and two integer keys, NULL keys, int8 keys, FILTER, empty input, sums beyond 64 bits per group, parallel workers, 1,500 groups and a two-key case that force the CPU overflow path, text and bool keys staying on the CPU, the group-count gate); all pass on the M1 Pro and on arm64 Linux with lavapipe.

**Performance of GROUP BY is not good enough yet** (16.8M rows, `EXPLAIN ANALYZE` time, 8 CPU cores; `pg_strom.gpupreagg_max_groups` raised for the measurement):

| Groups | GPU | 8-process PostgreSQL |
|---|---|---|
| 7 | 236 ms | 303 ms (1.3x) |
| 100 | 361 ms | 300 ms (0.8x) |
| 1,000 | 887 ms | 298 ms (0.3x; most rows overflow to the CPU) |

The kernel needs about 18 ms per 64 MB task for 7 groups, against 2 ms for aggregation without GROUP BY. What the experiments showed: a first version with slot-owner threads accumulating serially took 47 ms; chaining each slot's rows (27 ms) and then having every row's thread use shared atomics (18 ms) helped; the table size matters through shared-memory occupancy (128 slots 28 ms, 32 slots 13 ms in the earlier version), which is why the tables are small and overflow to the CPU beyond roughly 100 groups per workgroup; the row evaluation itself is only about 2 ms. So the default limit of 16 groups is where the GPU currently wins (about 1.3x); above it the planner keeps the aggregation on PostgreSQL. Things to try next: per-subgroup pre-reduction by slot to cut atomic contention, a smaller staging footprint for higher occupancy, and larger tables for the planner's estimated group counts; then raise the limit. The A3 criterion "faster than parallel PostgreSQL" therefore holds for aggregation without GROUP BY (2.6-4x) and for few groups (1.3x), not yet for many groups.

**GROUP BY tuning experiments (what did not help, so it is not repeated).** Measured per 64 MB task on the 7-group query (kernel 14-19 ms, against about 2 ms for aggregation without GROUP BY):
- Init and write-out of the 128-slot table cost about 1 ms; the row evaluation about 6 ms; staging, slot search and accumulation about 7 ms. Skipping the accumulation phase barely changed the time.
- Replacing the per-row shared atomic add of a hit counter by one add per subgroup: no change. 32-bit instead of 64-bit division and modulo for narrow integers: no change. Copying the VM program to shared memory at workgroup start (a measurement that looked like a 6x gain was the small last task of the query; with the full-size task it was neutral to slightly worse): reverted.
- Few groups are slower than many: 1,000 groups 15 ms, 7 groups 19 ms, because every thread's atomic updates hit the same few slots (a subgroup's lanes serialize on one address). Subgroup pre-reduction by slot could address that but replaces 12 atomics per lane by a ballot loop per distinct slot.
- A trivial qual doubles the aggregation kernel's time (2.4 ms to 5.6 ms for `WHERE v + 1 > 3`): the VM's registers are a dynamically indexed array in private memory. That is the cost of interpretation the A6 specialization (generated kernels with registers as local variables) removes; the spike measured it as 8-13x. **So the remaining GROUP BY speed-up belongs to A6**, where a specialized kernel can also keep a small group table in registers.

**Update (A6, kernel specialization):** the GROUP BY numbers above are the interpreter's. The specialized kernels change them (GROUP BY 7 groups 44 ms against 249 ms for 8-worker PostgreSQL, 100 groups 73 ms against 288 ms; 1,000 groups still loses, 855 ms against 285 ms) and `pg_strom.gpupreagg_max_groups` now defaults to 128; the findings (footprint of the group table in shared memory and the barrier rounds, not the row evaluation, dominate; direct-mapped tables remove the rounds) are in "A6, fourth part".

**Test-suite note:** the shell tests ran `ANYPLAN=1 runagg ...` as a one-shot variable, but macOS `sh` keeps the variable set after a function call, so plan checks after the first such call were silently skipped on macOS (Linux's `sh` did not). The tests now use an explicit `runagg_any` function; with the checks enforced both platforms pass.

## A4 status (done: inner, LEFT, RIGHT, FULL, semi and anti hash joins, up to four inner relations per GpuJoin; GpuPreAgg over a join with and without GROUP BY)

**Scope:** `Custom Scan (GpuJoin)` for `INNER`, `LEFT`, `RIGHT`, `FULL`, semi (`EXISTS`, `IN`) and anti (`NOT EXISTS`, and `NOT IN` where PostgreSQL 18+ turns it into an anti join) joins, hash joins only, up to **four inner relations in one GpuJoin** (`SCAN_JOIN_MAXDEPTH`; the plan shows them as `Join Quals [1]`, `[2]`, ...; the label says `Join`, `Left Outer Join`, `Right Outer Join`, `Full Outer Join`, `Semi Join` or `Anti Join`), equality keys of integer or bool type (`scan_vm_groupkey_type_supported`), any pushed-down join qualifier, scan qualifiers on the outer side, and projections that mix columns of the outer side and of every inner relation (pass-through including varlena, `ctid`/`tableoid`, computed expressions; a semi or anti join contributes no inner columns). Refused by the planner (`gpu_join.c`), so those joins stay on PostgreSQL: nest-loop and GiST joins, more than four inner relations, non-integer keys, any outer join (LEFT/RIGHT/FULL/anti) with a qualifier that comes from the WHERE clause (`other_quals`: it must be applied to the null-extended row), RIGHT/FULL joins in a parallel plan, and `JOIN_UNIQUE_INNER/OUTER` (PostgreSQL's unique-ified semi join). An aggregate over a join runs on the device too (GpuPreAgg on the join, see "Done: aggregation over a join" below), RIGHT and FULL joins included (see "GpuPreAgg over RIGHT and FULL joins"). Which shape the planner picks (one GpuJoin with several inner relations, or a chain of GpuJoins whose child is the hash side) is its cost decision; both run.

- **Inner side:** unchanged on the backend. The inner relations are built into the same POSIX shared-memory hash stores the CUDA code used (`kern_multirels` header, then one `KDS_FORMAT_HASH` store per relation: slot array of 64-bit offsets, `kern_hashitem` chains). The service maps it read-only by name (port + `join_inner_handle`, `scan_exec_join_open`), imports it into Vulkan with `VK_EXT_external_memory_host` (copy when the import is not possible) and keeps it for the session. A store the service cannot use (nest-loop, pinned, GiST, partitions, more than four relations) is a clean task error.
- **Hash:** device-side Jenkins `hash_any` over the little-endian bytes of the key, combined as in `xpu_common.h` (`HASHINIT`/`HASHMERGE`/`HASHFIN` are VM opcodes), so the backend's inner-side hash values match without change.
- **Kernel (`kernels_vm/join.slang`, three register-count variants):** one workgroup per outer page, a thread per line pointer. It evaluates the scan qualifiers and then walks the join tree depth first as a per-lane state machine (a private array of chain positions per depth): at depth d it takes the next item of the hash chain, compares the stored hash, deforms the inner tuple and runs the join quals; a match goes one depth deeper (the next hash value is computed from the columns loaded so far); at the last depth the projection runs and a record is appended (one atomic reservation per subgroup); an exhausted chain returns to the parent, and for a LEFT join an exhausted chain without a match continues once with NULL inner columns. A match record is the outer page and line pointer, the item offset in every inner relation (0xffffffff for a null-extended one), and the computed projection values. The output capacity starts at the number of line pointers (at least 4096); if more matches occur the task is run again with room for the exact count. No inter-workgroup waiting.
- **Service (`scan_prog_build_join`, `scan_exec_join_task`):** the program has the scan quals, then a hash section and a join-qual section per depth, then the projection, a column table per inner relation and a depth table; `form_tuple` builds the result tuples from the outer tuple, the inner items and the computed values.
- **Semi and anti joins:** the backend marks the relation in the `kern_multirels` chunk (`is_semi`, `is_anti`, two spare bytes of the old layout); the depth table word 11 carries 1 (semi) or 2 (anti). In the kernel a semi join goes one depth deeper at the first match and abandons the chain (`nxt[d] = NO_ITEM`), so an outer row passes once whatever the number of matching inner rows, and the rest of the chain is never walked; an anti join abandons the chain at the first match and drops the row, and when the chain ends without a match it continues like a LEFT join with NULL inner columns (the columns are never projected). The first chain entry that passes the full join qual decides, not the first entry with the hash (the chain may hold entries that fail an extra qual). NOT IN null semantics are PostgreSQL's business: it plans an anti join only for NOT EXISTS and for NOT IN over provably non-null columns (PostgreSQL 18); a hashed SubPlan is not a join. A NULL outer key never matches, so the anti join passes the row, as `NOT EXISTS` does. The CPU fallback (`fallback.c`) follows the same rules.
- **RIGHT and FULL joins:** the unmatched inner rows are not known until every outer row has been seen, so the backend emits them at the end (as CUDA did with `ExecFallbackCpuJoinRightOuter`, the existing CPU join code, which also continues through later depths with NULL outer columns). The outer-join map of the backend is one byte per inner row in the shared inner buffer (`ojmap_offset`, zeroed by the backend). The kernel sets a word per inner row it matched (`InterlockedOr`, the row id is the last word of the item) in a map at the head of its per-task output buffer (program header word 17 = size, depth table words 12/13 = its offset and rows; the match records follow it); after the task the service merges it into the backend's byte map (mapped writable through a second `shm_open`, only 0 -> 1 stores, so several sessions may merge at once) before it replies. The reply to `XpuTaskFinal` of a join session carries `right_outer_join`; the backend then runs the CPU right-outer emission and the tuples come out through the fallback queue. Costs: the map is one word per inner row, cleared and read back per task (fine for dimension-sized inner sides; a very large preserved inner side would want a device-resident map merged at the end). The map is flagged at the moment a join qual matches at its depth, like the CPU code, even if a later depth rejects the row. Not offered in parallel plans (each worker would see only a part of the outer rows; PostgreSQL itself offers no parallel-oblivious right joins) and with WHERE-derived quals.
- **Tests:** about 70 join checks per run in `scan_test.sh` (3 tables of different visibility): pass-through of both sides, int8 key, quals on both sides, computed mixed projection, text from either side, an extra join qual, no match, `ctid`, duplicate inner keys; LEFT joins (unmatched rows, ON quals on either side, no match at all, a WHERE qual that keeps the join on the CPU); stacked joins with a plan check for `Join Quals [2]` (two and three inner relations, duplicate keys at two depths, inner then LEFT, LEFT then inner, two LEFT joins, text columns of two relations); an aggregate over a join, a float key that must stay on the CPU, parallel workers. All pass on the M1 Pro and on arm64 Linux with lavapipe. (The test settings for stacked joins leave `enable_seqscan` on: with it off, the 1e10 penalty on the dimension tables' plain scans pushes the planner into odd join orders.)
- **Tests (semi/anti/right/full):** `scan_test.sh` section "semi and anti joins": EXISTS, IN, NOT EXISTS with correlated quals on both sides and a qual on the outer side only, duplicate inner keys (rows appear once; the matching entry is not the first of its chain), nothing / everything matches, NULL outer keys, int8 key with a computed key expression, ctid, stacked cases (`Join Quals [2]`: inner then EXISTS/NOT EXISTS, EXISTS then inner with duplicates, NOT EXISTS then LEFT, EXISTS and NOT EXISTS together, EXISTS then inner then LEFT), parallel workers, NOT IN over nullable and non-null columns (result checks only); and RIGHT/FULL: ON quals on the outer side, on the inner side and mixing both, duplicate inner keys, nothing matching, inner rows with NULL keys, text columns, stacked (inner then RIGHT, RIGHT then LEFT/inner on the inner side's column), and a parallel plan that must give the same rows. Each runs on the three tables of different visibility.
- **Performance (2M-row outer, 4,000-row inner, `EXPLAIN`-free wall time of the query):** a selective join (`d.k < 50 and b.w < 100`, 6,000 result rows) **12.5 ms against 24.8 ms** for 8-process PostgreSQL. An unselective one (1.6M result rows) takes 175 ms against 62 ms, because forming and shipping the result tuples dominates, as it does for an unselective GpuScan. Joins are a win when the join reduces rows or feeds an aggregate; the planner's cost model has not been tuned for that.
- **Not done yet:** nest-loop joins, outer joins with WHERE-derived quals (`other_quals`; the kernel would apply them to the null-extended row, and the CPU emission already does), non-integer keys (text, numeric need A6 types), inner stores larger than `maxStorageBufferRange`, and the upstream `gpujoin` regression expected files.

**Done: aggregation over a join (`Custom Scan (GpuPreAgg)` on top of the join, `Aggregate (CPU)` above it finalizes).** The joined rows are aggregated on the device and never travel to the backend. The plan is one node: `Custom Scan (GpuPreAgg) on <outer>` that lists the join (`GPU Join Quals [n]`, `GPU Left Outer Join Quals [1]`, `GPU Semi Join Quals [1]`, ...) and the inner relations below it.
- **Which shapes run on the GPU:** every join GpuJoin offers (inner, LEFT, RIGHT, FULL, semi, anti; one to four inner relations, stacked, with quals on both sides), with or without `GROUP BY` on up to two integer/temporal keys that may come from any side (including the inner side and the null-extended rows of a LEFT join, which form the NULL group), aggregates `count(*)`, `count(x)`, `sum/avg/min/max` of integers, expression arguments mixing columns of several relations, `FILTER`, parallel workers. **Stay `Aggregate (CPU) -> GpuJoin`** (the same gates as for scans apply): RIGHT/FULL joins combined with a GiST join, float/numeric/text aggregates or keys, more than `pg_strom.gpupreagg_max_groups` estimated groups. (Arrow/Parquet outer sources run on the device since A5 part 2.)
- **Kernel:** the depth-first walk of `join.slang` moved into `kernels_vm/join_walk.inc` (one page of outer rows, one lane per line pointer; `join_common.inc` has the hash-chain helpers) and is included by three entry points that differ only in what a completed joined row ("emit") does, selected by `JW_MODE`: `join.slang` (0, append a match record, unchanged behaviour), `jagg.slang` (1) and `jgagg.slang` (2). `jagg.slang` is `agg.slang` fed by the join: each lane adds the row to private accumulators, one workgroup runs over 8 outer pages, then reduces in shared memory and writes the same 6 words per aggregate, so the host merge (`agg_merge_workgroups`, factored out of `scan_exec_agg_task`) is shared. `jgagg.slang` is `gagg.slang` fed by the join: the group table in shared memory and its A (stage) / B (find or claim a slot) / C (accumulate, commit) rounds with barriers; **one walk iteration is one round**, because every lane emits at most one row per iteration. The barriers need a workgroup-uniform loop, so the loop condition is a shared flag published with the round's first barrier (bit 0: some lane still walks, bit 1: some lane has a row; three flag slots by round number avoid a reset race, and a round with no row skips its table work). No lane ever waits for another and nothing needs the memory model, so it stays valid on the base tier. A row whose key finds no slot (and a row whose min/max argument does not fit 32 bits) is not lost and does not need the join to be repeated on the CPU: its staged key and per-aggregate (ok, value) are appended to an **overflow list** (atomic counter, capacity passed as a push constant; if it was too small the task runs again with room, nothing is merged before), and the host adds them to the groups like `scan_exec_group_task`'s CPU rows (`group_merge_blocks` is shared too).
- **Program (`scan_prog_build_join`, `join_build_agg`):** with `DEVTASK__PREAGG` and an inner buffer, the section after the join evaluates, instead of the projection, the key expressions, the aggregate arguments and the FILTERs into registers (variables of the outer relation and of every inner relation are all in their registers when a row is complete; null-extended ones are NULL); header words 10-13 carry the aggregate table and key registers exactly as in scan programs. `wire.c` routes a PREAGG session that has `join_inner_handle` to `scan_exec_joinagg_task`; the reply to `XpuTaskFinal` is the unchanged partial-state row(s) of `scan_exec_agg_final`. Kernel variants: 16/32 registers x 4/8/12 aggregates for each of `jagg` and `jgagg` (12 more SPIR-V modules).
- **Planner (`gpu_preagg.c`):** the `custom_paths` block only refuses RIGHT/FULL together with a GiST join (it was the RIGHT/FULL gate until 2026-11-06); the path's cost drops the GpuJoin's DMA-receive term (the joined rows stay on the device). **Test-setting caveat:** with `enable_seqscan=off` the 1e10 disable penalty on the dimension table's scan is inside every path's cost and within PostgreSQL's 1% fuzz, so a sorted CPU `GroupAggregate` "dominated" the hashed GpuPreAgg path on its pathkeys; the new tests leave `enable_seqscan` on. Group-count estimates for expressions (`a % 10`) are one group per row, so such queries keep the aggregate on the CPU; the tests use plain key columns with statistics for GROUP BY.
- **Measurements** (M1 Pro, `EXPLAIN ANALYZE` execution time, best of 3, outer `big` of 2M rows (`k` in 4000 values) joined with a 4,000-row dimension, `pg_strom.gpupreagg_max_groups=1000`; 16M is the same table shape with 16M rows):

| Query | GPU join + aggregate | GpuJoin + CPU Aggregate | PostgreSQL, 8 workers |
|---|---|---|---|
| 2M, `count, sum, max` over the join, `v < 500` (1M joined rows) | **43 ms** | 140 ms | 35 ms |
| 2M, same with `v < 5` (10,000 joined rows) | **25 ms** | 28 ms | 19 ms |
| 2M, `GROUP BY` an inner column (20 groups) | **107 ms** | 336 ms | 65 ms |
| 2M, `GROUP BY` an outer column (100 groups, 5% of the rows overflow to the list) | **193 ms** | 322 ms | 63 ms |
| 16M, `count, sum, max`, `v < 500` | **238 ms** | 1,300 ms | 247 ms |
| 16M, `GROUP BY` an inner column (20 groups) | **730 ms** | 3,380 ms | 473 ms |

  Without GROUP BY the join aggregate is 3-5x faster than shipping the joined rows to the CPU aggregate (the old plan), and at 16M rows it equals 8-process PostgreSQL (the kernel takes 5 ms per 64 MB task; what is left is the backend's page copy and the fixed per-query cost of about 15-20 ms, so 2M rows are too few for the GPU to win). With GROUP BY it is 3x faster than the old plan but **slower than 8-process PostgreSQL** (about 56 ms of kernel per 64 MB task against 5 ms without GROUP BY: the same shared-atomic contention on few slots that limits the scan GROUP BY of A3, now with a barrier-synchronized round per walk step); the A6 specialized kernels are where that is attacked. The 3-slot flag change that skips empty rounds did not move the kernel time, so rounds are not the bottleneck, the per-row atomics are. The planner's cost model does not know this, so a GROUP BY over a join can be chosen where PostgreSQL's own plan is faster; `pg_strom.gpupreagg_max_groups` (default 16) keeps it to few groups.
- **Tests:** `test/gpuserv/joinagg_tests.inc` (sourced by `scan_test.sh` after the semi/anti/right/full sections; `joinagg_dev.sh` runs it alone on a small data set through `locked_test.sh`, with `ADHOC=<file>` for ad hoc SQL and benchmarks, `JAGG_FILTER=<egrep on the label>`, `TRACE=1`): the plan must show `Custom Scan (GpuPreAgg)` and the join lines, and the md5 of the result must equal the CPU's. Covered on the three visibility variants `s1/s2/s3`: count/sum/min/max/avg of int2/4/8 from either side, NULL values from the inner side, duplicate inner keys, empty join result (count 0, sum NULL), quals on both sides, expressions mixing sides, FILTER on either side, sums beyond 64 bits, int8 join keys, extra join quals, 9 aggregates (the 12-aggregate kernel), LEFT joins (`count(*)` against `count(inner column)`, no match at all, ON quals, FILTER on the null-extended column), stacked joins with two and three inner relations (inner then LEFT, LEFT then inner, two LEFT joins), EXISTS / NOT EXISTS; GROUP BY with keys from the inner side, the outer side, both, NULL keys, FILTER, sums beyond 64 bits per group, int8 keys, more groups than a workgroup's table (the overflow list), two keys with overflow, min/max beyond 32 bits, empty result, the NULL group of a LEFT join, stacked joins with keys from two inner relations, semi and anti joins; parallel workers with and without GROUP BY and with a LEFT join; RIGHT and FULL joins (own section below), and the shapes that must stay correct on the CPU (float aggregate, text key, too many estimated groups).
- **Known gaps:** GROUP BY speed (above); the per-query fixed cost; aggregates over text/numeric/float (A6); `gpusort` on top of an aggregate.

**GpuPreAgg over RIGHT and FULL joins (2026-11-06).** The aggregating kernels only return partial states, and the unmatched inner rows of a RIGHT/FULL join are known only after the last outer row. Design: (1) the join-aggregation tasks (`scan_exec_joinagg_task`, `scan_exec_arrow_joinagg_task`) append the outer-join map (one word per inner row of each RIGHT/FULL depth, `prog->oj_words`) **behind** the kernel's results in the output buffer (after the group blocks and the overflow list; the join kernels keep it at word 4) and patch the map offset in the depth table of the program copy that goes to the device (`scan_prog_ojmap_place`; the kernel adds 4 to the table's offset, `join_walk.inc` is unchanged and flags at the moment a join qual matches at its depth, as the CPU code does). After the dispatches the task merges the map into the backend's shared byte map (`join_merge_ojmap`, only 0 -> 1 stores) like a GpuJoin task does; the specialized kernels read the offset from the program buffer too (check mode compares only the result blocks). (2) The reply to `XpuTaskFinal` of a PREAGG session carries `right_outer_join` (`wire.c`; harmless without RIGHT/FULL relations). (3) The backend (`executor.c`, `pgstromExecScanAccess`) emits the unmatched inner rows when it **releases** the final reply, i.e. after all its chunks were handled: a final reply can carry `KDS_FORMAT_RECHECK` chunks (rows the kernel could not read), whose CPU join sets map flags that the emission has to see. `ExecFallbackCpuJoinRightOuter` joins each unmatched inner row with NULL outer columns through the later depths (LEFT/inner/semi on the inner side's columns) and projects it to a partial-aggregate row of `custom_scan_tlist` (the same `fallback_proj` path as the poison rows of a GiST join); the Agg node above adds those rows to the GPU's states, with and without GROUP BY (an unmatched inner row is a row of the NULL-extended outer side: group keys of the outer side are NULL, inner keys are the inner row's). **What stays on the CPU:** the unmatched inner rows themselves (a dimension-sized set; one CPU pass over the inner store, not a second GPU dispatch: the kernels would need a new "inner rows as the driving side" mode in `join_walk.inc` and in every specialized variant), RIGHT/FULL together with a GiST join (the poisoned outer rows are joined by the backend after the service replied and set flags too; refused in `gpu_preagg.c`, which recognizes the GiST depth by `gist_index_oid`, not only by `gist_func_oid` of the function clauses, and in `scan_prog_build_join`), and GPU-Sort over a RIGHT/FULL join (the backend's rows would follow the sorted groups). Parallel plans: GpuJoin offers no parallel RIGHT/FULL join (the outer scan stays serial; the plan of the parallel test shows a Gather only under the inner side), so a GpuPreAgg over such a join runs in one process and the emission happens once. That planner invariant is what keeps the result right: the final reply of every PREAGG process carries `right_outer_join`, and several processes would each emit the unmatched rows. GPU-Cache outer sources go through the Arrow join-aggregation task and are covered by `gpucache_tests.inc` (a RIGHT join whose only partners were deleted from the table: the cache still holds those slots, the row filter must keep them out of the map). **A bug found on the way** (`fallback.c`, `__execFallbackLoadVarsSlot`): int2/int4 columns of an inner row were stored as zero-extended Datums, so `pgstrom.pmin/pmax` (`PG_GETARG_INT64`) of a negative value read 4 billion and the final function raised "min(int32) out of range"; any CPU-joined row (LEFT null-extension excluded, but poison rows, recheck rows and the new unmatched rows) with a negative int4 aggregate argument was affected. Fixed with `Int16GetDatum`/`Int32GetDatum`. Tests: `joinagg_tests.inc` section "aggregation over RIGHT and FULL joins" (RIGHT/FULL ungrouped and grouped, ON quals on either side, nothing matching, inner rows with NULL keys, FILTER, keys from the outer side (the NULL group), two keys, the overflow list, inner join then RIGHT, RIGHT then LEFT/inner on the inner side's column, on the three visibility variants) and `arrow_tests.inc` (RIGHT, FULL, grouped, nothing matching on `a1`/`a2`/`a3`/`p1`). **Dispatch slicing:** the join-aggregation tasks (heap and Arrow) now dispatch at most 128 workgroups at a time (`JOINAGG_DISPATCH_GROUPS`): the query below (GpuJoin 6.7 s of kernel time, the aggregating kernel more) ran as one dispatch of 844 workgroups that passed the 10 s watchdog and lost the device (all sessions restart). A NULL-key inner row hashes like every other one, so an inner side with many NULL keys makes one long chain. Skipping the chain walk of a NULL outer key (and leaving NULL-key rows out of the chains unless the join keeps unmatched inner rows) would make it fast; not done. Test setup note: an inner side with many NULL keys makes the walk slow (NULL hashes to one chain; an outer row with a NULL key walks it): with `sdnl` (25% NULL keys) an ON qual that lets 1/3 of the outer rows through ran 10 s on the Apple GPU and hit the kernel watchdog, so the test uses a selective outer qual. The scan tests of `joinagg_tests.inc` can be filtered (`JAGG_FILTER=<egrep on the label>`), ad hoc SQL runs with `ADHOC=<file> SKIP_TESTS=1`, `TRACE=1` logs the service (the `/tmp/a4c_*` marker files are gone).


## A5 status (done: Arrow IPC files and Parquet row groups under GpuScan, GpuPreAgg and GpuJoin, and aggregation over such a join)

**Scope:** `Custom Scan (GpuScan)` on an Arrow_Fdw foreign table (one or several Arrow files, any number of record batches; partitioned tables with Arrow partitions use the same code but are untested) and on Parquet files (one task per row group). The quals and computed projections the heap path supports (bool, int1/2/4/8, float4; see A2.4) run on the GPU; every other referenced column is passed through. The planner offers the GpuScan only if every referenced column has a supported Arrow type (`arrowFdwGpuScanSupported()` in `arrow_fdw.c`, called from `gpu_scan.c`): **Int (1/2/4/8 bytes), FloatingPoint (2/4/8 bytes), Bool, Utf8/LargeUtf8, Binary/LargeBinary, Date[day], Time, Timestamp, FixedSizeBinary mapped to bpchar, and virtual columns** (per-file and per-record-batch). Decimal (numeric), Interval, Date[ms], List, Struct, macaddr and inet columns, and anything else, keep the table on the CPU Arrow_Fdw path. **Part 2 (below) lifted the refusal: GpuJoin and GpuPreAgg take an Arrow/Parquet table as the outer (scanned) relation.** An Arrow table as the inner side of a GpuJoin always worked (it is a separate scan). Quals on date/time/timestamp/utf8/char(n) columns now run on the GPU too; numeric expressions stay on the CPU (A6).

- **What the backend sends** (unchanged `pgstromScanChunkArrowFdw()`): per record batch an `XpuTaskExec` with a `KDS_FORMAT_ARROW` header (the `kern_colmeta` of every column; for a loaded column the `nullmap_`, `values_`, `extra_offset/length` relative to the start of the store, and `virtual_offset` for virtual columns), the file name, and a `strom_io_vector` (page-aligned chunks of the file: `fchunk_id`, `nr_pages`, `m_offset` into the region behind `KDS_HEAD_LENGTH + arrow_virtual_usage`). The service does the reading itself. Parquet: `parquetFillupRowGroup()`-style, the backend decodes the row group with libparquet (`parquetReadOneRowGroup`, the existing host-memory reader) into an Arrow-format store and sends it inline in the task (no i/o vector); the service then reads the columns from the task itself. (So Parquet decoding is on the backend's CPU, one row group at a time per backend; the GPU only filters.)
- **Service (`src/gpuserv/arrow_exec.c`, kernel `kernels_vm/arrow.slang`):** the file range of the i/o vector is mapped read-only (`mmap`, page cache, no copy; a `pread` into a store-shaped buffer is the fallback). The GPU gets a **packed copy of only the columns the kernel reads** (validity bitmap and values of the columns with a register slot, 8-byte aligned, one buffer; pass-through columns are not copied), and a column table (8 words per column: bitmap offset and length, values offset and width, mode normal / all NULL / constant for a virtual column, values length). The kernel is the existing scan VM (`vm_run`, three register-count variants `gpuarrow8/16/32`) with **one thread per row**: columnar loads with the Arrow validity bit (1 = valid; no bitmap = no NULLs), a bool as a bit, a value past its buffer reads as NULL. It writes a flag per row and the computed values, in passes of at most 1M rows (the output buffer is bounded). The service then forms the result tuples on the CPU from the Arrow buffers (`arrow_fetch()` converts as `pg_datum_arrow_ref()` of `arrow_fdw.c` does: Date32 and timestamps to the PostgreSQL epoch with the same unit arithmetic, Utf8 with a 1-byte or 4-byte varlena header, bpchar, bool bit) and the GPU's values, and replies with one `KDS_FORMAT_ROW` chunk per record batch. `tableoid` works; `ctid` of an Arrow table is refused (a clean error).
- **Findings:**
  - Importing the mapped file window into Vulkan as the GPU's buffer (the heap path's zero-copy trick) is **not** a win for Arrow: the GPU read 12 MB of two columns of a 2M-row batch in about 21 ms steady state (100+ ms the first time), against about 5 ms from a buffer the service filled with a memcpy of exactly those bytes (about 2.5 ms per task). Heap pages are read densely; sparse columnar reads through imported file-backed memory are slow on this GPU/MoltenVK. Hence the packed copy.
  - The backend decides which batches to read with the Arrow_Fdw min/max statistics hint (unchanged), so skipped batches cost nothing.
  - A record batch larger than the device's storage buffer limit for the GPU's columns is a task error (the heap path has the same limit for inner stores); Arrow files from `pg2arrow` default to 256 MB segments, far below it.
  - A large result set is formed on one CPU thread (about 60 ns per row for four columns), as for heap scans.
- **Tests (`test/gpuserv/scan_test.sh`, section "arrow (Arrow_Fdw)"):** a C++ generator (`test/gpuserv/arrow_gen.cpp`, built by the test with libarrow/libparquet; `arrow-tools` still do not build on macOS) writes Arrow IPC files and a Parquet file with NULLs, int2/int4/int8, float4 with NaN and Infinity, bool, utf8 (0-199 bytes, NULLs), date32 and timestamp[us] with NULLs. Tables: `a1` (3 record batches, the last one short), `a2` (one batch of 1003 rows), `a3` (two files with odd batch sizes), `p1` (Parquet, 3 row groups). Each of the four gets 26 differential queries (GPU md5 and row count against `pg_strom.enabled=off`, plan must show `Custom Scan (GpuScan)`): the heap path's query shapes (quals, arithmetic and casts with NULLs, NaN/Infinity, bool logic, IS [NOT] NULL on int/text/date/timestamp, division and modulo, the 16- and 32-register kernels with 10 and 24 computed columns, a generic-plan prepared statement), pass-through of text, date and timestamp, no row and every row qualifying, and the "stays on the CPU" shapes (float8, text equality, text function, date qual). Plus aggregate and GROUP BY over an Arrow table, a join with a heap table, an Arrow table as the inner relation, parallel workers, and a division-by-zero error. 111 checks in the Arrow section, all pass on the M1 Pro with the mapped file and with `PGSTROM_GPUSERV_NO_MAP=1` (the `pread` fallback). Not run on Linux/lavapipe by me (the parent does that after merging).
- **Performance (16.8M rows, 9 columns, 2.2 GB Arrow file in 8.4 batches of 2M rows, `EXPLAIN ANALYZE` execution time, warm page cache, M1 Pro, 8 CPU cores):**

| Query | GpuScan | Arrow_Fdw, 1 process | Arrow_Fdw, 8 workers |

| `select i, a, b, c ... where b < 0` (5.6M rows, 33%) | 987 ms | 1,507 ms | **372 ms** |

  A selective scan is 17-25x faster than one CPU process and 3-6x faster than 8 workers; per 2M-row task: 2.5 ms to map and pack the two columns, 4 ms on the GPU, 1 ms for the 300 result tuples. An unselective scan loses to 8 workers because forming and shipping 5.6M tuples dominates (the same limit as the heap path); parallel tuple forming in the service would address it. `count(*)` over a GpuScan is `Aggregate -> GpuScan` here (GpuPreAgg does not read Arrow), 325 ms against 163-187 ms for 8 workers; **GpuPreAgg and GpuJoin over Arrow sources are the main gap.**
- **Known gaps:** (GpuPreAgg / GpuJoin over Arrow: done, see part 2 below.) Decimal/Interval/List/Struct/Date[ms] columns (and inet/macaddr), expressions on date/time/numeric/text (A6; when that lands the Arrow loader needs the same column types: `arrow_build_table()` refuses an unknown value type with a clean error), `ctid`, Parquet row groups decoded on the GPU (A7-style cache) or in parallel, tuple forming on several threads, `pgstrom.arrow_fdw_*` stats of the Parquet cache, GPU-Direct (no equivalent), and the upstream `arrow_*` regression expected files (they need pg2arrow and CUDA-era plan text).

### A5 part 2: GpuPreAgg and GpuJoin over Arrow / Parquet (done)

- **Design: one Arrow row loader, the existing kernels.** `kernels_vm/arrow_load.inc` holds the columnar loader that `arrow.slang` used to contain (`arrow_load_row`, `arrow_eval_row`: validity bit, per-column mode normal / all NULL / constant / utf8-with-offsets / fixed-size string, conversion of the Arrow date/time units) and is included by `arrow.slang` and, with `-DARROW_SRC`, by `agg.slang`, `gagg.slang`, `join.slang`, `jagg.slang` and `jgagg.slang` (and through them `join_walk.inc`). With `ARROW_SRC` the kernels' "page" is a **virtual page of 256 consecutive rows** of the record batch (`arrow_page_rows()` / `arrow_page_row0()` read the pass's row count and first row from two words after the column table), the "line pointer" is the row inside it, and `eval_row()` becomes `arrow_eval_row()`; everything else (page loops, per-thread accumulators, the group table's A/B/C rounds, the join walk, the partial-state protocol, the host merges) is the code of the heap path, so the "no GROUP BY" and "GROUP BY with a per-workgroup table" designs carry over unchanged, as do the 16/32-register x 4/8/12-aggregate variants. New SPIR-V: `aagg`, `agagg`, `ajagg`, `ajgagg` (16/32 registers x 4/8/12 aggregates) and `ajoin` (16/32). The 8-register variants are not built (a small program uses the 16 one).
- **GROUP BY overflow.** The heap path re-evaluates a row that found no slot on the CPU from the heap tuple (`cpu_eval_row`). An Arrow row has no tuple to hand over, so `gagg.slang` under `ARROW_SRC` appends the staged key and aggregate values to an overflow list like `jgagg.slang`'s (count at the word the push constant names, capacity in `kparam.extra`; the host re-runs the pass with room if it was too small), and `scan_group_merge_overflow()` adds them to the groups. Nothing is lost, no CPU re-evaluation is needed.
- **Service (`arrow_exec.c`).** `arrow_task` (data, column table, packed GPU copy, program) is shared by four task kinds: `scan_exec_arrow_task` (GpuScan, as before), `scan_exec_arrow_agg_task` (with and without GROUP BY; `wire.c` routes a PREAGG session whose task source store is `KDS_FORMAT_ARROW` there), `scan_exec_arrow_join_task` (match records `{ virtual page, row, inner items, computed values }`; result tuples formed from the Arrow buffers for the outer columns, `arrow_inner_col()` for the inner items, the GPU values for computed columns incl. numeric) and `scan_exec_arrow_joinagg_task` (join aggregation). A record batch is processed in passes (aggregation: bounded by the size of the per-workgroup output; join: 1M rows). The merges are the heap path's, exported from `scan_exec.c` (`scan_agg_merge_workgroups`, `scan_group_merge_blocks`, `scan_group_merge_overflow`, `scan_join_merge_ojmap`). RIGHT/FULL joins work (the outer-join map merge is the same), also under GpuPreAgg (see "GpuPreAgg over RIGHT and FULL joins").
- **Parquet.** A Parquet row group arrives inline as an Arrow-format store, exactly as for GpuScan, so all four tasks work on it with no further code. The backend still decodes it on the CPU.
- **Value types.** The Arrow loader reads date32 (days since 1970 -> since 2000), time32/64 in s/ms/us/ns, timestamp in s/ms/us/ns (same wrap-around arithmetic as `pg_datum_arrow_ref()`), utf8 and large_utf8 (offsets and bytes are copied into the packed buffer; the register is `{offset | length << 32}` like a heap string), and `char(n)` (fixed_size_binary mapped to bpchar) as quals, join keys, group keys and aggregate arguments. `arrowFdwGpuScanSupported()` therefore only refuses a qual that reads or produces a numeric (`__arrowQualNeedsUnsupportedValue`): numeric would need the backend's per-row re-check, which an Arrow batch cannot do. Decimal columns themselves still keep the table on the CPU.
- **Planner.** `gpu_join.c` and `gpu_preagg.c` no longer call `pgstromPathScansArrowFdw()` (the function stays in `gpu_scan.c`). The gates are the heap ones. Plans over tiny Arrow tables (one batch of a thousand rows) are still chosen by cost and may stay on the CPU.
- **A fix found on the way (affects heap too): parallel GpuPreAgg lost rows.** `executor.c` let only the *last* process of a parallel plan send `XpuTaskFinal` (the CUDA service kept one final buffer per plan, shared by all processes), but this service keeps the partial aggregates per session, so the partial states of the other processes were dropped whenever more than one process really scanned. The old parallel tests passed because the leader usually scanned everything before the workers started; with Parquet decoding on the CPU the workers do participate and the aggregate came out as 1/6 of the data. Now every process of a PREAGG plan fetches its own partial result (RIGHT/FULL join emission still uses the last-process rule). Tests: "parallel workers only" with `parallel_leader_participation=off` on Arrow and Parquet.
- **Tests** (`test/gpuserv/arrow_tests.inc`, sourced by `scan_test.sh` before `types_tests.inc`; `sh test/gpuserv/locked_test.sh "$PWD" arrow_dev.sh` runs it alone on a smaller data set, `/tmp/a5b_adhoc.sql` runs ad hoc SQL there; `arrow_gen_ext.cpp` writes the extra files: an Arrow and a Parquet copy of the dimension table `sd`, `sd2` as Arrow, and `at1`/`at2` with timestamps of every unit, dates, times of every unit, utf8, large_utf8, char(5)). GPU result vs `pg_strom.enabled=off` by md5 of the sorted rows, and the plan must show the offloaded shape, on `a1` (3 batches, the last short), `a2` (one batch of 1003 rows), `a3` (two files, odd batch sizes) and `p1` (Parquet): aggregates with and without GROUP BY (NULLs, empty input, FILTER, expressions, sums beyond 64 bits, text/date/timestamp quals, 9 aggregates, int8/date/timestamp keys, the overflow list, two keys, text key and float8 aggregate staying on the CPU, parallel workers); joins (inner, LEFT, semi, anti, RIGHT, FULL with heap dimension tables; stacked two and three relations; an Arrow and a Parquet dimension table); aggregation over a join (with and without GROUP BY, keys from either side, the NULL group of a LEFT join, EXISTS / NOT EXISTS, two inner relations); and the value types on `at1`/`at2` (every timestamp/time unit as qual, projection, group key and join key against heap date/timestamp tables). Where the planner may legitimately pick the CPU (tiny tables, group estimates of expression keys) the check compares results only.
- **Measurements** (`test/gpuserv/arrow_bench.sh`, 16.8M rows, 9 columns, 2.2 GB, 8.4 batches of 2M, `EXPLAIN ANALYZE` execution time, three runs each (the first is cold), M1 Pro, 8 CPU cores; **the machine was shared with other agents' test runs, so the numbers are noisy by +-30%**):

## A6 status (four parts done: temporal types and text; numeric; numeric division/rounding/aggregates; kernel specialization and GROUP BY speed. The fuzzer is not started here)

**Scope of this slice:** more SQL types in the scan VM, so that more quals, projections, GROUP BY keys and join keys run on the GPU. Everything below is implemented in `scan_caps.c` (classification by opcode name, shared with the planner), `scan_prog.c`, `kernels_vm/scan_common.slang` (`vm_ext()`, a new instruction group dispatched from the `default:` of `vm_run`) and `cpu_vm.c` (the C copy used for GROUP BY overflow rows). New instruction numbers are far from the old ones (40+, 60+) in `scan_vm_ops.inc`, so merges with other work stay easy.

**Temporal types (exact, plain integers).** `date` (int4 days), `time`, `timestamp`, `timestamptz` (int8 microseconds) are VM integers (`reg_vtype`), so columns load like int4/int8, pass-through and `IS NULL` work as before, and infinities are INT_MIN/INT_MAX where the integer order is the right order.
- GPU: `=, <>, <, <=, >, >=` of the same type; `date` against `timestamp` in both directions (the date is converted with `D2TS`, saturating exactly as PostgreSQL's `date2timestamp_opt_overflow`: infinities map to infinities, a date beyond the largest timestamp compares greater than every finite timestamp); `date + int4`, `int4 + date`, `date - int4`, `date - date` (`DATEOP`, with "date out of range" and "cannot subtract infinite dates"); `date::timestamp` (error "date out of range for timestamp" outside the timestamp range) and `timestamp::date` (`TS2D`, floor of the days). `min`/`max` of date/time/timestamp/timestamptz and `count()` use the existing integer aggregate actions; `date`/`time`/`timestamp`/`timestamptz` are GROUP BY keys and GpuJoin hash-join keys (`scan_vm_groupkey_type_supported`; the device hash of these types is the Jenkins hash of the 4/8 stored bytes, which `HASHMERGE` already computed for int4/int8).
- Not on the GPU (by design): comparisons of `timestamptz` with `date` or `timestamp` (they use the session time zone), `timestamp + interval` and everything with `interval` (16 bytes, month/day/time semantics), `timetz`, `extract`, `date_trunc`, `timestamptz::date`, `overlaps`.
- A GROUP BY with a 64-bit min/max aggregate (timestamp) overflows those rows to the CPU path of the service (the shared-memory table keeps 32-bit min/max): correct, not fast.

**Strings (`text`, `varchar`, `bpchar`).** Design: a *string register* is one VM register holding `{ byte offset | length << 32 | source << 60 }` of the varlena payload in the buffer it lives in (source 0: heap pages of the file, 1: pages the backend loaded, 2: join inner buffer, 3: the program's **constant pool**). The pool (header word 20 of the program) holds string literals and LIKE literals; `CONSTSTR` makes a register that points into it. Instructions: `STRCMP` (bytewise, `bpchar` ignores trailing blanks), `STRLIKE`, `STRLEN`. Nothing is copied: the kernel reads bytes from the page buffer (4 bytes at a time, unaligned).
- GPU: `=`, `<>` for text/varchar/char(n) (bytewise: exact for every **deterministic** collation; the planner refuses non-deterministic ones through `get_collation_isdeterministic`); `<`, `<=`, `>`, `>=` only in the C collation (the existing `DEVFUNC__LOCALE_AWARE` check); `LIKE`/`NOT LIKE` with a **constant** pattern that is a literal with `%` before and/or after it (`'abc'`, `'abc%'`, `'%abc'`, `'%abc%'`, `\` escapes; `scan_vm_like_shape()` is shared by planner and service), for UTF-8 and single-byte databases only (bytewise search is exact there); `length(text)` for UTF-8 (counts non-continuation bytes). `count(text)`, `IS NULL` on text read only the NULL-ness. 1-byte and 4-byte varlena headers are both handled.
- Not on the GPU: `_` and inner `%` in LIKE, `ILIKE`, regular expressions, `upper`/`substr`/concatenation, text GROUP BY keys and join keys, strings in **any GpuJoin program** (outer scan quals of a join included: the codegen refuses text functions for `DEVTASK__JOIN` and `scan_prog_build_join` fails on a string register), `IN` lists, ordering in non-C collations, non-deterministic collations, `length` outside UTF-8, text parameters in a LIKE pattern (a Const is required to know its shape at plan time).
- **Compressed and out-of-line (TOAST) values.** The kernel cannot read them. `deform_tuple` sets `g_recheck` when it needs the *value* of a column whose varlena header says compressed (4-byte header with the compression bit) or external (1-byte header 0x01); `IS NULL`/`count(col)` never need the value and never trigger it. The row is not evaluated on the GPU: scan writes flag 2 instead of 0/1, GROUP BY writes flag 2 in its overflow-flag array, aggregation without GROUP BY got a flag array too. The service copies the raw heap tuple (with its block number and line pointer) into a new chunk of format `KDS_FORMAT_RECHECK` (`kern_recheckitem` in `xpu_common.h`): in the task reply for a scan, in the `XpuTaskFinal` reply for aggregation. The backend (`execCpuRecheckOneChunk` in `fallback.c`, called from `tryExecCpuFallbackChunks`) evaluates each such tuple from the start with the existing CPU fallback (`execCpuFallbackBaseTuple`: quals, projection, and for GpuPreAgg the partial-aggregate expressions, so PostgreSQL's Agg node combines them). Parallel workers each do their own. `EXPLAIN` does not show how many; `client_min_messages = debug1` prints "CPU re-evaluation of N tuples" per chunk, which the test uses.

**Files:** `scan_vm_ops.inc`, `scan_common.slang`, `scan.slang`, `agg.slang`, `gagg.slang`, `cpu_vm.c`, `scan_caps.[ch]`, `scan_prog.c`, `scan_exec.[ch]`, `xpu_common.h`, `codegen.c` (`vulkan_text_func_allowed`), `fallback.c`, `executor.c`, `pg_strom.h`, `test/gpuserv/types_tests.inc` (sourced by `scan_test.sh`).

**Tests:** `types_tests.inc`, new tables `ty1` (all-visible) and `ty2` (updates and deletes) of 300,000 rows with NULLs, infinities, microseconds, empty strings, multibyte UTF-8, values over 127 bytes, values over 2 KB stored compressed and out of line; GpuScan, GpuPreAgg (with and without GROUP BY) and GpuJoin results are compared with the CPU's, plus "stays on the CPU" shapes and the error texts of date arithmetic.

**Known gaps:** specialization and the fuzzer (the other A6 items) are untouched (numeric: see the second slice). `LIKE` is limited as above. Rechecked rows are collected in the service until the reply (an all-TOAST table makes the service hold the whole table's tuples for an aggregate; a scan sends them per task). A join whose *inner* side needs a text comparison, and text join keys, need the same recheck path in `join.slang` (matches there are produced depth first, so a row would have to be retracted); not started. `date_to_timestamp`/`timestamp_date` casts through `timestamptz` are not implemented. The `DEVTASK__JOIN` refusal also keeps text quals of a join's *outer* relation on the CPU.

### A6, second slice: numeric

**Design decision: a numeric register is `{ unscaled int64, scale }`, and what does not fit is rechecked by the backend (option b).** A 128-bit value would need limb pairs in every register, in the column loader, in the result tuple and in 32-bit-limb multiply/compare kernels (Metal has no int128 and no int64 subgroup ops), and PostgreSQL's `numeric` is arbitrary precision anyway, so 128 bits would still need a fallback. The common money/measure columns (`numeric(10,2)`, `numeric(18,6)`) fit 64 bits unscaled, so the exact int64 core with the existing `g_recheck` / `KDS_FORMAT_RECHECK` path covers them and never produces a wrong answer. `Reg` got a third field `sc` (the scale; it fills the padding of the 16-byte struct, so register files do not grow). Invariants: `|v| <= INT64_MAX` (never INT64_MIN, so negation is safe) and `sc <= 255`; `sc` is PostgreSQL's dscale, so a computed value prints exactly as PostgreSQL prints it.
- **Loading.** `deform_tuple` decodes the numeric varlena (`num_decode`: short and long header, sign, dscale, weight, base-10000 digits, `v = digits * 10^(4*(weight-ndig+1)+dscale)`, exact division when digits stand beyond dscale). It sets `g_recheck` (the row goes to the backend) for NaN, +-Infinity (`n_header & 0xC000 == 0xC000`), compressed or external varlenas, more than 5 digits, a value over INT64_MAX, dscale over 255. `IS NULL`, `count(col)` read only the NULL-ness (`VT_NULLONLY`), so NaN/huge values never trigger a recheck there. The same decoder exists in C (`scan_vm_numeric_payload_decode` in `scan_caps.c`, used for constants, the planner's check and `cpu_vm.c`).
- **Instructions (`vm_num`, numbers 80-84, `scan_vm_ops.inc`).** `NUMCONST`, `NUMCMP` (exact for different scales: the smaller scale is scaled up; if that overflows, the sign of that operand decides, so comparison never needs a recheck), `NUMARITH` (`+`, `-`: scale = max, aligned by 10^d with overflow check; `*`: scale = sum, 64-bit overflow check; `numeric_uminus`, `numeric_abs`; `numeric_uplus` is a MOV), `I2N` (`intN_to_numeric`), `N2I` (`numeric_to_int1/2/4/8`: rounding half away from zero). Overflow, a scale above 255, or an integer cast out of range returns `SOP_RECHECK_CODE` (0x7ffffffe): `eval_row` turns it into `g_recheck` and the backend re-evaluates the row from scratch, which also yields PostgreSQL's own error text for out-of-range casts and NaN -> int.
- **Result tuples.** A computed numeric is written as `{ isnull | scale << 8, lo, hi }`; `form_tuple` (`scan_exec.c`) encodes it with `scan_vm_numeric_encode` exactly as `make_result` does (base-10000 digits aligned to the decimal point, leading/trailing zero digits stripped, short header when dscale <= 63 and -64 <= weight <= 63, else long header, 1-byte varlena header). The host now tests NULL with `& 1`.
- **Planner (`codegen.c`).** Numeric Consts are pushed down only if they decode (no NaN/Infinity, fits 64 bits); numeric Params and pseudo-constants are refused (the program builder could not know that the value fits). Numeric functions are refused in GpuJoin programs (outer quals included); GpuPreAgg may use numeric quals (the GROUP BY overflow path of the service has the same VM in `cpu_vm.c`, and its recheck rows are handed to the backend), but numeric aggregate arguments/actions and numeric GROUP BY/join keys are not offered. `arrowFdwGpuScanSupported` refuses quals that touch numeric.
- **Not on the GPU (first slice; division, rounding, sum/avg and group keys came in the third slice below):** float/money casts, text -> numeric, `min`/`max` of numeric, numeric join keys, numeric in a GpuJoin program, numeric Params.
- **Pitfalls found:** `ld16()` of the page loader assumes 2-byte alignment (it only special-cases offset 3 mod 4), but the payload of a 1-byte-header varlena is at an odd offset, so the digits are read with `ld16u()` (byte loads). A constant `int64_t` array (powers of ten) did not look wrong but was replaced by a computed loop to stay clear of MoltenVK/Metal constant-array handling. The planner checked the join quals and the outer scan quals of a GpuJoin with the SCAN task flags while the program is built with the JOIN flags, so "refused in a join" gates (text, numeric) raised an error at plan time; `gpu_join.c` now checks both with the JOIN flags.
- **Tests:** `test/gpuserv/numeric_tests.inc` (sourced by `scan_test.sh` after `types_tests.inc`; `test/gpuserv/numeric_test.sh` runs only that section, with the prelude cut out of `scan_test.sh`). Tables `nm1` (all-visible) and `nm2` (updates, deletes) of 300,000 rows with `numeric(10,2)`, `numeric(18,6)`, `numeric(38,10)` (values beyond 64 bits, tiny values) and unconstrained `numeric` (integers, long fractions, NaN, +-Infinity, 1e20+, zeros with a scale, trailing zero digits, dscale 70 for the long header and dscale 140 for its square).

### A6, third slice: numeric division, rounding, aggregates and group keys

**Done (all exact; a row that does not fit goes to the backend, a wrong answer is never produced).**
- **Division, remainder.** `numeric_div` reproduces `select_div_scale()` of `numeric.c`: the result scale is `max(16 - 4 * qweight, dscale1, dscale2, 0)` (cap 1000, above 255 the row is rechecked) where `qweight = weight1 - weight2 - (firstdigit1 <= firstdigit2)`; weight and first base-10000 digit are derived from `{unscaled, scale}` as `make_result` would normalize it (`num_weight_firstdigit`). The quotient `round_half_away(a * 10^E / b)` (`E = sb + rscale - sa`) is a long division in chunks of 18 digits; the 128/64-bit step (`rem * 10^k / b`) is done bit by bit with 32-bit-limb products in Slang (`num_divround`, no int128 type) and with `unsigned __int128` in C (`scan_vm_num_div`). `numeric_mod`/`mod` (scale = max of the two, truncated, sign of the dividend) and `div()` (scale 0). A zero divisor, a quotient above INT64_MAX or a scale above 255 returns `SOP_RECHECK_CODE`, so the backend raises PostgreSQL's own "division by zero".
- **Rounding.** `round(n, k)` / `trunc(n, k)` (the one-argument forms are the same function with k = 0; negative k rounds to tens/hundreds, result scale 0), `ceil`/`ceiling`/`floor`/`sign` (scale 0), and the `numeric(p,s)` typmod coercion (`numeric_typmod`, new `FUNC_OPCODE(numeric, numeric/int4)`: rounds or pads to s; "numeric field overflow" is left to the backend by a recheck). New VM instructions `NUMDIV` (85), `NUMRND` (86), `NUMARITH` with `NUMOP_CEIL/FLOOR/SIGN`.
- **Verification of the scale rule and the algorithms.** `test/gpuserv/numfuzz.sql` generates random operand pairs in PostgreSQL (1 to 18 significant digits, scales 0 to 59, both signs, zeros, runs of 9s and 0s, shared leading digits, ties for rounding) with PostgreSQL's own results for `/`, `%`, `div`, `round`, `trunc`, `ceil`, `floor`, `sign` and `numeric(p,s)`; `test/gpuserv/numfuzz.c` links `scan_caps.c` and compares the C helpers (which the Slang code mirrors line by line) byte for byte: 1,500,000 pairs, 11,072,810 results compared, 0 mismatches (2,427,190 results are handed to the backend as not representable, which is not a mismatch). The Slang version is exercised by `nm_fz` (a 300,000-row table of such pairs) in `numeric_tests.inc`, GPU result md5 against the CPU's; the C copy in `cpu_vm.c` shares the helpers. (Build the fuzzer with `cc -DCUDA_MAXTHREADS_PER_BLOCK=512 -I src -I src/gpuserv -o numfuzz test/gpuserv/numfuzz.c src/gpuserv/scan_caps.c`.)
- **sum(numeric), avg(numeric)** (GpuPreAgg over a scan, with and without GROUP BY). Accepted only when the *scale of the argument is fixed by the plan* (`pgstrom_numeric_static_dscale()` in `codegen.c`: `numeric(p,s)` columns, constants, and `+ - *`, `abs`, unary minus, `round(x, const)`, `ceil/floor/sign`, `div()`, `numeric(p,s)` casts, int casts of those; not `/`, not unconstrained numeric). The device sums the unscaled int64 values with the existing exact integer-sum machinery (`agg.slang` 32-bit halves, `gagg.slang` 16-bit limbs of the biased value; the service adds up in 128 bits) and the service forms `kagg_state__psum_numeric_packed` with `attrs & 0xffff = dscale` and the 128-bit unscaled sum, so `fsum_numeric`/`favg_numeric` print the same text as the CPU's `sum()`/`avg()` (dscale of the sum = maximum dscale of the inputs, `avg = sum / n` through `numeric_div`). The aggregate entry word 3 carries `scale + 1`; the kernels check each qualifying row (`agg_scales_ok`) and the service checks the CPU-overflow rows, and a row of another scale than the plan's goes to the backend's recheck. Rows whose numeric does not fit int64 (more than 18 digits, NaN, Infinity) are rechecked as for quals; the backend computes their partial state with `pgstrom.psum(numeric)`, which was rewritten: the state is `{ attrs: dscale | NaN/+Inf/-Inf flags | BIG, nitems, int128 sum }` and the combine function adds at the larger scale in int128 and, on 128-bit overflow or an input that does not fit, switches to a BIG state holding the sum as a numeric varlena (appended to the struct) computed with `numeric_add`. Old states of the earlier format (a `weight` instead of a dscale) are not produced anymore by anything.
- **GROUP BY a numeric key** of a known scale (up to two keys, mixed with integer keys). The key is the unscaled int64 (the scale is fixed, so 1.0 and 1.00 cannot meet inside one group; NULL is the NULL group); the result key is formed with `scan_vm_numeric_encode(v, scale)` exactly as the CPU would print it.
- **Not on the GPU (stay on the CPU):** `min`/`max` of numeric (the catalog's partial state is a float8 and would be inexact; a numeric partial state would need its own final functions), `sum`/`avg` and GROUP BY of numerics whose scale depends on the row (unconstrained `numeric` columns, quotients), numeric -> float casts, numeric Params; **numeric inside GpuJoin programs, numeric join keys and numeric aggregates/keys of a GpuPreAgg over a GpuJoin** (see below).

**Why joins were not done.** A numeric hash-join key would need the device hash to equal the backend's `devtype_numeric_hash` (it hashes the weight and a 128-bit normalized value, not the `{int64, scale}` register) and, more importantly, a numeric that does not fit would have to be rechecked inside the join kernels: matches there are produced depth first, so a row would have to be retracted (the same open problem as text join keys, A6 first slice). Numeric quals on the outer side of a join and numeric join quals have the same recheck problem. Pass-through of numeric columns in joins already works. Not started; the required change is a retraction/recheck path in `join_walk.inc`, after which the program builder's `no_strings` refusal can be lifted for numeric (`Reg.sc` is already carried through the join registers).

### A6, fourth part: kernel specialization (done) and GROUP BY speed

**Result.** A query that runs more than one task gets a kernel generated from its program: per 64 MB task aggregation without GROUP BY is 3-9x faster than the interpreter (a trivial qual no longer doubles the time), GROUP BY 2-9x, aggregation over a join 4-9x, GROUP BY over a join 13x. End to end on 16.8M rows (M1 Pro) the GPU now beats 8-worker PostgreSQL for aggregates (3.5-5x), GROUP BY up to about a hundred dense integer groups (4-5.7x), aggregates over a join (4.8x) and GROUP BY over a join (3.5x); see the table at the end. `pg_strom.gpupreagg_max_groups` defaults to 128 now (16 before).

**Design.**
- **The generated code is not a second VM.** `src/gpuserv/specialize.c` turns a session's program (`scan_prog` words: instructions, column tables, aggregate/key/computed-value tables, join depth tables) into Slang source, `spec_gen.inc`, that the kernel includes at a `SPEC_PROG` hook (the kernels `scan.slang`, `agg.slang`, `gagg.slang`, `join.slang`, `jagg.slang`, `jgagg.slang` and `arrow.slang`, `join_walk.inc` keep their code; the hooks replace the places that indexed registers or read the program dynamically). Every instruction except `AND`/`OR` (forward jumps: a flag guards the skipped instructions) is a call `vm_step(op, dst, ra, rb, k0, k1, ip, regs)` with literal operands: `vm_step()` is the old body of `vm_run()`'s `switch` moved into a function (the case bodies are byte for byte what they were), so the generated kernel executes the interpreter's own helpers (numeric, strings, overflow checks, `vm_ext`) and the Metal/SPIR-V compilers fold the switch and turn the register array into constant-indexed locals. The column loads are `deform_col(c, desc, ...)` / `arrow_load_col(c, desc, row, regs)` (the body of the old column loops) with constant `c` and descriptor. What the VM kernels computed from program words dynamically (aggregate accumulation, key and aggregate staging for the group table, projection stores, the join's hash / join-qual / projection sections and inner column loads, the outer row's qual evaluation) is generated with constants (`spec_acc`, `spec_stage`, `spec_store_comp`, `spec_hash`, `spec_jqual`, `spec_inner`, `spec_eval_row`, `spec_arrow_eval_row`, `spec_scales_ok`). Words that depend on the query's data, not its text, are not baked in (the inner buffer layout of a join), so a kernel is reusable across executions.
- **Fall back to the VM, never miscompile.** `spec_generate()` refuses (the program stays on the VM) an opcode that is not in its list (`op_known()`: the 31 opcodes of this commit; a new opcode added by someone else runs on the VM until it is added there after a look at whether it touches control flow), a register beyond the 32 of the VM, a malformed table, more than two keys. A compile or pipeline failure marks the session's program as VM-only. The register file is sized by the registers the instructions name.
- **Compile and cache (`spec_mgr.c`).** One worker thread per service (the only other thread; the service stays a poll loop): `slangc` run as a subprocess (found through `PGSTROM_GPUSERV_SLANGC`, the path it was built with, or `PATH`; its version is part of the key) on `main.slang` = `#include "spec_defs.inc"` (the `#define`s: register count, aggregate capacity, table slots, `SPEC_PROG`, `ARROW_SRC`) + the kernel file, with `-I` the scratch directory (holding `spec_gen.inc`) and the kernel sources, which are **embedded in the binary** (`gen_ksrc.sh`: all of `kernels_vm/`) and extracted once to `<cache>/src-<hash>/`. The SPIR-V is cached as `<key>.spv` beside the generated source `<key>.src` (key: two FNV-64 over kind, `slangc` version, the hash of the embedded sources and the text; a hit also compares the stored text, so a hash collision cannot load a wrong kernel); files are written to a temporary name and renamed (concurrent services); the directory is `$PGSTROM_GPUSERV_CACHE_DIR`, `$XDG_CACHE_HOME/pgstrom` or `~/.cache/pgstrom`, created 0700, pruned at service start (256 MB, least recently used first, other builds' source directories after a month). The **pipeline is created on the worker thread** (`gpu_vk_pipeline_create_ex()`: Vulkan pipeline creation needs no external synchronization; a private error buffer), so neither `slangc` nor the driver's compile (Metal 50-90 ms, lavapipe more) is ever on the dispatch path; the main thread reads an atomic state and gets the pipeline. Entries are shared by all sessions with the same text (two sessions that need the same new kernel at once queue one compilation), reference counted by the sessions' programs, at most 64 kept.
- **When.** `PGSTROM_GPUSERV_SPECIALIZE` / `pg_strom.gpu_specialize`: `auto` (default) queues the compilation at the session's **second** task (a one-task query never compiles; `..._TASKS` changes the number) and the interpreter serves the tasks until the kernel is ready; a kernel already in the disk cache is used **from the first task** (the task waits for the pipeline) and then the VM kernel's own pipeline is not even created (its first Metal compile took 0.8-4.5 s on a cold machine); `force` waits for the kernel at the first task; `check` is `force` plus a comparison of every dispatch; `off`. Without `slangc` and without a cached kernel the job fails ("slangc not found") and the VM runs, as it does if the cache directory is not writable (kernels are then compiled in a scratch directory each time the service starts).
- **Self-check (`check`, `spec_verify.c`).** Every dispatch runs the VM kernel on a copy of the output buffer's initial contents, restores it, runs the specialized kernel and compares the two outputs: word for word for the scan, aggregation and join-aggregation kernels (deterministic), as multisets of records for a join's match records and of the slot records of each workgroup's group table (their order depends on atomics); a dispatch whose group tables overflowed is "skipped" (which rows overflow depends on the slot race). A difference fails the query ("the specialized kernel differs from the VM"). `scan_test.sh` runs with it by default.
- **GROUP BY kernels.** The measurements below (sweep) showed that the kernel's time is dominated by the footprint of its group table in shared memory (a workgroup that needs more than a fraction of the 32 KB leaves no room for others on the core: 16 slots 2.5 ms per 64 MB task, 64 slots 2.9, 128 slots 4.1, 256 slots 6.6 for 7 groups) and by the barrier-separated rounds, not by the row evaluation or the number of atomics. Three changes: (1) the specialized kernel has the **exact aggregate count** (the output layout is the kernel's: `spec_pipe()` returns the shape, `scan_exec.c` and `arrow_exec.c` size the output and merge by it); (2) the table is **sized for the groups the session has seen** (`2 x groups`, between 16 and what shared memory allows) and grows while the old kernel keeps serving (a bigger kernel is compiled when `groups * 3/2` exceeds the slots; rows that find no slot are aggregated on the CPU as before); (3) **direct-mapped tables** (`gagg_dm.slang`, `jgagg_dm.slang`; join walk mode 3): when the session's keys (one or two) are integers in a small window (up to 4,096 wide, at most about 380 cells, not much sparser than the groups seen) a row's slot is `key - base` (NULL: the extra index), so nothing is staged, no slot is claimed and **no barrier separates rounds**: a thread adds its row with shared atomics at once (the 16-bit-limb sums of `gagg.slang`), the output layout is the hash kernel's, so the host merge is unchanged; a key outside the window, or a min/max argument beyond 32 bits, is handled as an overflow (a flag for heap rows, the overflow list for Arrow and join rows) and a window exceeded later makes the service compile a wider kernel. The planner knows nothing of key ranges: the window comes from the groups the first tasks produced.
- **Stopped when returns vanished.** Tried: pages per workgroup 8/16/32/64 (no effect on the hash kernel: `PGSTROM_GPUSERV_GROUP_PPW`), 256-slot tables (slower), per-subgroup pre-reduction (not built: the direct-mapped kernel removed the barriers that made it attractive). Not done: per-aggregate compact slots (a count needs one shared word, a sum five), subgroup reductions of equal slots, a global-memory table for several hundred groups.

**What is specialized.** Heap and Arrow sources; scan, aggregation, GROUP BY (hash and direct-mapped), join, aggregation over a join, GROUP BY over a join; every VM opcode of `op_known()`. Everything else (an unknown opcode, `PGSTROM_GPUSERV_SPECIALIZE=off`, no compiler) runs on the VM unchanged.

**Safety nets.** VM fallback on any refusal or failure; `check` mode; the key includes the generated text and the kernel sources, and a disk hit is verified against the stored text; the 10 s dispatch watchdog is untouched because compilation and pipeline creation are off the dispatch path; the worker blocks all signals; at shutdown the worker is stopped (its `slangc` child gets SIGTERM) and joined.

## A7 status (part 1, GPU-Sort of GpuPreAgg groups: done for integer keys; GPU-Cache is not started)

**What the backend expects (read from the CUDA code).** The planner builds `GPU-Sort keys` (`gpusort_keys_expr/kind/refs` in `pgstromPlanInfo`) in `consider_sorted_groupby_path()` and `codegen_build_gpusort_keydesc()` turns them into a `FuncOpCode__SortKeys` expression sent as `session->xpucode_gpusort_keydesc`: per key `kind` (`KSORT_KEY_KIND__VREF` = a group key or count, `PSUM_INT64`, `PSUM_NUMERIC` (sum of int8), `PMINMAX_INT64`, ... `PAVG_*`, `PVARIANCE_*`), `order_asc`, `nulls_first`, `src_anum` (resno of the partial-aggregate column), `key_type_code`; plus `window_rank_func` / `window_rank_limit` / `window_partby_nkeys` / `window_orderby_nkeys` (rank filter) and `session->gpusort_limit_count` (LIMIT pushed down; `LIMIT` + `OFFSET` rows are kept and the Limit node above drops the offset). The CUDA service merged the per-GPU final buffers (`DEVTASK__MERGE_FINAL_BUFFER`), finalized the aggregates in the buffer, ran a bitonic sort (`cuda_gpusort.cu`), applied the rank filter or the top-N cut, and answered `XpuTaskFinal` with the sorted rows as final values: the plan has **no Aggregate and no Sort above the GpuPreAgg**, only a Projection for the final functions (`fsum_int(psum(..))` and so on, computed by PostgreSQL from the partial state).

**Design here.** The Vulkan service already keeps the groups of a session in `agg_state.groups` and answers `XpuTaskFinal` with one row per group. For a session with `xpucode_gpusort_keydesc` the reply is built by `scan_exec_agg_final_sorted()` (`scan_exec.c`): it computes the final value of every sort key of every group (key, count, 128-bit sum, min/max), encodes them as unsigned 32-bit words (`gpusort.c: gpusort_encode`: a NULL word first, then the value with the sign bit flipped and the bits complemented for DESC, 64 or 128 bits), sorts the row indexes, applies the cut and writes the groups in that order as the partial-state rows (same wire format; `fsum_int` etc. on the CPU finalize them). **The unsigned-word order is the sort order, so the same keys serve the device sort and the CPU merge sort**, and the row index is the last tie-breaker, which makes the order total and the GPU result bit-identical to the CPU engine's. The kernel (`kernels_vm/gsort.slang`): a bitonic network on row indexes; every workgroup first sorts a 512-index tile in shared memory, then for each merge size k the steps with distance >= 512 are one global compare-exchange dispatch each and the steps below 512 are one in-tile dispatch. No atomics, no inter-workgroup waits, no subgroup operations. All passes (45 for 70,000 rows) are recorded in **one command buffer** with a compute-to-compute barrier between them (`gpu_vk_dispatch_seq`, `gpu_vk_seq.c`), so the sort costs one submit. Padding indexes (>= n) sort last.
- **Window-rank filter** (`rank()`, `dense_rank()`, `row_number()` `<`/`<=` N per PARTITION BY): after the sort the service walks the sorted rows once and keeps those whose rank within the partition (the first `window_partby_nkeys` keys; the next `window_orderby_nkeys` keys order it) is below the limit; PostgreSQL's WindowAgg still computes the ranks (`Run Condition`), the filter only drops rows early.
- **Planner (non-parallel only).** `tryAddGpuSortedGroupByPath()` adds Projection -> GpuPreAgg (no Aggregate) with the sort keys as pathkeys. It is not built for parallel plans (every worker has its own session, so no session sees all groups) nor with `pg_strom.cpu_fallback = on`, HAVING, DISTINCT. `lookup_gpusort_keykind` returns the aggregate action; `scan_vm_gpusort_key_supported()` (`scan_caps.c`) lists what the service sorts: GROUP BY keys of bool/int1-8/date/time/timestamp(tz) (the integer representation is sorted, so no device compare handler is needed), `count(*)`/`count(x)`, `sum` of int1/2/4/8, `min`/`max` of int1/2/4/8 and dates/times. **Not sorted on the GPU (the CPU sorts, the plan has a Sort node):** `avg`/variance/covariance keys, float and numeric sums, text keys, any expression that is not a GROUP BY key or an aggregate of the result, scan/join results (`gpu_join.c` returns early: the CUDA design needed a pinned final buffer), parallel plans. `float4` NaN keys: float GROUP BY keys are not offloaded by GpuPreAgg at all, so the NaN-after-everything rule is not exercised (the planner keeps those on the CPU; a differential test checks the rows).
- **Failure mode.** The sorted plan has no Aggregate above, so rows the CPU would have to evaluate (`KDS_FORMAT_RECHECK`: compressed/external values, numeric overflow) cannot be combined: the service fails the query ("GPU-Sort cannot combine N rows that the CPU has to evaluate; run the query with pg_strom.enable_gpusort = off"). `enable_gpusort` stays **off by default**.
- **Thresholds.** The device sorts n rows when `16384 <= n <= 4,194,304` (2^22 indexes) and `n * key_words * 4` is at most 512 MB and the device's `maxStorageBufferRange`; otherwise, and on any device error (logged: "GPU-Sort fell back to the CPU"), the CPU merge sort of the same keys runs. `PGSTROM_GPUSERV_SORT=cpu|gpu` forces an engine and `PGSTROM_GPUSERV_SORT_MIN` sets the threshold (the differential tests force `gpu`).
- **Measurements** (M1 Pro, `gpusort_check` with `GPUSORT_BENCH=1`: two keys, 8 words per row, whole call including key upload and index read-back, other agents were using the machine so treat as +-30%): 16,384 rows 1.2 ms GPU / 1.8 ms CPU; 65,536 5.1 / 8.9; 262,144 21 / 68; 1,048,576 97 / 483; 4,194,304 1047 / 2972. Break-even is about 16K rows, which is why that is the default threshold. For the groups GpuPreAgg serves (`pg_strom.gpupreagg_max_groups`, default 16) the CPU sort is the one that runs; the GPU sort only matters if that limit is raised. So GPU-Sort is **correct but not a speed-up for typical queries today** (the aggregation itself is the limit, A3).
- **Found and fixed on the way.** (1) With several parallel workers only the last worker sent `XpuTaskFinal`, so the partial aggregates of the other workers' sessions (held in the service per session, unlike the CUDA shared final buffer) were lost: every worker of a GpuPreAgg now fetches its own (executor.c; a test with `parallel_leader_participation=off` over 5M rows). (2) `pgstrom.fmin_i2/i4/i8` and `fmax_*` all call one C function that range-checked as int1 ("min(int8) out of range"): invisible while an Aggregate node used the combining functions, hit as soon as the final projection ran on the CPU; the width now comes from the declared result type (`aggfuncs.c`). (3) `DESC` keys were rejected by the planner (`__PathKeyUseGreaterThanCompare` test inverted).
- **Tests.** `test/gpuserv/gpusort_tests.inc` (sourced by `scan_test.sh` after `numeric_tests.inc`; `gpusort_dev.sh` runs only it): 52 checks, GPU vs `pg_strom.enabled = off`, output order hashed: one and several keys, ASC/DESC, NULLS FIRST/LAST, sum/count/min/max keys, LIMIT, LIMIT+OFFSET, NULL group keys, ties, over a join, rank/dense_rank/row_number filters, plus "stays on the CPU" shapes (avg, float4, bool group key, expression key), `enable_gpusort=off`, `cpu_fallback=on`, parallel settings, every group once, no device fallback in the log, and the parallel GpuPreAgg fix. `src/gpuserv/gpusort_check.c` (`make -C src/gpuserv gpusort_check`) compares the device and CPU sorts on random keys (14 sizes from 2 to 70,000 rows around the tile boundaries, 64/128-bit, NULLs, ties, window filters against a naive reference). The upstream `gpu_sort` test groups by `char(10)` columns, which GpuPreAgg does not take, so its plans stay on the CPU there: it passes with `gpu_sort_9.out` (rows equal the CPU run) and is in `vulkan_schedule`.
- **Known gaps.** GPU-Cache (the other half of A7) is not started. Sorting scan/join results, sorting on `avg`/float/numeric/text, parallel plans, string group keys. A real speed-up needs a many-group GpuPreAgg (A3) first.

## A8 status (done for quals, aggregate arguments and number extraction; a jsonb or text value *computed* from a document stays on the CPU)

**Design.** A jsonb value is a varlena whose payload is a `JsonbContainer` (`utils/jsonb.h`): a header word (count | object/array/raw-scalar flags), the JEntry words (the keys, then the values, of an object), then the data. A JEntry carries the type of the child and its length; every 32nd entry (`JB_OFFSET_STRIDE`) carries the end offset instead, so the start of child *i* is found by walking back to the previous end offset. Strings are stored as is, numerics and nested containers are aligned to 4 bytes from the start of the data, keys are ordered by length and then bytes (binary search). The VM keeps the string-register design: a jsonb register is `{ offset | length << 32 | source << 60 }` of the container in the page buffer (nothing is copied), and `Reg.sc` says what it points at (the JEntry type: 0 string payload, 1 numeric varlena, 2 false, 3 true, 4 JSON null, 5 container). A column loads as kind 5 (`SOP_VT_JSON`, in `deform_tuple`, with the same compressed/external test as strings: such a row goes to the backend, `KDS_FORMAT_RECHECK`). An element reached by `->` is a register of the same shape (scalars are not wrapped in a new container, which is why no value is ever built on the device). Because no jsonb or text value can be returned from the device, nothing that is a computed jsonb/text result is pushed down (`pgstrom_xpu_expression` refuses a text/varchar/jsonb expression that is not a column); quals, aggregate arguments and numbers computed from a document are.
- **Instructions** (`scan_vm_ops.inc`, 100-106; `scan_common.slang` `vm_json()`, mirrored by `cpu_vm.c` and by the C helpers `scan_jb_*` in `scan_caps.c`): `JSONGET` (`->` with a text key, binary search, or an integer index, negative from the end; a scalar behaves as a one-element array as in PostgreSQL), `JSONTXT` (`->>`: a string is the same bytes, `true`/`false` are literals in the constant pool, a JSON null is SQL NULL), `JSONEXISTS` (`?`: object key, or string element of an array), `JSONTYPE` (`jsonb_typeof`, literals from the pool), `JSONNUM` / `JSONINT` (the planner's `(x ->> key)::numeric / int2 / int4 / int8` shortcut), `JSONCONT` (`@>`).
- **`@>`** against a constant is compiled by the program builder (`scan_vm_jsonb_pattern()`, shared with the planner) into a conjunction of terms in the constant pool: a path of object keys and either "equals this scalar (same JSON type; numbers compared by value, `1 = 1.0`)", "is an object" (`{}`), "is an array" (`[]`, nested only) or "is an array holding this scalar". Shapes it expresses exactly: objects whose values are scalars, objects, empty arrays or arrays of scalars (to depth 6, 48 terms), a non-empty root array of scalars. Everything else (arrays of arrays/objects in the pattern, a raw scalar, the empty root array, a number that does not fit) is refused by the planner and stays on the CPU. PostgreSQL's quirks were checked against a plain server (a raw scalar never contains an array pattern, `'[{"a":1}]' @> '{"a":1}'` is false, ...) and by differential tests on random documents.
- **Exactness.** Whatever the kernel cannot decide returns `SOP_RECHECK_CODE` and the backend evaluates the row with PostgreSQL's own code: a number that does not fit `{ int64, scale }` (numeric decoding is the A6 one), malformed container data, a string cast to a number (`(d->>'k')::int` of `"5"`), and `->>` of a number or of a container where the text itself is needed. That text is a *deferred text* (bit 62 of the register set): it can be tested for NULL on the device (`d->>'k' IS NULL`), every other use (comparison, LIKE, length) rechecks the row. `(x->>k)::intN` is evaluated on the device only when the number has scale 0 and is in range (the text then parses); `1.50` or `1e30` take the backend, which raises PostgreSQL's own "invalid input syntax"/"out of range" error. Float casts, int1 and every other `CoerceViaIO` are not pushed down (the generic text->number cast, which used to be planned and then fail in the service, is now refused by the planner).
- **Planner (`codegen.c`).** `jsonb_object_field`, `_text`, `jsonb_array_element`, `_text`, `jsonb_exists` (its signature in `xpu_opcodes.h` said `jsonb/int4`), `jsonb_typeof`, `jsonb_contains` are classified in `scan_caps.c`; the first argument must be a column or the result of another of these (no jsonb constant or parameter has a register); join programs and Arrow tables never get jsonb (a jsonb column still passes through a GpuJoin); jsonb constants are accepted only as the pattern of `@>`.
- **Not on the GPU:** jsonb/text values in the target list (`SELECT d->>'k'`: the column is read and the CPU evaluates it; forming a result from a sub-range of the page needs the host to resolve `{source, offset}` in every result path and, for numbers and containers, PostgreSQL's text output; not started), float casts, `jsonb = jsonb` and ordering, `#>`, `?|`, `?&`, `<@`, `jsonb_array_length` and the other functions, `@>` with the unsupported shapes above, jsonb parameters, jsonb inside GpuJoin programs, jsonb in Arrow tables. The upstream `dtype_jsonb` test passes (`dtype_jsonb_9.out`: its numeric sums of extracted numbers now run on the GPU, the rest of its projections stay on the CPU; rows equal the CPU oracle).
- **Tests.** `test/gpuserv/jsonb_tests.inc` (sourced by `scan_test.sh` after `numeric_tests.inc`; `jsonb_test.sh` runs only it): 219 checks, GPU vs CPU result md5 on `jb1` (all-visible) and `jb2` (updates, deletes), 200,000 rows each of 21 document shapes (40 keys, so that the 32-entry offset stride matters; nested objects; arrays, also over 32 elements; raw scalars; empty containers; escapes and UTF-8; numbers with exponents, fractions, `-0`, beyond 64 bits; equal-length and 100-byte keys; strings that look like numbers; compressed and out-of-line documents) and on `jb_rnd` (random documents with up to 44 keys of 3 to 5 bytes, 7 keys probed with 5 query shapes each, `@>` with random subsets and whole documents of 6 rows as patterns), joins (pass-through, jsonb quals keep the outer scan on the CPU), aggregates (also GROUP BY a key computed from a document, which overflows to `cpu_vm.c`), errors raised alike, and "CPU re-evaluation" counts (toasted and numeric-text rows are rechecked, plain ones never). Bugs it found: the container bound check (`count > clen / 8` rejected arrays), pool offsets of the `true`/`false`/type-name literals in Slang (the pool address is `prog[20] * 4 + k0`), and `1ul << 62` in Slang being a 32-bit shift (use `uint64_t(0x40000000u) << 32`).
- **Measurements** (M1 Pro, 3,000,000 documents of about 150 bytes, all-visible heap, warm; `jsonb_bench.inc`): `d->>'status' = 'open'` 225 ms GPU / 397 ms CPU (1 worker) / 171 ms CPU (2 workers); `(d->>'score')::int > 990` 222 / 425 / 188; `d ? 'k8' and d @> '{...}'` 362 / 653 / 246; `d->'geo'->>'city' = 'c7'` with `sum(...)` 269 / 447 / 190; GROUP BY 5 groups with `d @> '{"status":"new"}'` 379 / 618 / 235. So the GPU is 1.7-1.8x faster than one CPU worker and slower than two: the kernel walks the document byte-wise through storage-buffer loads and the scan is bound by reading pages, not by the predicate. No speed claim beyond that.
- **Known gaps.** Computed jsonb/text results; the full `jsonb` operator set; specialization of the kernels by instruction group (the jsonb code is compiled into every scan/aggregate/join kernel variant, which grew the build and the first-dispatch compile on lavapipe somewhat; A6 specialization would remove that); no C-vs-PostgreSQL fuzz of the raw container reader beyond the SQL differential tests.

## A7 part 2 status (GPU-Cache: done for scan, aggregation and join over a cached table; the gpu_cache test is in vulkan_schedule)

**What the CUDA GPU-Cache promises (read from `master:src/gpu_cache.c`, `cuda_gpuscan.cu`, `man/gpucache.md`).** A table with an `AFTER INSERT OR UPDATE OR DELETE ... FOR EACH ROW` trigger on `pgstrom.gpucache_sync_trigger('options')` has its copy resident on the GPU; the first backend that writes or scans it builds it (a `SnapshotAny` heap scan sends every tuple that is committed, or that belongs to the backend's own transaction); the trigger sends one log record per inserted / deleted row version, and the transaction's end sends COMMIT / ABORT of every version it logged; a scan task (`XpuTaskExecGpuCache`) reads the cache through `KDS_FORMAT_ROW`-like items and a per-row check (`__gpuscan_check_row_visibility`): a version is visible if its `xmin` is `FrozenTransactionId` (committed) or one of the session's own transaction ids, and its `xmax` is not committed and not one of the session's ids. So the semantics are **"the latest committed state plus my own changes"**, not a snapshot: a REPEATABLE READ transaction sees rows committed after its snapshot. An UPDATE / DELETE plan scans the cache and projects `ctid`. Row versions are found by ctid (hash), `max_num_rows` bounds the row versions, an overflow marks the cache `corrupted` (WARNING "gpucache: rowid exceeds max_num_rows ... 'corrupted'"), `pgstrom.gpucache_recovery()` makes it rebuild. DDL (ADD COLUMN, DROP, TRUNCATE, rewrite, trigger changes) changes the table's *signature*, which keys the cache; the old one is dropped. The v6.2 SQL surface is `gpucache_info()` / `gpucache_info(regclass)` (json), `gpucache_apply_redo()`, `gpucache_compaction(regclass)`, `gpucache_recovery(regclass)`; options `gpumask`, `cache_size` (v6.2) and the older `gpu_device_id`, `max_num_rows`, `redo_buffer_size`, `gpu_sync_interval`, `gpu_sync_threshold`, which the upstream test (`test/sql/gpu_cache.sql`, written for the older design: it queries a view `pgstrom.gpucache_info` that v6.2 dropped) still uses. The CUDA service sent the log through pipes to a service thread and applied it with kernels; those parts are replaced (below). Kept as they are: the semantics above, the trigger and options, the initial-load visibility rules (`__initialLoadVisibilityCheck`, ported verbatim), the signature scheme, the phases (`not_built` / `loading` / `ready` / `corrupted`), the DDL callbacks, the explain lines of the upstream expected output.

**Design here.**
- **The cache is a columnar copy in one host-visible device buffer owned by the service** (`src/gpuserv/gcache.c`). Row slots `0 .. max_rows-1`; per column a validity bitmap and the values: fixed-length types (any `attlen` 1..1024) as `attlen` bytes per slot, `bool` as bits, varlena as `{ offset, length }` pairs into a per-column data region that holds the complete datum (header included, detoasted by the backend, so numeric, arrays, jsonb and text of any size pass through unchanged) and is compacted when it fills. Every type is stored; the GPU kernels read the ones the VM computes with (bool, int1-8, float4, date/time/timestamp(tz), text/varchar/bpchar) and the result tuples copy the rest. The buffer is written by the service's CPU directly (the buffers are host-visible, unified memory on Apple) and read in place by the kernels: **no page transfer and no per-task copy**. Limits: the buffer must fit the device's `maxStorageBufferRange` and 4 GB (32-bit offsets in the kernel); `max_num_rows` is clamped to what `cache_size` (default 512 MB) holds.
- **The cache is read as an Arrow record batch of row slots.** The Arrow kernels (`arrow_load.inc`: scan, aggregation, GROUP BY, join, join aggregation, all register variants) are reused unchanged except for two small additions to the loader: mode 5 reads a string from a `{ offset, length }` pair (skipping the datum's 1- or 4-byte header), and a **row filter**: `ptab[8*ncols+2] != 0` means the fifth buffer (`pagel`, a placeholder for Arrow) holds one bit per row slot and rows with a 0 bit do not exist. The service runs the task through the same `arrow_task` machinery (`arrow_exec.c`) with the cache's buffer as the GPU's data (`at->bg`, not owned) and the visibility bitmap as the filter; result tuples are formed from the cache (`gcache_fetch()`, the ctid from a host array). So scan, `GpuPreAgg` and `GpuJoin` over a cached table all work, and the planner / executor side is the existing one (`pgstromGpuCacheExecInit()` decides at executor start; `XpuTaskExecGpuCache` carries the table and signature plus a KDS header with the columns).
- **Visibility.** Per slot the service keeps `ctid`, `xmin`, `xmax` and a chain in a ctid hash. The bitmap `vis` has bit = "`xmin` is committed" (a version being deleted by a transaction in flight stays visible to everyone else). Versions of transactions in flight are listed under their transaction id, so `COMMIT(xid)` / `ABORT(xid)` finalize them without a scan (commit: `xmin` becomes frozen, a version whose `xmax` committed is freed; abort: an inserted version is freed, a deletion is undone). A task of a session whose transaction ids (`SerializedTransactionState.parallelCurrentXids`, already in the session) touch pending versions gets a patched copy of the bitmap; otherwise the cache's own bitmap is used.
- **The redo log: synchronous requests on the service socket instead of shared-memory buffers and pipes.** The backend appends the trigger's records to a buffer of its own (one INSERT per new row version with all columns deformed and detoasted, one DELETE per removed version), and **sends it (and waits for the answer) before the transaction commits (`XACT_EVENT_PRE_COMMIT`), before the backend itself scans a cache (read your own writes), and when the buffer reaches 4 MB**; at `COMMIT` / `ABORT` it sends the final status of every transaction id it logged (looked up in the commit log, so subtransactions need no bookkeeping beyond the id list). The data records reach the service *before* the commit is visible, so another transaction that updates a row after it sees the commit finds the earlier insert already applied; the commit flip is atomic for readers because the service is single-threaded. The CUDA design's asynchronous apply, `redo_buffer_size`, `gpu_sync_interval`, `gpu_sync_threshold` and `pg_strom.gpucache_log_buffer_size` / `_sync_*` are therefore accepted (validated, shown in `config_options`) but have no effect; a commit that touched a cached table waits for one round trip to the service.
- **The cache never gets silently wrong; it rebuilds.** Whenever the cache may not mirror the table the backend *invalidates* it (phase back to `not_built`, `invalidate_seq` bumped, the service's copy replaced at the next SETUP): the service restarted (the launcher's `generation` differs from the one the cache was built on, checked at every use), a log request was refused (unknown row, duplicate ctid with another version), a transaction could not log (service down, request failed) or logged to an older cache (`invalidate_seq` / generation changed since its first request). In the failure cases the invalidation happens *after* the transaction's commit so that a rebuild sees its rows. A rebuild is a full `SnapshotAny` scan sent to the service. **Only an overflow** (more row versions than `max_num_rows`, a data region that does not fit even after compaction, a table larger than `max_num_rows` at the initial load) marks the cache `corrupted` (a WARNING at the statement; queries read the table; `pgstrom.gpucache_recovery()` makes it rebuild). A loader that dies leaves the phase `loading`: waiters check the loader's pid.
- **Fallback to the heap.** A cache that is not ready, is corrupted, was written by a transaction that could not log, or whose plan needs a value the cache cannot load into the VM (a **numeric** read by a qual, projection or aggregate; checked at the start of execution by building the scan program in the backend, `pgstromGpuCacheProgramOk()`; join programs never read numerics) is not used: the same GpuScan reads the table. `EXPLAIN` shows `GPU Cache: GPU0 [phase: ready, max_num_rows: N]` and `GPU Cache Options: ...` only when the cache is used.
- **Not supported (documented, enforced).** `PREPARE TRANSACTION` of a transaction that wrote a cached table is refused (the final status could not be sent); a table with a column of `cstring` or of a fixed type longer than 1024 bytes is refused with an error at the initial load; more than 512 columns; `gpu_device_id` other than 0.

**Tested (M1 Pro, MoltenVK).** `src/gpuserv/gcache_check.c` (`make -C src/gpuserv gcache_check`, no GPU needed): the store against hand-built logs (commit / abort / own-transaction visibility with two ids, UPDATE as delete + insert, resent insert, unknown delete and duplicate ctid drop the cache, slot overflow, region compaction on demand, region growth with the other columns intact, compaction of released rows). `test/gpuserv/gpucache_tests.inc` (sourced by `scan_test.sh` before the `errors` section; `gpucache_dev.sh` runs it alone), GPU against the heap with `pg_strom.enabled = off`, every query's plan must show `GPU Cache:`: two 60,000-row tables of 15 columns (every type above plus numeric, float8, float2, uuid, char(n), varchar), one loaded from the heap by the first scan and one through the log; 22 scan shapes each (quals on every GPU type, NULLs, NaN, text equality / LIKE, date arithmetic, ctid, 10 and 24 computed columns, pass-through of every type, numeric / float8 / uuid quals that read the table), 5 aggregates and GROUP BYs (GpuPreAgg over the cache), 3 joins (GpuJoin with the cache as the outer side, LEFT, join aggregate), parallel workers; the SQL surface and option errors; INSERT / UPDATE / DELETE / key update / NULL and long text; in-transaction visibility of the session's own changes (rollback and commit, savepoint rollback, nested savepoints, released savepoint, insert then delete, double update); `PREPARE TRANSACTION` refused; 1,500 small transactions; four concurrent writers moving money between rows while a reader sums the table 150 times (the sum was never wrong: a transaction becomes visible atomically); another session's uncommitted INSERT / UPDATE / DELETE invisible, visible after COMMIT, unchanged after ROLLBACK; TRUNCATE (alone and with inserts in a transaction), ADD COLUMN, DROP COLUMN, ALTER COLUMN TYPE, VACUUM FULL, DROP TRIGGER and re-create, a write while the trigger is disabled, DROP TABLE; overflow (corrupted, WARNING, queries still correct, recovery); a table larger than `max_num_rows`; kill -9 of the GPU service (the launcher restarts it, the caches rebuild, changes after the restart work); `DELETE ... RETURNING`, `FOR UPDATE`, a partitioned table with one cached partition, a 36-column table; a 200,000-row table through the log with bulk UPDATE / DELETE. **Full `scan_test.sh`: ALL PASSED, 1477 `ok` lines** (about 190 of them in the GPU-Cache section). `test/vulkan_schedule`: 23 tests pass (the 22 before plus `gpu_cache`, through `gpu_cache_9.out`, which differs from the CUDA-era file in plan text and in the phase after `gpucache_recovery()`; see `vulkan_known_failures.txt`).

**Measurements** (200,000 cached rows, 15 columns, warm, `EXPLAIN ANALYZE` execution time, 8-core Mac, other agents were using the machine): `select count(*), sum(b), max(c) ... where a > 0` **3.8 ms** against 16.6-17.2 ms for PostgreSQL's own scan (4.4x); a selective scan `select id, a, f ... where b < -49500` **2.4-2.6 ms** against 13.0 ms (5x). The first GPU query after a restart of the service pays the pipeline creation (about 1.2 s) and the cache rebuild (the initial load sends every tuple through the socket, about 1 s per 200,000 rows). The commit of a transaction that wrote a cached table waits for one round trip (tens of microseconds) plus the CPU time to apply its records.

**Known gaps.** The log is applied by the service's CPU (the CUDA product used kernels), one request at a time by one thread, so a very write-heavy workload serializes on the service; the redo buffer, sync interval and threshold options do nothing; a cache cannot exceed the device's storage buffer range or 4 GB (the plan for a larger one is multiple buffers, not started); the buffer is not preloaded at start-up (`pg_strom.gpucache_auto_preload` of the CUDA product does not exist here: the first use builds it); a cache is lost with the service and rebuilt by the next user, which blocks that query for the load time; numeric columns can only be passed through (a numeric qual / aggregate reads the table); not tested on lavapipe / Linux (the parent does that) nor with PostgreSQL 15, 16, 18, 19 (`gpu_cache_9.out` exists for 17 only); EvalPlanQual rechecks on a cached scan were not exercised; a whole-row reference (`select t from tbl t`) through any GpuScan fails in the planner (found here, not cache related, in `vulkan_known_failures.txt`); the GpuJoin of two 35-column tables is refused by the service with an error instead of staying on the CPU (planner limit, the upstream test avoids it with `enable_gpujoin = off`).

## A6/A9 robustness status (differential fuzzer; planner respects the service's translation limits)

**The fuzzer.** `test/gpuserv/fuzz.py` (Python 3 standard library, `python3 -I`, drives `psql`) + `test/gpuserv/fuzz_test.sh` (throwaway cluster with the settings of `scan_test.sh`, run through `locked_test.sh`: `FUZZ_SEED=1 FUZZ_COUNT=2000 sh test/gpuserv/locked_test.sh "$PWD" fuzz_test.sh`; `FUZZ_TIME`, `FUZZ_ARGS="--only N"` / `--verbose`, `DBG_SQL=<file>` for ad-hoc SQL on its tables). Data: `fz1` (all-visible), `fz2` (updates and deletes), `fz3` (vacuumed mix), 30,000 rows each, with narrow columns (`n2 n4 n8 nf`: small values, so arithmetic seldom overflows) and edge columns (`e2 e4 e8 ef`: min/max, +-1, around 2^15, 2^31, 2^63, NaN/+-Infinity floats, denormals), bool, date/time/timestamp/timestamptz with infinities and BC/far-future values, text/varchar/char(6) (empty, UTF-8, 120-hash strings, 4 KB compressible), numeric(10,2), numeric(18,6) and unconstrained numeric (NaN, +-Infinity, > 64-bit, long fractions), about 7% NULLs per column; `fz_d` (400-row dimension table with duplicate keys, NULLs, int8 extremes, infinite dates) and `fz_w` (60 narrow columns for the translation-limit shapes). Each query is generated from `Random(seed, index)` (so `--only N` reproduces it) as a random expression tree (depth 1-4) over typed operators, casts, comparisons, AND/OR/NOT, IS [NOT] NULL, LIKE of all pattern shapes, BETWEEN/IN/COALESCE and functions the VM does not have (about 22% of queries may use them: gating is fuzzed too), in one of the shapes: scan (quals, projections, DISTINCT), aggregate with and without GROUP BY (FILTER, up to 3 keys), joins (inner, left, right, full, semi, anti, extra ON quals, computed keys, int2/int4/int8/date/timestamp/text keys), aggregate over a join, with and without parallel workers; 15% of the queries are "stress" shapes over `fz_w` (wide projections, 40-column sums, 100 quals, AND/OR chains of 40, many aggregates with filters, deep left/right/balanced trees). Every query runs with the GPU settings of `run` and with `pg_strom.enabled=off`.

**Comparison rule** (header of `fuzz.py`): both succeed -> the sorted result rows must be equal (md5 of the row texts + count; a mismatch is repeated once to rule out nondeterminism); both fail -> fine (equal messages "same error", different "diff error" is only tallied: PostgreSQL evaluates quals in its cost order and rows in physical order, the GPU in its own order, so a query with several kinds of errors may raise either); exactly one fails -> "asym", tallied (a qual order or a short-circuit PostgreSQL has and the device lacks; a failure is reported only for "strict" queries with one top-level condition tree); an error that only the GPU raises and that names the service (translation limits, program too large, ...) is always a failure ("service refused the program"); errors both sides raise from PostgreSQL's parser are generator mistakes ("invalid", about 3-4% of the queries). A failing query is minimized (drop columns/conditions/aggregates, replace subexpressions by children or constants while the verdict stays) and appended to `test/gpuserv/fuzz_corpus.txt`, which the next run replays first.

**What the fuzzer found** (11,560 distinct queries over seeds 1-6, about 48 minutes of fuzzing in 7 chunks, each chunk after the fixes of the previous one; every difference was analysed): 14 real bugs, all fixed, with regression tests in `test/gpuserv/fuzz_regress.inc` and details in `test/vulkan_known_failures.txt` (items 5-14): `char(n) LIKE` stripped trailing blanks (wrong rows); GpuJoin hash keys of different integer widths found no partner (no rows); parallel GpuJoin killed the server on macOS (process-shared `pthread_cond_wait` EINVAL); `sum(3)` (aggregate of a constant) crashed the backend (setrefs had turned the kernel parameter into a custom_scan_tlist reference); IS NULL of an inner column in a join qual failed in the service; float4 comparison and arithmetic with denormals (Metal flushes them; comparison now on bits, arithmetic on denormals goes to the backend's recheck); float4 -> int casts rounded ties away from zero (Metal's `round`); computed projections ran before host quals and aggregate arguments before their FILTER (spurious errors); unary minus of a computed value clobbered its operand. Not bugs, handled in the fuzzer: evaluation order differences (about 1% of the queries: "asymmetric errors"), different error messages of two errors (about 5%), `sum/avg` of float4 (depends on the order rows arrive in), numeric GROUP BY keys with mixed scales (0 vs 0.00 prints whichever row came first), DISTINCT of floats/numerics. The last two chunks (seeds 5 and 6, 6,500 queries) had no failing query besides the float4 sum that is now excluded from the generator.

**Translation limits** (`src/gpuserv/scan_caps.h` holds the constants, shared by the planner and the service). A program the service cannot translate fails the query, and there is no CPU fallback for a refused program, so the planner now keeps what may not fit on the CPU, with conservative estimates that follow `scan_prog.c`'s register allocation: per expression (`pgstrom_vulkan_expr_limits()` in `codegen.c`, applied by `pgstrom_xpu_expression()` for every qual, projection, key and aggregate argument): temporary registers (`SCAN_VM_TEMP_BUDGET` 6) and nodes (`SCAN_VM_EXPR_NODES` 120); per GpuScan (`gpu_scan.c`): referenced columns + computed values <= `SCAN_VM_SLOT_BUDGET` (23) or no device quals / computed projection, more than `SCAN_VM_BOOL_ARGS` (60) quals in one AND move to the host; per GpuJoin (`gpu_join.c`) and GpuPreAgg (`gpu_preagg.c`): kernel variables + one more register per computed value + temporaries <= 32 registers, `SCAN_AGG_MAX` (12) output columns; GpuJoin refuses more than 60 join quals. The aggregate arguments of an aggregate with FILTER must be unable to fail (`pgstrom_vulkan_expr_cannot_fail()`), because the device evaluates them for every row. Verified by the fuzzer's stress shapes over a 60-column table (44 computed columns, 40-term sums, 100 quals, 14 aggregates with filters over 30 columns, GROUP BY with 4 keys, joins) and by `fuzz_regress.inc`. **Not done:** the CPU fallback for a refused program (a scan task could be answered with all its tuples as `KDS_FORMAT_RECHECK` items, but joins have no recheck path and the backend does not hold the pages the service reads from the relation file; a general mechanism is a design change, not a small one), a check of the sum of all expression sizes in one GpuJoin program (16384 words), and a recheck path in join programs (a float4 denormal there fails the query).

**How to run it:** `FUZZ_SEED=7 FUZZ_COUNT=3000 sh test/gpuserv/locked_test.sh "$PWD" fuzz_test.sh` (about 12 minutes; the cluster setup is about 30 seconds). A failing query is printed with its minimized form and appended to `test/gpuserv/fuzz_corpus.txt` (replayed by every run: delete entries that were nondeterministic, keep real reproducers as regressions). The 24-hour run of the A6 gate is a loop over seeds of this command.

## A10 status (part 1: software binary64 library and its check; part 2: float8 in the VM for quals, projections, joins, Arrow and GPU-Cache; part 3: float8 aggregates without GROUP BY; float8 aggregates with GROUP BY, keys and math functions are not done)

**Why.** `float8` was pass-through only (the plan said Apple has no fp64 and emulation "is not IEEE-exact", correction 5). That blocked `float8` quals and aggregates in general (SSB and TPC-H style data) and every geometry function. The ArrowMetal write-up showed that integer emulation of binary64 is exact and cheap for the operations a database needs; this part reproduces and checks the idea here before any VM work.

**What exists.**
- `src/gpuserv/kernels_vm/f64_soft.inc`: doubles are `uint64_t` bit patterns (they fit the VM's `Reg.v`). `f64_add f64_sub f64_mul f64_div f64_sqrt`; `f64_key` (order-preserving integer key with PostgreSQL's float8 order: NaN equals NaN and is the largest, -0 equals +0) and `f64_eq/ne/lt/le/gt/ge` (PostgreSQL's `float8_eq` ... `float8_ge`) built on it; `f64_rint`, `f64_fits_i64`, `f64_to_i64_rint` (the float8 to int8 cast: rint, then the range check), `f64_from_i64`; `f64_from_f32` and `f64_to_f32(mode)` with nearest-even and the two directed roundings (PostGIS rounds bounding boxes outward). Round to nearest, ties to even; subnormals, signed zeros, infinities and overflow follow IEEE; a NaN result is the canonical quiet NaN. No float instruction is used, so fast-math, flush-to-zero and FMA contraction of the compiler cannot change a result. Division is a 63-iteration restoring division and square root a digit-by-digit loop with a 128-bit remainder: simple and fixed-length, the first candidates to replace by a Newton iteration if they matter.
- The source is the common subset of C and Slang (`F64SOFT_C` selects the C side), so one text is both checked on the host and compiled into kernels. Shift counts are always below the operand width.
- `src/gpuserv/f64soft_check.c` (`sh test/gpuserv/f64soft_check.sh [N [device|-1]]`; `make -C src/gpuserv f64soft_check build/f64soft_check.spv`): part 1 runs the library as C against the hardware double on N operand pairs per operation, part 2 runs the Slang build (`kernels_check/f64soft_check.slang`) on the device. Operand categories: uniform bit patterns, close exponents, sparse mantissas (exact results and ties), subnormals, specials, products and quotients around the subnormal boundary and around overflow, powers of two and neighbours, ranges where a double becomes a float4 subnormal or overflows, small integers and halves, 2^52 to 2^64. The comparison functions are checked against PostgreSQL's own formulas; the int64 cast against `rint()` with the range check.

**Result (this Mac, Apple GPU through MoltenVK, `fp64=0`).** Every operation matched the hardware double bit for bit on 16,000,000 cases per operation, on the host and on the device. A mutation check shows the test has teeth: 12 deliberate bugs, each checked at 200,000 cases (no tie-to-even, a dropped sticky bit in mul, div, add alignment and the subnormal path, a wrong shift, sqrt with an odd exponent, -0 not folded, rint ties, float4 directed modes, float4 subnormals) were planted in a copy; 11 were reported and one was an equivalent mutant (an optimization clamp whose removal cannot change a result).

**Cost (one run, kernel time of a 16M-pair dispatch including loading two operands and storing the result, so mostly memory traffic; not a benchmark).** add, sub and mul about 1.8 to 2.2 Gop/s (the first dispatch of the run also pays pipeline warm-up), div about 0.65 Gop/s, sqrt about 0.34 Gop/s, conversions and rint 2 to 5 Gop/s. The VM's own interpretation overhead (see A3) is larger than the arithmetic for simple expressions.

**Part 2: float8 in the VM (done for scan, join, Arrow and GPU-Cache; not for aggregates with GROUP BY or keys; the math functions sqrt, round, ceil, ceiling, floor, trunc, sign are done, see below).**
- Math functions (`SOP_DUNARY` kinds `DUN_SQRT`..`DUN_SIGN`, `f64_math()` in `f64_soft.inc`): `round` is rint (ties to even, as PostgreSQL's float8 `round`), `ceil`/`floor`/`trunc` keep -0, `sign` returns 0 for 0 and NaN. A negative `sqrt` (including -Infinity, not -0 or NaN) returns `SOP_ERR_SQRTNEG`, reported with PostgreSQL's message. Checked bit for bit against the hardware on host and device (`f64soft_check`, ops 24-30); tests in `float8_tests.inc`, `arrow_tests.inc`, `gpucache_tests.inc`; fuzzer `g_f4` uses them on widened float4. Semantics probe: `test/gpuserv/float8_math_probe.sql`.
- `kernels_vm/scan_vm_ops.inc`: value type `SOP_VT_FLOAT8` (a register is the 64 bits of the double) and the opcodes `CMPD`, `DARITH`, `DUNARY` (negate, abs), `I2D`, `D2I`, `F2D`, `D2F` (120-126), implemented in `vm_f8()` of `scan_common.slang` on `f64_soft.inc` and mirrored with host doubles in `cpu_vm.c`. The mixed forms `float48xx` and `float84xx` widen the float4 side with `F2D` first (the same temporary register the date/timestamp comparison uses); the planner's register estimate already reserves it.
- `scan_caps.c` `classify_float8()` opens `float8eq ... float8ge`, `float8pl/mi/mul/div`, `float8um/up/abs`, the mixed forms, `float8_to_int2/4/8`, `float8_to_float4`, `intN_to_float8`, `float4_to_float8`. `scan_prog.c` translates them; `specialize.c` lists the new opcodes (the specialized kernel calls the same `vm_step`). Heap columns needed no loader change (an 8-byte fixed attribute is read as raw bits); `arrow_exec.c` accepts an Arrow double, and `GCVT_FLOAT8` carries float8 from `gpu_cache.c` to `gcache.c`.
- Semantics checked against PostgreSQL's `float.c` (15 - 19): the errors are overflow (an infinite result from finite operands), underflow (`*` and `/` giving 0 from non-zero operands; not for `+`/`-`), division by zero **except for a NaN dividend** (`NaN / 0` is NaN), and for `float8 -> float4` and `-> intN` the overflow, underflow and range errors. No recheck path is needed (unlike float4, whose hardware arithmetic flushes denormals on Metal). The test caught `NaN / 0` and showed the float4 path had the same flaw; both are fixed.
- Join keys of float8 stay on the CPU (`float8` has no hash flag, and the hash of -0 and NaN would differ). `emit_hash_value()` also refuses it.
- Tests: `test/gpuserv/float8_tests.inc` (91 differential checks over heap tables with NULLs, NaN, +-Infinity, -0, subnormals, the largest and smallest normals, rounding ties, 2^63; 11 queries that must raise the same error on both paths; GpuJoin with float8 on both sides) and `float8_dev.sh` to run it alone; float8 columns in the Arrow `types` file (`arrow_gen_ext.cpp`) and float8 quals in `gpucache_tests.inc`. The service runs in `PGSTROM_GPUSERV_SPECIALIZE=check`, so every dispatch also runs the specialized kernel and compares it with the VM.

**Part 3: float8 aggregates without GROUP BY (done for scan, join, Arrow and GPU-Cache sources).**
- Classes 6 (sum, avg), 7 (min), 8 (max) of the aggregate table (`PSUM_FP`/`PAVG_FP`, `PMIN_FP64`, `PMAX_FP64`): `fagg_acc()` and `fagg_merge()` in `scan_common.slang` do the per-thread accumulation and the tree reduction of `agg.slang` / `jagg.slang` / `join_walk.inc` (min and max through `f64_key`, so NaN is the largest as in PostgreSQL; a sum with `f64_add`). A partial is `{ n, bits }` in the existing 6-word record; the service merges the records of the workgroups in order with the same library (`agg_merge_workgroups`) and writes `kagg_state__psum_fp_packed` / `kagg_state__pminmax_fp64_packed` for PostgreSQL's Agg to finalize. The specializer's `spec_acc` returns the first error.
- A sum of finite values that overflows raises PostgreSQL's "value out of range: overflow" (kernel and service merge). The order of additions is fixed (thread, workgroup tree, service), so the result is deterministic, but it is not the order of a serial scan: **a sum or average of inexact values can differ from PostgreSQL's in the last bits** (as it can between PostgreSQL's own parallel workers). The tests use data whose sums are exact in any order, or round.
- Planner (`gpu_preagg.c`): these actions are offered only without GROUP BY (`scan_vm_agg_action_nogroup`; the GROUP BY kernels combine states with integer atomics, which a soft-float sum cannot use; `scan_prog.c` also refuses them with keys); `sum(float4)` is not offered (the CPU adds in float4, the device would add in float8: another result) nor anything on `float2`. `min`/`max`/`avg(float4)` are offered (the argument is widened to float8 exactly; PostgreSQL's `avg(float4)` also accumulates in float8).
- Tests: float8 aggregates over heap tables (exact values, NaN and Infinity, FILTER, NULL results, computed arguments, overflow error, the CPU-only cases), join aggregates, Arrow doubles and the GPU-Cache; the old Arrow test that expected `sum(d::float8)` to stay on the CPU now expects the GPU, and `sum(float4)` takes its place.

**Not done.**
0. float8 aggregates with GROUP BY (a per-group table needs a soft-float combine in shared memory: a lock per slot, a per-thread table merged on the service, or two-phase min/max on 32-bit halves), float8 group, sort and join keys, and the other math functions (`exp`, `ln`, `pow`, trigonometry; `sqrt`, `round`, `ceil`, `floor`, `trunc`, `sign` are done). The items below are the earlier list.
1. (done, see part 2) A `float8` type and its opcodes in the VM (`scan_vm_ops.inc`, `scan_caps.[ch]`, `scan_prog.c`), planner gating in `codegen.c`, the opcode list of `specialize.c`, loading `float8` columns (heap, Arrow, GPU-Cache).
2. `float8` comparison, `min`/`max`, GROUP BY keys and GPU-Sort keys through `f64_key` (these also remove the float NaN-key exception of GPU-Sort). `min`/`max(int8)` in GROUP BY could use the ArrowMetal two-pass 32-bit-halves design (Metal accepts only 64-bit atomic min and max, the base tier has none).
3. Arithmetic opcodes and error semantics: PostgreSQL raises `value out of range: overflow` / `underflow` and `division by zero` for float8; the kernel has to report them as it does for the integer operators.
4. Aggregates: `sum`/`avg(float8)` add in a different order than a serial CPU sum (each operation is exact, the totals can differ in the last bits, as for parallel PostgreSQL itself); the differential tests need a stated tolerance, as the fuzzer already has for floats.
5. Risk not covered by the checks: the CPU reference may not be plain per-operation IEEE. Clang on arm64 contracts `a*b + c` inside an expression into a fused multiply-add by default; if PostgreSQL's float8 code or PostGIS was built that way, the CPU result differs from separate multiply and add by up to an ulp. The build flags of the installed binaries were not checked. A software FMA (Berkeley SoftFloat's `mulAdd` is the reference) would be needed to match it.
6. Transcendental functions (`exp`, `ln`, `pow`, `sin`) are not planned: the platform libm differs from fdlibm by an ulp, so they cannot be bit-exact against the CPU, and ArrowMetal measured them 6 to 10 times slower than a multicore CPU.

**PostGIS, revised.** With exact binary64 the earlier "needs fp64" split changes: planar `st_distance`, `st_dwithin`, the point-in-polygon tests, `st_expand` and the `&&` family can run exactly (the float32 margin and CPU recheck scheme is no longer the main route), still limited by what the plan already says: only quals against a constant geometry (the hash-only GpuJoin cannot run `st_contains(geom, point)` between two tables), table-side polygons are usually toasted and take the per-row CPU path, a large constant geometry may exceed the program size, and the `postgis` extension must be installed for the test. Order of work: `float8` in the VM first (it is useful alone), then `geometry` as a varlena type, the header predicates and `st_makepoint`, then the bounding-box operators, then the constant-geometry predicates.

## A11 status (PostGIS: part 1, the 2D bounding-box operators `&&`, `~`, `@`; part 2, point in polygon; heap tables only)

**Design decision (the FMA experiment, `test/gpuserv/postgis/fma_probe.sh`).** The installed PostGIS 3.7 evaluates its orientation test with fused multiply-add, and two call sites of the same library fuse differently (the standalone `lw_segment_side` fuses one product, the copy inlined into `ptarray_contains_point_partial` the other; `ST_Contains` matched the second on 2,000,000 near-edge points, plain IEEE evaluation disagrees on 3.1% of them). Bit-exact emulation of "the CPU's double" is therefore not a goal: the geometry predicates will compute with the soft binary64 and an error bound (Shewchuk's filter, `|det| >= 4 * (3 + 16 eps) eps (|a| + |b|)`), decide when the sign is certain and hand the row to the CPU recheck otherwise. Among the points the filter calls certain there were 0 mismatches against PostGIS under all three models; on 60 million random points none was doubtful.

**What runs on the GPU.** `geometry` is registered like `cube` (`xpu_postgis.h`; type opcode with the extension name "postgis", a hash function in `codegen.c`) and read as a string register over the GSERIALIZED payload, so the heap loader, constants and the recheck of compressed or external values are the strings'. The opcode `GEOMBOX` (`scan_common.slang` `vm_geom()`, mirrored in `cpu_vm.c`) implements `geometry_overlaps` (`&&`), `geometry_contains` (`~`) and `geometry_within` (`@`) between two geometries (columns or constants) on the 2D float boxes (`gserialized_overlaps_2d`, `gserialized_contains_2d`): the cached box of GSERIALIZED v1 or v2 (extended flags skipped, Z/M boxes use the first four floats), or for a point without one the box of its coordinates rounded outward to float4 (`f64_to_f32` modes 1 and 2, the `next_float_down/up` of PostGIS). Everything the VM cannot box returns `SCANVM_RECHECK_CODE` and the backend decides: geodetic values, a small line or polygon PostGIS keeps no box for, NaN coordinates, malformed data.

**PostGIS behaviours found by the tests (not in upstream PG-Strom's code):** the float boxes are clamped to +-FLT_MAX, never infinity (checked on the stored bytes: a polygon with x up to 1e39 caches `0x7f7fffff`); an *empty* operand decides: `&&` is false, `~` and `@` are **true**.

**Planner.** `scan_caps.c` `classify_geometry()` opens only those three function names; join programs refuse them (`vulkan_text_func_allowed`), since a join program loads no string registers. The other registered names (`st_makepoint`, `st_contains`, `st_dwithin`, `st_distance`, `st_srid`, ...) stay on the CPU.

**Tests.** `test/gpuserv/postgis_tests.inc` (skipped when the extension is missing; sourced by `scan_test.sh`) and `postgis_dev.sh`: 16 queries over two tables of 100,000 rows of every shape (points, 3D and M points, lines and polygons with a cached box, 2-vertex lines and triangles without, empties, multipoints, collections, NULLs, tiny, huge and infinite coordinates), each compared with the CPU's PostGIS.

**Not done.** `ST_Distance` (part 3 explains why it stays on the CPU), `ST_DWithin` of a point and a line or polygon, `ST_Expand`, `ST_SRID`, `box2df`; Arrow and GPU-Cache sources for geometry columns (the cache type mapping and the Arrow Binary mapping are missing, untested); the spatial join (the GpuJoin is hash-only: it needs a nested-loop join or a GiST traversal), so the `postgis` regression test stays in `pending_schedule`. Performance: PostGIS caches an R-tree of the segments of a constant polygon, the device would test every segment per row, so large polygons may need an acceleration structure in the constant pool.

**Part 3: `ST_DWithin` of two points (`GEOMDWITHIN`).** Semantics read off PostGIS 3.7 (`test/gpuserv/postgis/dwithin_probe.{sql,out}`): only X and Y count (Z and M are ignored); an empty point is false (`ST_Distance` is NULL); any SRID difference raises "mixed SRID", also against an empty point; a negative tolerance raises "Tolerance cannot be less than zero" (`-0` is accepted, NaN gives false, Infinity true, NULL gives NULL); a distance that overflows or involves a non-finite coordinate gives false; the test is `distance <= r` on PostGIS's own distance. **That distance is not plain binary64:** against `sqrt(dx*dx + dy*dy)` computed with separate operations it is 1 ulp below for 12,111 and 1 ulp above for 12,193 of 300,000 random pairs (8.1%, maximum relative difference 2.2e-16), so a squared comparison disagrees with PostGIS on 26% of the pairs that sit on the boundary. The instruction therefore decides only when `dx*dx + dy*dy` is beyond `r*r` by a relative 2^-47 (about 4 times the observed error band), and hands the rest back: the boundary, a SRID mismatch, a negative, NaN or infinite tolerance, non-finite or overflowing values, an underflow (below 2^-900), a multipoint, line or geodetic operand. `ST_Distance` in a projection has no tolerance band to hide in, so it stays on the CPU (`ST_DWithin` of a point and a line or polygon too: PostGIS goes through its segment distance code). Operands: a point column, constant or parameter (a string register) or the fused `ST_MakePoint(x, y)` under an optional `ST_SetSRID` of a constant; two fused points must carry the same SRID (the planner refuses otherwise: the instruction has room for one); the tolerance is any `float8` expression. Join programs refuse it (they load no string registers); Arrow and GPU-Cache scans take it since A12. Measured: 0 of 100,000 random pairs rechecked, 720 of 100,800 on the boundary grid. **A deep tolerance expression is refused by the planner** (`sqrt(x*x + y*y) * (1 + k*eps)` exceeds the 6 temporary registers and the qual stays on the CPU with the right answer), so the boundary tests store the tolerance in a column. Tests: `postgis_tests.inc` (about 60 checks: every shape, both argument orders, SRIDs, tolerance 0, Infinity, NaN, NULL, negative, the grid at distance exactly r, tolerance 0 to 3 ulp either side of the plain distance, the recheck counters).

**Spatial join: what the branch already has (read before designing).** The backend planner cannot create a GiST join path: `pgstromTryFindGistIndex()` and the clause matching live in master's `src/gist.c` (639 lines), which is not in this branch and which nothing calls. What is left is plumbing: `gist_clause` in `pp_inner` (copied and serialized in `misc.c`), `__codegen_build_one_gistquals()` and the `GiSTEval` expression in `codegen.c`, the clause's expression state in `executor.c`, and `kern_multirels.chunks[].gist_offset`. The service has nothing: `scan_exec.c` refuses a join whose chunk has `gist_offset != 0`, and no kernel walks index pages. A join program also loads no string registers, so a geometry column from either side of a join cannot be read by any instruction today (`vulkan_text_func_allowed()` refuses the geometry functions in joins). The two ways to a spatial join: **(a) GiST traversal** (port `gist.c`, reconnect `gpu_join.c`, ship the index pages in the inner buffer, write a page-walking kernel with the opclass consistent function in the VM): scales to large inner tables, the largest piece of work, and depends on the PostgreSQL index page format per major version; **(b) nested loop over a small inner table**: a hash join with a constant key and the geometry predicate as the extra join qual (the extra join qual machinery exists), a box test as the first filter; cost O(outer x inner), fine for tens of thousands of inner polygons, and it needs only string registers in join programs (the inner geometry) and a way to say "no hash key". Either needs strings in join programs. **Decided (2026-11-04): option (a), GiST traversal**; see the A13 status below.

**Part 2: point in polygon (`GEOMPIP`).** `ST_Contains` / `ST_Covers` / `ST_Intersects` / `ST_Within` / `ST_CoveredBy` of a (multi)polygon and a point. Semantics were read off the installed PostGIS 3.7 (`test/gpuserv/postgis/semantics_probe.{sql,out}`): a non-zero winding number over the rings (a self-overlapping ring or a bowtie is "inside" where the winding is not zero; orientation does not matter), a hole excludes, a point on a hole's rim is a boundary; the three predicates differ only on the boundary (`ST_Contains` false, the others true); an empty operand is false; a different SRID raises "mixed SRID" (and `ST_Covers` with an empty point does not), so any SRID mismatch is a recheck; a multipoint, line or collection goes through GEOS, so only a single POINT is handled. **A multipolygon is order-dependent:** the first component the point is not outside of decides (inside, or boundary), so a point inside part 1 and on the edge of part 2 is contained, the reverse order is not; found by the differential test, the kernel exits at the first non-outside component.

The kernel never decides a boundary: an edge's side of the point is taken only when its sign is beyond Shewchuk's error bound with a safety factor (`2^-49 * (|l| + |r|)`; PostGIS fuses the product in some call sites, so the model is "filter and recheck", see the FMA experiment), and the terms must be finite and neither subnormal nor close to overflow. A point exactly on a horizontal edge's line inside its x range, on a vertex, within the bound, or with non-finite coordinates is rechecked. A cached float box (rounded outward) rejects far points without touching an edge. Measured on 100,000 pseudo-random points against a square, a polygon with two holes, a three-part multipolygon and a 32-gon: 0 to 25 rows rechecked (`EXPLAIN ANALYZE` "Fallback-stats: depth[0]"), against 4,800 of 100,800 on an integer grid full of edges and vertices (the test's positive control). `st_makepoint(x, y)` / `st_point(x, y)`, optionally under `st_setsrid(., constant)`, is fused into the instruction (x and y as float8 registers, the SRID in `k1`); `codegen.c` checks the shapes (`vulkan_geom_pip_args_ok`) because a program the builder refuses has no CPU fallback.

**Arrow and GPU-Cache sources (A12, done).** They used to refuse the geometry predicates (no recheck path: `gpuScanGeometryQualOk()` and `vulkan_geom_source_ok()` kept them on the CPU); since A12 the recheck rows of an Arrow, Parquet or cached scan go to the backend like those of a heap scan, and both gates ask `pgstrom_source_can_recheck()`. See the A12 status section.

**Planner limits found.** The register estimator (`SCAN_VM_TEMP_BUDGET`) counts the fused `st_makepoint` as a nested call, so a point built from a deep expression (about 14 nodes) stays on the CPU; that is the estimator's conservative rule, not a correctness limit.

**Tests.** `postgis_tests.inc` (the PostGIS dev suite) grew from 32 to 188 checks: seven polygon shapes (square, two holes, multipolygon, 32-gon, bowtie, doubled loop, clockwise) times six predicates and argument orders, NULL / infinite / NaN coordinates, columns of every shape, mixed-SRID errors that must match the CPU's text, an integer grid, points 0 to 6 ulps off a diagonal edge, huge, tiny and sliver polygons, both orders of a multipolygon, counts and a GROUP BY over the predicate, the recheck fraction with its positive control, and a GPU-Cache table.

## A12 status (recheck path for Arrow_Fdw, Parquet and GPU-Cache scans: done, scan / aggregation / join / join aggregation on all three sources)

**The problem.** An instruction the VM cannot decide for one row returns `SCANVM_RECHECK_CODE`. On a heap scan the service turns that into a row for the backend (`rck_add`: a `kern_recheckitem` in a `KDS_FORMAT_RECHECK` chunk) and the backend evaluates quals, joins and projection of that tuple on the CPU (`execCpuRecheckOneChunk` -> `execCpuFallbackBaseTuple`). Until A12 the Arrow, Parquet and GPU-Cache paths (`arrow_exec.c`, `gcache.c`) died with "a compressed or external string reached the CPU re-evaluation", so the planner kept every recheck-capable instruction (the geometry predicates) off those sources.

**What a row is on each source (as built).**
- *Arrow / Parquet:* an item of kind `RECHECK_KIND_ARROW` (16 bytes, no tuple): `blkno` = `rb_flat` (index into `ArrowFdwState.rb_states[]`, copied from `kern_exec_task.arrow_rb_flat`), `offnum` = `scan_relidx`, `arrow_row` = row in the batch / row group. The backend decodes the batch again (`pgstromArrowFdwRecheckTuple`, the last batch kept per scan state, its own buffer) and builds the heap tuple of the referenced columns.
- *GPU-Cache:* an item of kind heap: `gcache_form_tuple()` builds a heap tuple from the cache slot (every cached column, frozen xmin, the slot's ctid). The cache is **not a snapshot** (latest committed state plus the session's own changes, `gcache_visibility`), so the backend must not fetch the version by ctid, and it does not: the heap-kind branch of `execCpuRecheckOneChunk` uses only the tuple bytes. The rows the kernel handed back were visible to the session by the bitmap, and a row the cache has no column for is NULL.

**Kernels.** `arrow_eval_row` and the generated `spec_arrow_eval_row` set `g_recheck` and return false on `SOP_RECHECK_CODE` (`g_recheck` is now reset before the GPU-Cache row filter, not after: a skipped row kept the previous row's value). Each mode reports it deterministically, one word per row of the pass, written only by the row's own thread (so `PGSTROM_GPUSERV_SPECIALIZE=check` compares them):
- `arrow.slang` (scan): the row flag word is 2.
- `agg.slang` (no GROUP BY): a flag word per row after the per-workgroup records (`FLAG_AT`; **fixed an out-of-bounds write**: under `ARROW_SRC` the scale-mismatch flag was written at `ptab[2 * page + 1] + lp`, where `ptab` is the column table, and `kparam.total_lps` was 0, so it landed in the workgroup records).
- `gagg.slang`, `gagg_dm.slang` (GROUP BY): the flag words follow the overflow list (`flags_base + 1 + extra * OV_REC`). The recheck rows used to vanish there (a scale mismatch was neither aggregated nor reported).
- `join_walk.inc` (join, mode 0): **the hole is closed.** An outer row whose scan quals could not be decided (`eval_row` / `arrow_eval_row` set `g_recheck`, the row came back `hit = false`) was silently dropped from an inner join and, worse, not null-extended in a LEFT join. It now sets `pz` and appends a poison record (the item word of depth 1 = 0xfffffffe, the record the GiST join already used for an inner poison); the same for an instruction that rechecks in the join projection. The loop runs `WaveActiveAnyTrue(d != 0 || pz)` so a lane that is done before it starts still appends its record. This holds for heap and Arrow outers and for the specialized join kernels (the poison code is no longer `!SPEC_PROG`).
- jagg / jgagg over a GiST join with an Arrow outer: the same scout pass and skip bitmap as for heap (`arrow_join_scout`): the VM join kernel runs with `kparam.extra = 1` (poison records only), the poisoned rows of the pass set bits in a bitmap behind the column table (`ptab[8 * ncols + 4 + (row >> 5)]`, the pass-relative row) and become Arrow items; the aggregating pass skips them. Poison dedupe keys on the batch row.

**Service.** `rck_add`, `rck_add_arrow`, `rck_chunk_size`, `rck_chunk_fill` are exported by `scan_exec.h`. `arrow_rck_row()` makes the item (Arrow item, or the synthesized heap tuple for a cache task) and `arrow_append_recheck()` appends the RECHECK chunk to the reply (`chunks_nitems++`; an empty ROW chunk leaves `chunks_offset` at the new chunk). The aggregation tasks put the items in `st->rck`, which the final reply sends as before. `spec_verify.c` compares the flag words of the Arrow GROUP BY kernels.

**Planner.** `gpuScanGeometryQualOk()` and `vulkan_geom_source_ok()` no longer refuse Arrow and GPU-Cache; both ask `pgstrom_source_can_recheck(root, rel)` (codegen.c), the one place where a source that cannot hand a row back would be refused. A GiST geometry join accepts an Arrow / Parquet / GPU-Cache outer relation.

**GPU-Cache columns.** The cache stores every column type but the kernels read only some of them; `geometry` is now one of them (`__gpuCacheColumnVt`: `GCVT_STR`, a string register like a heap geometry column), so `ST_Intersects(g, const)` on a cached geometry column runs on the GPU (the `pg_gc` / `pg_3dc` tests of `postgis_tests.inc`, which used to stay on the CPU, now require a `GPU Cache:` plan). A numeric, jsonb or other passed-through cached column that an expression reads still raises "the expression reads a value that the GPU cannot load from a GPU-Cache".

**Backend fix.** `pgstromArrowFdwExecEnd` drops the recheck slot (a "resource was not closed: TupleDesc" warning after every EXPLAIN ANALYZE with a recheck).

**Tests.** `test/gpuserv/recheck_tests.inc` / `recheck_dev.sh` (`arrow_points.cpp` writes the grid as Arrow IPC / Parquet): scan (ST_Contains / Covers / Intersects against a square, a polygon with holes and a multipolygon), the first, last and only row of a batch and a one-row Parquet file, aggregation without and with GROUP BY (one and two keys, FILTER), Z / M / ZM points, parallel workers (with and without the leader), GiST joins with an Arrow and a Parquet outer relation (inner, LEFT, semi, anti, RIGHT, counts above the join, outer and inner quals) and aggregation over them, a cached table (scan, aggregate, GROUP BY, parallel, join, join aggregation), in-transaction changes of a cached table (insert / update / delete at the grid's vertices, commit and rollback, savepoint), and `Fallback-stats` non-zero for each source.

**Cost of the tests (2026-11-06, M1, `PGSTROM_GPUSERV_SPECIALIZE=check`).** The `recheck` unit of `scan_test.sh` takes about 620 s: 540 s of it are the two join-aggregation checks (`rk_j: GROUP BY an inner key`, `rk_gc: ungrouped aggregate over the join`), which compile a new specialized kernel and have the driver compile it; the 60 other checks take under 90 s (Arrow / Parquet scans and aggregation 16 s + 7 s, the other joins about 25 s). The whole scan stage ran 3279 s against 3386 s for the previous tree (the run varies by 2400-3500 s with the driver's shader cache); `recheck_dev.sh` alone takes 350-730 s. The first version of the unit (37 join checks, big outer files) took 1180 s and was cut to the checks that reach a distinct kernel.

- **Closed (A14, 2026-11-06):** the wrong-answer gap in the aggregating join kernels (see "A14" below).

## A13 status (spatial join through a GiST index: slice 1 done; facts read from master and this branch)

**Decision.** Option (a), the GiST traversal, over the nested loop and the grid (the user's choice, 2026-11-04). The grid was estimated to come within about 2x of the GiST walk for point-in-polygon joins, since the point-in-polygon refinement dominates both; that estimate is not measured.

**What master does (read, `git show master:src/...`).**
- *Planner* (`gist.c`, `gpu_join.c`): when `pg_strom.enable_gpugistindex` is on and the join has no hash keys, `pgstromTryFindGistIndex()` looks for a GiST index on the inner relation with a join clause that `match_opclause_to_indexcol` / `match_funcclause_to_indexcol` (the latter through the function's support function, as `ST_Contains` needs) turn into an index clause, and `fixup_gist_clause_for_device` accepts it if `__lookup_gist_device_function` has a device function for the (operator, left type, right type, index key type). It appends `ctid` to the inner target list (`gist_ctid_resno`) and stores the clause in `pp_inner->gist_clause`. **`pp_inner->join_quals` is kept whole**: the original clause (`&&`, or `ST_Contains`) still runs as the post-qual in `ExecGiSTIndexPostQuals`; the index clause only chooses candidates. So a faithful port needs the inner geometry readable in the join program (string registers in joins). An exact non-lossy clause such as `&&` (the index leaf key is the geometry's float box, the operator compares the same float boxes) could be dropped from the post-quals as a tracer-bullet shortcut; that deviation needs a test that the index answer equals the sequential one.
- *Preload* (surviving here in `gpu_join.c` lines ~2018-2080, `innerPreloadSetupGiSTIndex`): the inner tuples go into a hash-format store keyed by `hash_any(ctid)`, the index pages are copied verbatim into a block-format store (`gist_offset`), and a host pass writes the parent block and offset of every page into `pd_lsn` (the walker climbs back up by it, no stack).
- *Leaf TIDs* (`gpujoin_prep_gistindex` in `cuda_gpujoin.cu`, not here): after the inner store is built, every leaf entry's heap TID is looked up in the hash store by `hash_any(ctid)`; on a match the TID is rewritten to the inner **row id** (`bi_hi:bi_lo`, `ip_posid = InvalidOffsetNumber`), otherwise the line pointer is marked `LP_DEAD`. So an index entry whose heap tuple is not in the inner buffer (not visible to the snapshot, removed by an inner qual, dead) is skipped by the walker (`ItemIdIsNormal`); NULL and empty geometries are not in the index (an empty one is, with an empty key: check). This can be a host pass in the service or the backend instead of a kernel.
- *Walker* (`ExecGiSTIndexGetNext`, `xpu_common.cu` ~2030): resumable by a line-pointer offset (`l_state`, 0 = start at the root); for each line pointer it extracts the index key, evaluates the `GiSTEval` expression (the opclass consistent function as device code) on key and outer value, descends into a child page (block number from the TID) or, on a leaf, loads the inner tuple by row id and returns the next line-pointer offset; at the end of a page it follows the right-link or pops to the parent through the `pd_lsn` metadata. `ExecGiSTIndexPostQuals` then loads the inner variables and runs the join quals.

**What this branch has.** The preload and the `gist_clause` plumbing (serialization in `misc.c`, `codegen_build_packed_gistevals` / `__codegen_build_one_gistquals` in `codegen.c`, the expression state in `executor.c`, `kern_multirels.chunks[].gist_offset`, `pgstrom_enable_gpugistindex` default off); the structures in `xpu_common.h` (`GISTPageOpaqueData`, `GistPageIsLeaf` ...). **Missing:** the planner entry (`gist.c` is not here and `gpu_join.c` says "hash join only: no GpuNestLoop, and no GiST-index join"), so no GiST join path is ever created; everything in the service: no handling of `gist_offset` (`scan_exec.c` refuses it), no walker, no leaf-TID pass, no consistent functions, and no string registers in join programs.

**Slices.**
1. *Tracer bullet:* `inner.geom && ST_MakePoint(outer.x, outer.y)` with a GiST index on the inner geometry. Fused outer floats need no outer strings, and `&&` is a plain operator clause (no support function). It exercises the `gist.c` port, the path creation, the preload and leaf-TID pass, the page walker, row-id lookup in the inner store and pass-through output. The post-qual is either the dropped exact clause (with the equality test above) or the first use of inner geometry string registers in a join.
2. `ST_Contains` / `ST_Intersects` / `ST_Within` through the support function, point-in-polygon as the post-qual: needs inner geometry string registers in join programs.
3. `ST_DWithin`: the index condition is the point expanded by the tolerance.

**Walker design constraints.** A native whitelist, not a general `GiSTEval` in the VM: `gist_geometry_ops_2d` and the strategies supported (`&&`, `~`, `@`, the support-function-derived ones), each with its own leaf and internal-page test (for `~` an internal key must contain the query box, for `@` it need only overlap it); the planner refuses every other opclass or strategy, because a refused program has no CPU fallback. The resume state is a line-pointer offset so the walker fits the multi-match loop of `join_walk.inc` like a hash-chain next pointer. The walk is bounded (a step limit, and the page id and block number checked on every hop: a runaway walk would hang the service). `pg_strom.enable_gpugistindex` stays off by default until A13 is verified; the tests turn it on.

**Tests.** An inner table large enough for several index levels (internal pages and right-links), deleted and updated inner rows (dead index entries), an inner qual, NULL and empty geometries, each query compared with `pg_strom.enabled=off`; the plan must show a GpuJoin using the GiST index.


**Slice 1 as built (2026-11-04).** `src/gist.c` matches `geom && st_makepoint(x, y)` (either operand order) against a `gist_geometry_ops_2d` index of a plain base relation and reads the inner rows with PostgreSQL's own sequential scan plus ctid; `gpu_join.c` takes the clause out of the device join quals and ships x, y as the depth's "hash keys". `innerPreloadFixupGiSTLeaves()` (last preload worker) rewrites leaf entries to inner row ids, keyed by the HOT chain root, and marks entries without an inner row LP_DEAD. The service maps the index pages (`scan_exec_join_open`), the depth table has 19 words (`JDT_WORDS`; [14] strategy, [15] y register, [16] page 0 offset, [17] blocks, [18] step limit) and `join_common.inc` walks it (`gist_open`, `gist_next`: downlinks and parent metadata in pd_lsn, no right-links). A non-finite probe point and the step limit (`pg_strom.gpugist_max_steps`, session field `gist_max_steps`) are errors (`SOP_GIST_*_CODE`). GiST programs stay on the interpreter. Tests: `gist_tests.inc` / `gist_dev.sh`, also part of `scan_test.sh`. Added after the first push: semi, anti, RIGHT and FULL joins use the same walk (the planner and builder refusals are gone; PostgreSQL itself cannot plan a FULL JOIN on `&&`, so the test checks left + right - inner rows), and the page copy remembers each page's LSN, verifies them after the copy and repeats it up to three times, then raises a serialization failure ("kept changing", retry the query); `gist_tests.inc` runs joins in a repeatable-read snapshot against a table that gets bulk inserts (index splits) and compares the GPU with the CPU. **Slice 2 as built (2026-11-05).** `gist.c` matches `st_contains(inner.geom, pt)`, `st_within(pt, inner.geom)` and `st_intersects` (either order); `pt` is `st_makepoint(x, y[, z[, m]])` of outer columns, optionally under `st_setsrid(., const)`. **GpuPreAgg over a GiST join (2026-11-05).** An accumulator cannot retract what a poisoned outer row already added, so the service decides the poison before it aggregates: a **scout pass** runs the join kernel with poison markers only (no records, no accumulation) and sets one bit per poisoned outer row in a skip bitmap kept in the page-table buffer; the aggregating kernels (`jagg` / `jgagg`) then skip those rows. The skipped rows are returned to the backend as a `KDS_FORMAT_RECHECK` chunk and take the path of slice 2 (`execCpuRecheckOneChunk` -> `execCpuFallbackBaseTuple` -> `__execFallbackCpuJoinOneDepth`, GiST depth through the nest-loop fallback), which projects each joined row to the partial-aggregate row of `custom_scan_tlist` (group keys and `pgstrom.psum()` / `nrows()` calls); the Agg node above GpuPreAgg, which is always there for the join case, combines the GPU's partial states with the backend's. Planner (`gpu_preagg.c`): the refusal of a join with `gist_func_oid` is gone; RIGHT/FULL together with a GiST join stay refused (see "GpuPreAgg over RIGHT and FULL joins"), and GPU-Sort of the groups is not built over such a join (`tryAddGpuSortedGroupByPath`; the service's GPU-Sort refuses RECHECK rows). The join program for the aggregation task comes from the same `codegen_build_packed_joinquals` call as for GpuJoin, so `pgstrom_codegen_join_geom` is already on for it. Tests: `gist_tests.inc` section "GpuPreAgg over a GiST join" (`gistagg` requires GpuPreAgg and GPU GiST Join in the plan): slice-2 and slice-3 tables ungrouped and grouped by outer / inner / two keys, LEFT, semi / anti, empty result, big polygons, bad tolerances, RIGHT staying off GpuPreAgg, and `pg_g4z` / `pg_g4p` (30 overlapping polygons plus Z, M, ZM, line and point partners for the same outer rows).

**Slice 1 design constraints (2026-11-04; probes in `test/gpuserv/postgis/gist_probe.sql`, `gist_srid_probe.sql`; tests first in `gist_tests.inc` / `gist_dev.sh`).**

- Index layout (pageinspect, PostGIS 3.7): key `box2df` = 4 floats (xmin, xmax, ymin, ymax) at index tuple +8; internal entries ctid `(child, 65535)`, 24 bytes; leaf entries carry the heap TID; an empty geometry's key is four NaNs; a NULL geometry has a leaf entry with the null flag (`t_info` bit 0x8000) and no key; coordinates beyond float range clamp to +-FLT_MAX.
- `&&` between different SRIDs does not error (it compares the boxes), so the GPU ignores the SRID.
- HOT chains: a leaf entry points at the chain root, the visible tuple may be a later member. Key the inner row lookup on `(block, root offset)` (`heap_get_root_tuples()` per loaded page), not on the visible tuple's `t_self`; otherwise HOT-updated rows vanish silently. The test asserts `n_tup_hot_upd > 0`.
- The walker follows downlinks only. Following rightlinks too would visit leaves twice on a consistent tree; PostgreSQL follows them only after a concurrent split (NSN against the parent LSN), and that check needs the real `pd_lsn`, which the preload overwrites with parent metadata. Copy consistency against concurrent inserts is an open item that must be closed before the GUC can default on.
- A walk that reaches the step limit raises a task error (`pg_strom.gpugist_max_steps`); a refused or truncated program has no CPU fallback, so a short result would look valid.
- The box overlap test is a conjunction of `<=` comparisons, so a NaN key (empty geometry) never matches; the query box reuses GEOMBOX's outward float4 rounding and clamping, one copy of that code.
- Planner scope: the inner side is the plain heap base relation that owns the index (no partitioned parents, inheritance children, subqueries); both argument orders of `&&` are accepted.

## Desktop tier: pros and cons (decided: implement after A3, experimental)

Evidence from the Linux container: lavapipe (Mesa's CPU Vulkan, Vulkan 1.4) reports `shaderInt64`, `shaderFloat64`, 64-bit buffer and shared atomics, buffer device address, the Vulkan memory model, and `VK_EXT_external_memory_host`. All the Apple spike kernels (scan, 16-bit-limb sum, the opcode VM, specialized kernels) passed on it, and Apple's Metal-rejected int64 `subgroupAdd` compiles there. Two numbers from it matter for the design: **subgroup size 4** (code that assumes 32 breaks) and **`maxStorageBufferRange` of 128 MiB**, which a base tier that assumes at least 1 GiB would exclude (BDA or chunking is needed). The VM was 3.2x slower than the hand-written kernel there, against 10x on the M1; CPU timings say nothing about GPUs.

| | Implementing the desktop tier (64-bit atomics, fp64) |
|---|---|
| **Pros** | `float8`, the most common floating type in PostgreSQL, can be pushed down (on Apple it stays on the CPU). 64-bit atomics make PreAgg simpler and faster: `sum`, `min`, `max` on `int8` and 64-bit hash-slot CAS need no limb or two-pass workaround. It delivers the stated cross-platform objective (NVIDIA, AMD, Intel on Linux). lavapipe gives a free correctness oracle for the logic, including exact IEEE fp64, with no GPU needed. BDA lifts the 4 GiB buffer limit. |
| **Cons** | It cannot be validated on real hardware, which you have ruled out; lavapipe passing is not the same as an NVIDIA, AMD or Intel GPU passing (driver quirks, NVIDIA's proprietary int64-atomics support is unverified, AMD wave64, Intel subgroups of 8 or 16, forward progress, memory ordering). Two compiled kernel variants double the test matrix and can drift apart. Discrete GPUs change the memory design (PCIe copies) and performance, none of which can be measured here. It costs effort that the Apple-only product does not need. |

**Recommendation:** keep the tier abstraction and the probed `devcaps` now (cheap, and Apple needs them anyway). Defer the desktop shims until after A3, then implement only what lavapipe can verify exactly (fp64 arithmetic, 64-bit atomic sum/min/max), behind capability bits so the Apple path is untouched, and ship it labelled experimental and unvalidated. Do not tune performance for it. **Decided:** the desktop tier is implemented after A3 as milestone A3b, on exactly these terms (verifiable-by-lavapipe features only, behind capability bits, experimental, unvalidated, no performance tuning).

## Risks

**Top 3 that could invalidate the approach**
1. **Cost of the expression and type engine** (about 670 opcodes, varlena in the VM, superlinear Metal compile times). Mitigation: one op library, VM first, type breadth in A6, CPU fallback through gating, specialization optional.
2. **Everything outside Apple is unvalidated.** The Vulkan code is portable by design, but memory-model, subgroup and driver behaviour on other vendors is unknown. Mitigation: devcaps probe, lavapipe VM, honest labelling.
3. **MoltenVK dependency.** Regressions or translation bugs on the only validated platform. Mitigation: pin the version; Slang can emit MSL if MoltenVK blocks us (behind `gpu_vk.c`).

**Others:** the A2 to A4 window leaves the branch without join/aggregate offload; watchdog timeouts on long dispatches (bounded dispatch size); devices with a very small `maxStorageBufferRange` fall below the base tier; hard-fork maintenance.

## Assumptions to confirm (defaults used unless you object)

1. `master` stays CUDA and untouched; all work is on `vulkan-gpu`.
2. Linux and non-Apple vendors are "designed for, not tested"; the optional lavapipe VM track is used for host-code portability.
3. Desktop-tier shims are implemented after A3 (milestone A3b) as an experimental, unvalidated tier, tested on lavapipe only.
4. `libslang` is an optional `dlopen`ed runtime dependency; servers without it run the VM only.
5. Minimums: Vulkan 1.2 plus the needed extensions, macOS 14 or later, PostgreSQL 15-19 kept.
6. The 1.5x/2x-versus-CUDA criterion is recorded but not a gate on this branch.

## Verification (how each stage is checked end to end)

- **Correctness:** the existing `pg_regress` schedule runs with `pg_strom.enabled=on` against the CPU result of the same query (`pg_strom.enabled=off`); `test/Makefile` gets a `vulkan_schedule` that grows per milestone, with `pending_schedule` holding what is not ported yet. Plan-shape tests confirm offload or correct gating.

- **Performance:** each of A2-A4 compares against PostgreSQL's own parallel plan on the same Mac and table (spike baseline: 163 ms with 8 workers for 16.8M rows; the realistic end-to-end GPU figure today is about 28 ms specialized and 56 ms VM including the page copy).

## Kernel source language: Slang (carried over, decision unchanged)

- Slang has a real preprocessor, so `xpu_opcodes.h` can be included unchanged.
- It supports generics and interfaces, which suit the type library.
- It emits SPIR-V and also MSL, which keeps a native Metal path open if MoltenVK limits block us.
- Rejected: GLSL (no generics, macro-heavy), HLSL/DXC (no Metal path), clspv (poor pointer model, thin maintenance), and CUDA-to-SPIR-V translators such as chipStar/ZLUDA (they emit OpenCL-flavoured SPIR-V, which Vulkan and MoltenVK reject).

**Avoiding two diverging code bases.** The kernel bodies must differ, so the shared contract is the ABI:
1. `xpu_opcodes.h` is the single opcode source for `codegen.c`, CUDA and Slang.
2. A new `src/xpu_layout.def` (X-macro of fields and offsets) generates static asserts for the C structs and `src/vulkan/xpu_layout.slang` offset accessors.
3. One test suite and oracle (CPU PostgreSQL) for the single Vulkan backend.
4. Pure scalar helpers go in a shared `xpu_scalar_ops.inc`, written in the common C/Slang subset.

## Kernel ABI and build (carried over; superseded where the plan above says otherwise)

- **Memory.** Use VMA, with a pool per existing `gpuMemoryPool`.
  - Apple: unified memory, so every buffer is device-local and host-visible, persistently mapped. Prefetch is a no-op.
  - NVIDIA: a host-visible staging ring feeds device-local buffers via `vkCmdCopyBuffer`. Read-back happens on demand. ReBAR heaps are used when present.
  - Buffer growth: the kernel reports overflow, the host reallocates and relaunches, reusing the existing suspend/resume logic.
- **Shader build.** `Makefile.vulkan` runs `slangc -target spirv` per entry point. The entry points are packed into `pgstrom-vulkan-<slangc-ver>-<md5>.spvpack`, mirroring the fatbin naming and runtime rebuild logic (`gpu_service.c:640-915`). A `VkPipelineCache` is persisted under `$PGDATA/pg_strom/`.
- **Kernel ABI.** One descriptor set with fixed bindings (session and program, task state, `kds_src`, `kds_dst`, inner/extra, scratch arena, error buffer), plus push constants of at most 128 bytes. Buffers are `RWByteAddressBuffer`, offset-based, with 64-bit loads done as two 32-bit loads. BDA is not required in M1 and is gated by `devcaps.BDA` (it works on MoltenVK per the spike).
- **Subgroups.** Rewrite the stair-sum and scan primitives (`cuda_gpuscan.cu:33-76`, `cuda_common.h:26-32`) with `WaveActive*`/`WavePrefixSum`. Request size 32 via `VK_EXT_subgroup_size_control` where available, with a shared-memory scan fallback. Workgroup size is a specialization constant (default 256), capped by device limits.

**What this changes in the plan**
- **BDA works on MoltenVK.** The earlier worry ("poorly supported") was wrong on this device. BDA stays optional for M1 (offset ABI is still the portable default), but it is a viable fallback for pointer-heavy structures later. Keep it behind `devcaps.BDA`.

- **No 64-bit atomics on M1-class devices.** M2 aggregates (`sum`, `count`, `min`, `max` on 64-bit) cannot use CAS or native atomics. Sum works with the limb + carry technique above. `min`/`max` on 64-bit and any 128-bit accumulator still need a design (per-workgroup partials plus a second reduction pass is the leading option). This is now the main technical risk for M2.
- **M1 scope is unblocked.** Everything GpuScan needs (deform, int/float32/int64 quals, ballot compaction, error buffer) ran on the hardware. float8 remains gated off, as planned.

### Slang port of the scan kernel (done)

`spike/vulkan-apple/shaders/scan.slang` is a line-for-line port of `scan.comp` (Slang 2026.20, official macOS aarch64 release). It compiled on the first attempt with `slangc -target spirv -entry main -stage compute`, passes `spirv-val --target-env vulkan1.2`, and on the M1 Pro produces the same 1,078,674 matches, with an identical index set to the CPU reference. Across five runs both builds landed between 1.6 and 2.2 ms (best-of-5 each) with no consistent difference. That is too coarse to rank them: at this size the kernel is bandwidth-bound and the timer includes submit and fence overhead.

- The port is smaller: HLSL-style wave intrinsics (`WaveActiveCountBits`, `WavePrefixCountBits`, `WaveIsFirstLane`, `WaveReadLaneFirst`) replace the GLSL extension boilerplate, and `StructuredBuffer<uint8_t>` and `int64_t` map straight to SPIR-V 8-bit storage and Int64.
- Slang requests `UniformAndStorageBuffer8BitAccess`, where glslang requested `StorageBuffer8BitAccess`. Device creation must enable both 8-bit storage features; `devcaps` should probe for them.
- This validates the toolchain for one small kernel only. It does **not** yet cover the parts of the plan that carry the real risk for Slang: including `xpu_opcodes.h` unchanged, generics or interfaces for the type library, the opcode-switch VM, and compile time on a large shader set. Treat the choice of Slang as supported, not settled, until M1a has a representative slice of the VM compiling.

### Opcode-switch VM prototype in Slang (done)

Code: `spike/vulkan-apple/` (`make run-vm`): `shaders/vm.slang` (the VM), `vmspike.c` (tree linearizer, CPU references, checks), `gen_opcodes.sh`. Measured on the M1 Pro, 16M rows of 21-byte unaligned rows.

**What works**
- **`xpu_opcodes.h` is used unchanged by Slang.** It compiles, and 670 opcode entries expand into the enums. Only a warning appears: the header leaves three helper macros (`__FUNC_OPCODE`, `__FUNC_LOCALE_OPCODE`, `__FUNC_RECURSIVE_OPCODE`) defined at the end, so including it a second time redefines them. Adding three `#undef` lines at the end of the header would silence that. It is not applied.
- **One source of numbering.** The `TypeOpCode`/`FuncOpCode` enums live in `xpu_common.h`, not in `xpu_opcodes.h`. `gen_opcodes.sh` extracts them verbatim for both the C harness and Slang, and the VM dispatches correctly on the values the C side emits (for example `int4pl`=85, `int4div`=160). A real implementation should move the enum into a shared header (an M0 refactor) instead of extracting it with awk.
- **No recursion, no function pointers.** The host flattens a tree into a register program `{op, dst, a, b, imm_lo, imm_hi}`, and the shader runs a `switch(op)` loop. `AND`/`OR` become accumulate-and-jump steps with SQL three-valued logic. `VarExpr` selects the heap-read by `TypeOpCode`, which replaces the `xpu_datum_operators` vtable.
- **Correct on all 5 tests**, each checked against an independently written CPU reference (exact index sets for 2.6M and 7.4M matches): arithmetic plus compare under `AND`; `NULL` tests with `OR`/`NOT`; a short-circuit case where `NOT(d = 0) AND a / d > 3` must not raise the zero-divide that 150k rows would cause; and two cases that must report the right error code (`int4div` 160, `int4pl` 85) at a row that really errors.
- **`int8pl` overflow is detectable without int128**, using a sign test on int64. The CUDA templates use `int128_t` even for `int8` add and subtract. `int8mul` was not implemented, so its overflow check is still open.

**What does not work well: speed**

| Kernel (same predicate E1, 16M rows) | Time |
|---|---|
| Hand-written kernel | 3.0 ms |
| Opcode-switch VM | 31 ms (10.5x slower) |
| One CPU thread | 39 ms |

The VM is compute-bound: it moves about 11 GB/s on a chip with several times that bandwidth. I tried the obvious fixes, and none helped much: a 4-entry register file with no zero-init (26.7 ms), and the program in a uniform buffer (33.9 ms, no gain). That points at interpretation overhead itself (per-instruction decode and dispatch, and int64 arithmetic for every register op), not at instruction fetch or register spilling. This is one expression on one GPU, so treat 10x as an order of magnitude, not a constant.

**Pipeline creation cost (cold = fresh shader text, so Metal cannot reuse a cached build)**

| Kernel | Cold | Warm |
|---|---|---|
| VM | about 105 ms | about 3 ms |
| Small specialized kernel | about 23 ms | about 0.5 ms |
| `slangc` to SPIR-V (both) | about 0.15 s | n/a |

**What this changes in the plan**
- **The VM alone is not enough on Apple.** It is a good correctness baseline and costs one pipeline build, but a 10x gap on an expression-heavy qual removes most of the GPU's advantage over parallel CPU workers.
- **Add per-expression specialization as a follow-on (M1c).** Generate a kernel from the linearized program, compile it, and cache the pipeline by program hash. The M1c experiment measured what it buys: generated kernels ran 8-13x faster than the VM and within 1.24x of the hand-written kernel, at a cold cost of roughly 0.2-6 s depending on expression size (see below). The planner needs a rows-times-size threshold. The M1c experiment below confirmed this with generated Slang text compiled by the `slangc` CLI. Whether to embed `libslang` or emit SPIR-V directly instead was not tested.
- **The VM stays as the fallback and the correctness oracle** for the specialized path, and for expressions too large or too cold to be worth compiling.
- **Fixed-width registers only cover fixed-width types.** Registers are 16 bytes (int64 value plus null flag), which fits bool, int2/4/8 and float4. text, numeric, jsonb and other varlena types need arena offsets and variable-length results. The prototype does not address that, and it is the largest remaining unknown for M4.

**Not covered:** 12 of the roughly 670 function opcodes are implemented; NaN ordering for floats; `CASE`, `COALESCE`, scalar-array ops; projection and `LoadVars`; any type wider than 8 bytes; error-reporting parity with CUDA's `kern_errorbuf`; and behaviour on NVIDIA.

### M1c experiment: specialized kernels generated from the expression trees (done)

Code: `generate`/`specialize` in `spike/vulkan-apple/vmspike.c` (about 150 lines of C emitting Slang text), plus `shaders/common.slang` shared with the VM. The generator walks the same trees as the linearizer and emits one kernel per expression: typed locals (`int`, `int64_t`, `float`, `bool`) with explicit NULL flags, no register file, and each `AND`/`OR` as a `do { ... break; } while (false);` block so a short-circuit is a structured jump. It covers the same 12 opcodes as the VM. The text is compiled with the `slangc` CLI, cached by a hash of the source, and loaded as a pipeline. `make run-vm` runs everything; `SPEC_COLD=1` forces fresh shader text so neither `slangc` nor Metal can reuse a cached build.

**Correctness.** All five expressions pass the same checks as the VM: exact match sets against the CPU reference, the right error opcode at a row that really errors, and the short-circuit case raising no zero-divide. The specialized kernel is therefore a drop-in for the VM on this opcode subset.

**Speed (16.8M rows, data already resident, best of 5)**

| Expression | VM | Specialized | Hand-written | VM / specialized |
|---|---|---|---|---|
| E1 (4 terms, 20 insns) | 31.4 ms | 3.7 ms | 3.0 ms | 8.6x |
| E2 (`NULL` tests, `OR`, `NOT`) | 36.4 ms | 2.8 ms | n/a | 13x |
| E5 (short-circuit) | 23.7 ms | 3.1 ms | n/a | 7.7x |
| N=4 terms (27 nodes) | 52.1 ms | 6.0 ms | n/a | 8.7x |
| N=16 (111 nodes) | 215.5 ms | 20.5 ms | n/a | 10.5x |
| N=64 (447 nodes) | 886.6 ms | 90.3 ms | n/a | 9.8x |
| N=256 (1,791 nodes) | 3,582.6 ms | 376.2 ms | n/a | 9.5x |

- **The generated E1 kernel is 1.24x the hand-written one**, inside the M1c target of 1.5x. Specialization recovers essentially all of the 10x.
- **The gap is a steady 8-13x at every size**, so it is not an artifact of small expressions. Large expressions are compute-bound in both forms, and the specialized form is about 9.5x faster per node throughout.

**Cost of specializing (cold, fresh shader text)**

| Expression | Nodes | `slangc` | Metal pipeline | Total |
|---|---|---|---|---|
| E1-E5 | 12-30 | about 140-150 ms | about 24-27 ms (E1: 76 ms, includes first-use start-up) | about 170-225 ms |
| N=4 | 27 | 147 ms | 39 ms | 186 ms |
| N=16 | 111 | 172 ms | 96 ms | 268 ms |
| N=64 | 447 | 325 ms | 517 ms | 842 ms |
| N=256 | 1,791 | 1,630 ms | 4,796 ms | 6.4 s |

Two runs of the scaling cases agreed within a few percent. Generating the source takes under 1 ms even at N=256. With a warm Metal cache, pipeline creation is about 1 ms. `slangc` runs as a separate process, so about 140 ms of its time is fixed start-up and compile overhead; whether `libslang` or direct SPIR-V emission would cut that was not tested.

**Break-even** (rows scanned before the compile cost is repaid, from the measurements above)

| Expression | Compile | Saved per 16.8M-row scan | Pays back after |
|---|---|---|---|
| E1 | about 175-225 ms | 28 ms | about 100-135M rows |
| N=4 | 186 ms | 46 ms | about 68M rows |
| N=16 | 268 ms | 195 ms | about 23M rows |
| N=64 | 842 ms | 796 ms | about 18M rows |
| N=256 | 6.4 s | 3.2 s | about 34M rows |

**What this means for the plan**
- **Specialization is the fast path and the VM is the fallback (revised by the real-page measurement below: run the VM first, specialize when it pays back).** On a one-off scan below roughly 20-130M rows (depending on expression size) the compile cost exceeds the saving, so the VM is faster end to end. Above that, or whenever the same expression runs repeatedly and the pipeline is cached by hash, specialization wins by about 9x. A planner threshold on estimated rows times expression size is needed. A persistent on-disk cache (the Metal cache already behaves this way for identical shader text) removes the cost for repeated expressions.
- **Metal compile time is superlinear**: 4x the nodes (N=64 to N=256) cost 9x the pipeline time. Very large predicates should stay on the VM. Removing duplicate loads in the generator (each `Var` currently reloads its column) might shrink the kernel and its compile time; that was not tried.
- **The VM penalty only shows when data is resident and the kernel is compute-bound.** These rows are 21 bytes. With wide rows, or when heap pages have to be fetched and moved first, scan I/O dominates and the VM's cost is partly hidden. That moves break-even later, not earlier. The real PostgreSQL path (M1b) must be measured before fixing the threshold.
- **Not tested:** `libslang` embedding, direct SPIR-V emission, compile in a background thread while the VM runs the first scan, error-path performance (E4 is slow in both forms because millions of rows contend on one error word), and anything on NVIDIA.

### Real PostgreSQL scan path measurement (done)

> **Correction (verified in code, `src/relscan.c:439-500`, `src/executor.c:171-195`):** PG-Strom copies every page under `BUFFER_LOCK_SHARE` into the command buffer and performs the tuple-visibility check **on the CPU** (invisible tuples are marked unused in the copy) before anything reaches the GPU. So the "visibility checks not implemented" limitation below does not apply to the real kernel path. The end-to-end figures that follow use kernel time plus a 21 ms page copy; the later zero-copy section removes only the *service-side* copy, not this backend copy.

Code: `spike/vulkan-apple/` (`pg_setup.sh`, `pg_baseline.sh`, `heapspike.c`, `shaders/heap_common.slang`; `make run-heap`). A throwaway PostgreSQL 17.11 cluster (Homebrew, under `/tmp`, no TCP, port 54329) holds `t(a int4, b int8, f float4, d int4)` with 16,777,216 rows (823 MB, 105,381 pages, same distributions and NULL rates as the earlier row tests). It was `VACUUM (FREEZE)`d and the visibility map confirms all 105,381 pages are all-visible and all-frozen, which is what lets the kernel skip per-tuple visibility checks. The harness copies the relation file's raw 8 KB pages into a GPU buffer and scans them with a Slang kernel that parses the page header, the line pointers and the tuple headers, deforms the four columns (null bitmap, 8-byte alignment of `int8`) and evaluates the predicate. The page, line-pointer and tuple-header offsets were checked against the installed PostgreSQL 17 headers.

**Correctness.** Every kernel run matched the SQL oracle exactly, on two predicates: the match count and the sum of `blkno * 512 + offnum` over all matches (derived from `ctid` in SQL), for 2,589,788 (E1) and 7,405,661 (E2) matches.

**Speed, same table and predicate E1 (16.8M rows, table fully in shared buffers, best of 5)**

| Path | Time | Notes |
|---|---|---|
| PostgreSQL, no parallelism | 909 ms | `SELECT count(*)`, JIT off |
| PostgreSQL, 8 workers | 163 ms | 6 performance + 2 efficiency cores; 6 workers: 171 ms |
| GPU VM, kernel only | 34.8 ms | 41.4 ms for E2 |
| GPU specialized, kernel only | 7.2 ms | 5.6 ms for E2; identical to the hand-written kernel |
| Page transfer into the GPU buffer | 21 ms | `memcpy` from ordinary memory, about 42 GB/s |
| Reading the pages from the OS cache with `pread` | 193 ms | what the service would pay if it read files itself |

End to end per scan (kernel + page copy): **VM about 56 ms** (2.9x faster than 8-worker PostgreSQL, 16x faster than one process); **specialized about 28 ms** (5.8x and 32x). Neither the workgroup size (64-256 threads) nor the workgroup count (2,048-65,535) changed any kernel time by more than a few percent.

**What this changes in the plan**
- **The hand-written and specialized kernels are memory-bandwidth-bound**: 823 MB in 7.2 ms is about 120 GB/s, the same rate as the row-format kernel earlier. They cannot go faster on this chip. The VM is compute-bound at about 25 GB/s.
- **The page copy is now the dominant cost of the fast path**: 21 ms of the 28 ms specialized total. Avoiding the copy (importing host memory into Vulkan with `VK_EXT_external_memory_host`) would matter more than any further kernel work; the zero-copy test below confirms it works on this device. The service must also consume pages from shared memory, not read relation files, since `pread` cost 9x more than the copy.
- **The VM penalty is smaller end to end than in the kernel-only tests**: 56 ms vs 28 ms (2x), because the copy is common to both. The earlier concern that I/O would hide part of the VM cost is confirmed: roughly a quarter of the 10x is hidden once the copy is included.
- **Specialization threshold, revised.** The VM alone already beats parallel PostgreSQL by about 3x. A cold specialized kernel costs 170-240 ms to build here (`slangc` 140-170 ms plus pipeline 26-70 ms), against about 28 ms saved per 16.8M-row scan, so it pays back only after roughly 7-9 scans of this size, about 115-150M rows (6-7 GB of heap), or immediately if the pipeline is already cached. So: **run the VM first, specialize in the background or only for expressions that recur or for scans well above about 100M rows.** The earlier "specialize by default" recommendation is withdrawn for one-off scans.
- **M1b target, restated with a measured baseline.** The plan compared against "the CPU"; the real baseline is PostgreSQL's own parallel seq scan, 163 ms for this table on 8 workers. A kernel-plus-copy time below that is the bar; the VM already clears it by 2.9x.

**Not measured, and likely to narrow the margin**
- **Integration overhead:** moving pages from PostgreSQL's shared buffers to the service, launching per-chunk kernels, and returning results. The GPU side here returns only match ids; PostgreSQL's side includes the aggregate. A `GpuPreAgg` that aggregates on the device would avoid shipping matches, but that is M2.
- **Visibility checks:** only a fully frozen, all-visible table was tested. Pages that are not all-visible need per-tuple checks, which were not implemented.
- **Cold data:** the table was in shared buffers and the OS cache. A cold scan is dominated by storage in both systems.
- **Row shape:** 4 fixed-width columns, no varlena, no TOAST, about 160 rows per page. Wider or text-heavy rows change the balance, and the VM cannot represent text yet.
- **Contention:** PostgreSQL workers and the GPU shared the same memory system but were never run at the same time.
- **Unexplained:** the specialized E2 kernel (5.6 ms) is faster than E1 (7.2 ms) although both deform the same bytes; I did not investigate.
- Single machine (M1 Pro, 16 GB), one PostgreSQL version, one run of setup.

### Zero-copy import of host memory (done)

> **Correction:** the end-to-end numbers in "What this changes" below (about 7.2 ms specialized and 35 ms VM) leave out the mandatory backend copy under the share lock (about 21 ms per 823 MB). Realistic figures on this Mac are about **28 ms specialized and 56 ms VM**, against 163 ms for 8-worker PostgreSQL (5.8x and 2.9x faster). Zero-copy applies to unified memory only (Apple, integrated GPUs); on discrete GPUs every byte crosses PCIe. The statement that the service should import PostgreSQL's memory directly is replaced by the per-session shared-memory ingest ring in the plan above.

Code: `spike/vulkan-apple/` (`vk_buf_import` in `vkutil.h`; `HEAP_SRC` modes in `heapspike.c`; `zc_test.sh`, `zc_cold.sh`). `VK_EXT_external_memory_host` wraps existing host memory as a Vulkan storage buffer, so the kernel reads it in place. The device reports `minImportedHostPointerAlignment` = 16 KB, and the imported memory type is device-local, host-visible, coherent and cached (flags 0xf), the same type as normal allocations. The throwaway cluster was recreated for this and removed afterwards. Same table shape, 16.8M rows, 863 MB.

| Page source (all imported with no copy) | Import time | Kernel (hand-written E1) | Matches SQL oracle |
|---|---|---|---|
| Control: `memcpy` into a Vulkan buffer | 19 ms copy per scan | 7.2 ms | yes |
| Anonymous `mmap`, filled by `pread` | 0.1 ms | 7.2 ms | yes |
| POSIX shared memory (`shm_open`), filled by a different process, attached by name | 0.1 ms | 7.2 ms | yes |

| Relation file, `mmap` `MAP_PRIVATE` | 0.1 ms | 7.2 ms | yes |

For every source the VM and the specialized kernels also matched the oracle on E1 and E2. Imported memory is no slower for the kernel than a normal buffer.

**Coherence (does the GPU see CPU writes with no copy in between?)** After a scan, the CPU zeroed column `a` in 1,000 matching tuples through the mapping, and the GPU rescanned. Every imported source showed exactly 1,000 fewer matches (the GPU read the writes in place). For shared memory the writes went through a second mapping of the same region. The control (copied buffer) correctly showed the old count, so the test can detect a stale view. The `MAP_PRIVATE` case also showed the writes; I would not have predicted that for copy-on-write memory, and I have no explanation, so nothing should rely on it.

**Cold file pages.** A copy of the relation file written with `F_NOCACHE` had 0% of its pages in the OS cache (checked with `mincore`). With the GPU as the first reader, the scan was still correct (oracle matched), the first dispatch took **333 ms** against 7.3 ms afterwards, and residency was 100% when it finished. So the pages are brought in on first use at about storage speed (863 MB in roughly 325 ms, 2.6 GB/s), with no error. The mechanism (pre-faulted at submit, or faulted during execution) was not determined.

**What this changes in the plan**
- **The page copy disappears.** End to end per scan on warm memory is now the kernel time: **about 7.2 ms specialized and about 35 ms for the VM**, against 163 ms for 8-worker PostgreSQL (22x and 4.7x faster) and 909 ms for one process. The earlier figures that included a 21 ms copy (28 ms and 56 ms) no longer apply on Apple.
- **Specialization matters more again.** With the copy gone, the VM is about 5x slower end to end, not 2x. Payback is unchanged (compile 170-240 ms against about 28 ms saved per scan, so about 7-9 scans), but the benefit per scan is 5x instead of 2x.
- **The service can map shared memory or the relation files directly.** On Apple, M1b should import PostgreSQL's memory (or mapped files) rather than copy pages.

**Not tested, and the real design risks**
- **PostgreSQL's actual `shared_buffers`.** Only my own mappings were imported. In the real design the GPU service is a background worker forked from the postmaster, so it already has `shared_buffers` mapped and needs no named region. PostgreSQL aligns `BufferBlocks` to 4 KB, so the import range would have to start at the next 16 KB boundary and skip at most one leading buffer. Importing a range above 4 GB (`maxStorageBufferRange`) would need several imports. Neither was tried.
- **Concurrent writers.** PostgreSQL backends modify buffers under content locks that a GPU kernel cannot take. A scan over live buffers can see torn pages unless the buffers are pinned and protected, or the pages are snapshotted. My coherence test only wrote between scans. This is the main correctness risk of in-place reads.
- **Very cold or very large files.** A first dispatch that has to page in several gigabytes could run into a GPU command-buffer time limit; I only tested 863 MB (333 ms).
- **Memory pressure.** Whether imported pages are pinned in RAM for the life of the buffer was not checked.
- **NVIDIA/Linux:** this is `VK_EXT_external_memory_host` on MoltenVK. The CUDA path uses `cuMemHostRegister`, a different mechanism, and was not looked at.

### Live shared_buffers with a concurrent writer (blocked on macOS; superseded, platform findings still valid)

> **Superseded:** PG-Strom never reads live `shared_buffers` from the GPU (see the correction under "Real PostgreSQL scan path measurement"), so the torn-read question this section leaves open does not arise in the real design, and the `zcscan/` module and `heap_live.slang` kernel are not needed. What stays valid: a forked process cannot use Metal's shader compiler, the postmaster cannot pre-initialise Metal under PostgreSQL 17, and an exec'd helper cannot attach the anonymous buffer pool; together they are why the GPU service is an exec'd process on macOS. The "What this means for the plan" bullets below that talk about in-place reads of live buffers are moot.

Code: `spike/vulkan-apple/zcscan/` (a PostgreSQL module: pins a table's buffers, imports the whole `shared_buffers` array into Vulkan, scans three ways), `shaders/heap_live.slang` (a lock-free, bounds-checked scan that detects torn reads through a per-tuple invariant `b = 3a + d + 7` that every writer preserves, bad line pointers, bad tuple headers and bad page headers), `pg_setup_live.sh`, `live/writer.sql`, `live/reader.sql`, `forktest.c`, `forktest2.c`. Everything built and ran up to the first GPU dispatch inside a backend; no torn-read measurement could be taken.

**What worked.** PostgreSQL's real `shared_buffers` (an anonymous shared `mmap`, 1,199 MB, 153,600 buffers) was imported into Vulkan without error. `BufferBlocks` is only 4 KB-aligned, so 12,288 leading bytes had to be skipped to reach the 16 KB import alignment (one or two leading buffers cannot be scanned in place). The module compiled against the Homebrew PostgreSQL 17 headers with PGXS (`MODULE_big`; `SHLIB_LINK` is ignored for a plain `MODULES` build).

**What blocked the test (each reproduced; the first two without PostgreSQL)**
1. **A forked process cannot use Metal's shader compiler unless its parent already initialised Metal.** A backend, like any `fork()` without `exec`, fails with `Unable to reach MTLCompilerService ... Connection init failed at lookup with error 3 - No such process`. `forktest.c`: compiling a fresh shader in a normal process works (about 75 ms); forking first, with the parent never touching Vulkan, and compiling in the child is rejected with that error. A warm Metal cache did not help, and neither did `setsid()` (ruled out).
2. **The postmaster cannot pre-initialise Metal either.** Creating even a bare Vulkan instance makes the process multithreaded (`pthread_is_threaded_np()` goes from 0 to 1), and PostgreSQL 17 aborts: `FATAL: postmaster became multithreaded during startup`. So the obvious workaround (initialise in `shared_preload_libraries`) is impossible on this PostgreSQL.
3. **An exec'd helper cannot reach `shared_buffers`.** The buffer pool is anonymous memory that another process cannot attach. `shared_memory_type = sysv` would make it attachable, but `kern.sysv.shmmax` here is 4 MB (4,194,304), so a 1.2 GB pool needs root to raise the limit.

**What this means for the plan**
- **On macOS the GPU service must be a separately executed process, not a PostgreSQL background worker.** The Linux design (a bgworker forked from the postmaster) does not carry over. This changes M1b and the macOS portability track (P): the service is spawned with `exec` and talks to backends over the existing socket protocol.
- **Reading live buffers in place is not available on macOS with stock PostgreSQL.** The only way the GPU service sees PostgreSQL pages is a copy that a backend makes into a named shared region (POSIX shm, which the zero-copy test above showed imports fine). The safe protocol for that copy is a shared content lock per buffer. So the practical macOS design is: backend copies pages under lock into shared memory, and the GPU scans that region in place. The copy (about 21 ms per 823 MB measured earlier, plus locking) comes back, but it stays on the CPU side and the GPU still reads without a second copy.
- **The torn-read risk for in-place reads of live buffers remains untested.** It still applies to the Linux design, where a bgworker can map `shared_buffers`. The prepared kernel and extension are the starting point, but they need a Linux machine (or a way around blockers 1-3).
- **Pinning:** a backend that pins buffers stops PostgreSQL pruning and defragmenting those pages (cleanup locks wait for all pins). An external helper cannot pin buffers at all. Neither effect was measured.

**Not covered by the spike (still open)**
- M2 or newer Apple GPUs (the plan assumed they may add 64-bit atomic min/max; unverified).
- Subgroup-size behavior under load (`VK_EXT_subgroup_size_control`), pipeline cache persistence, and multi-threaded queue submission.
- Anything on NVIDIA/Linux (M1a).

## Test speed (2026-11-05)

Findings and changes (all on the vulkan-gpu branch, working tree before the commit of this date):

- **Where the time went.** A full `scan_test.sh` took 70+ minutes and the `installcheck` 35 minutes after a change of the kernels. Both were dominated by the first compile of each interpreter kernel by Metal (join kernel: 6.5 MB of SPIR-V at the time (9.6 MB full, 0.9 MB lite after the later growth), 4.5 minutes; warm: 13 s), once after every edit of `kernels_vm/`. A failing run could also hang: the receiver thread in `executor.c` set `conn->terminated` when the service socket closed, but the backend's wait loops never looked at it (fixed: "the connection to the GPU service was lost").
- **Lite kernels.** `scan_common.slang` compiles the numeric, jsonb, float8 and geometry instruction groups out with `-DVM_NO_NUM/JSON/F8/GEOM`; every VM kernel family exists as `<name>_lite` (62 kernels, a fourth to a tenth of the size) and `scan_prog.feat` (set in `emit()`) selects it when the program uses none of the groups. Engine arrays hold both (`pipe[6]`, `agg_pipe[6][3]`, `gagg/jagg/jgagg/aagg/...[4][3]`, `join_pipe[6]`, `ajoin_pipe[4]`). Result: cold installcheck 35 min -> 2.5 min, scan 39 min -> 25 min (warm and cold).
- **First dispatch.** A pipeline's first dispatch gets 600 s (`first_timeout_ms`) because the driver may compile lazily then; later dispatches keep `PGSTROM_GPUSERV_TIMEOUT_MS` (10 s).
- **Pipeline cache: persisted (revised).** The first attempt looked at the cache size through MoltenVK (~14 KB for several pipelines) and dropped it; with the interpreter kernels the blob is large (42.9 MB for the full and lite `gpujoin16`) and it holds what Metal needs, so the creation of the full join pipeline in a new process went from 3.8 s (Metal's own system cache warm) to 20 ms (lite: 125 ms to 1 ms). `gpu_vk.c` `pcache_open`/`pcache_save`: one `VkPipelineCache` per context, file `<cache dir>/pipeline-<vendor>-<device>-<uuid>.bin` (own 24-byte frame: magic, size, hash, because a body damaged on disk made MoltenVK abort), written by temp file + rename (under a mutex, from whichever thread created a pipeline that took >= 50 ms, so also from the specializer worker), ignored on a wrong frame, hash, vendor/device/cache UUID, or a driver that refuses it; over `PGSTROM_GPUSERV_PIPELINE_CACHE_MAX_MB` (768) it is deleted. It does not help the first compile after a change of `kernels_vm/` (full join kernel: 44.9 s with a cold Metal cache in this measurement), which is the other half of the problem. `test/gpuserv/pcache_test.sh` (through `locked_test.sh`; `src/gpuserv/pcache_check.c` creates the join pipelines and prints the times) checks off/cold/warm and truncated, garbage, foreign and damaged files.
- **Prewarm after an edit of the kernels.** `locked_test.sh` runs `test/gpuserv/prewarm_kernels.sh` after the install: the common interpreter kernels (smallest register file of each family, 4 aggregates, full and lite; `PREWARM=all` for every variant) whose SPIR-V checksum differs from `<cache dir>/prewarm.sums` get their pipeline created once by `pgstrom-gpuserv --prewarm NBIND PCSIZE file.spv` (nice, one after the other), and the persisted pipeline cache keeps it. Measured on the M1 after a one-line change of `arrow.slang`: `gpuarrow8` 53.5 s cold (0.58 s for the lite one), then 0.01 s in a new process (0.91 s with the pipeline cache off, i.e. Metal's own cache alone). The compile is the same work as the first query of a test would have done, moved to a place where no query timeout runs and no second backend compiles the same kernel; what is saved is every later service start (installcheck, scan, dev scripts: 0.9 s to 5.5 s per full kernel instead of 0.01 s, about 40 kernels per `scan_test.sh`).
- **`spirv-opt` over the kernels: no gain.** `spirv-opt -O` (SPIRV-Tools 2026.4) stops with "ID overflow" on the full join kernel (9.6 MB; `--compact-ids` first does not help, 26 s) and a hand-picked pass list ran two minutes without producing a file. On the lite join kernel (0.9 MB) it works in 3 s and gives 0.76 MB, but the driver needs 4.5 s for the changed module cold (the unoptimized one: 1.2 s cold, 0.12 s warm) and 0.21 s warm against 0.12 s: Slang has already optimized, and the extra pass only changes what Metal sees. Not added to `gen_kspv.sh`.
- **Sharding.** `SHARD=i/n` in `scan_test.sh` and `scan_shards.sh` work, but three services on one Apple GPU got a Metal command buffer killed ("Impacting Interactivity"): opt-in only (default 1 part), meant for Linux/lavapipe/CI.
- **Pitfalls hit:** the service Makefile did not track headers (stale objects: garbage self-test message, crashes inside MoltenVK) - now `-MMD`; an array enlarged without its `_ready` twin (`pipe_ready[3]`) corrupted the next member; the fuzzer's check mode compares error rows that are racy by nature (do not run `fuzz` through `verify_all.sh`).
- **Resource limits.** `locked_test.sh` builds with 3 jobs and runs tests at `nice -n 10`; test clusters use `pgconf_test.sh` (fsync off, autovacuum off, parallel workers capped). Same wall time as before (installcheck 132 s + scan 1541 s); `taskpolicy -b` made a dev script 5x slower and is opt-in.
- **Open:** one unkillable `close()` on the service socket (macOS kernel, ended when the service was killed) seen once in the `gpu_cache` installcheck test; one scan run in which the cluster went into crash recovery during the GiST index-split test (not reproduced).

## Smaller items (2026-11-05)

- **EvalPlanQual crash (found by `session_churn.sh`).** Concurrent `UPDATE`s over a GpuScan made the backend segfault in
  `heap_form_minimal_tuple`: `execCpuFallbackBaseTuple` (fallback.c) copied the columns of the CPU-fallback load list with
  `attno - 1`, but an UPDATE's scan carries the system column `ctid` (negative attno), so it read outside the slot arrays. It now
  fetches system columns with `heap_getsysattr`. This was very likely the cause of the unexplained crash recovery seen once in the
  GiST index-split test.
- **close() hang.** `xpuClientCloseSession` closed the socket while the session worker sat in `poll()` on it; macOS blocks there.
  Now `shutdown()`, join the worker, then `close()`.
- **verify_all.sh** copies the cluster log and any new `postgres-*.ips` / `pgstrom-gpuserv-*.ips` crash report of a failed stage into
  the stage's log directory.
- **GPU throttle: not needed.** Trace of a whole dev script: 142 GPU tasks, 1.26 s of GPU time in ~100 s (median 6 ms, max 37 ms), i.e.
  ~1% busy. The load that slows the machine is CPU (queries, page copies) and Metal's shader compiler, which runs as root (cannot be
  reniced); the lite kernels shrink the latter.
- **New on the GPU:** `&&&`, `ST_3DIntersects(point, point)`, `ST_HasZ/HasM/NDims/Zmflag/CoordDim` (probes `postgis/threed_probe*.sql/.out`).
  `ST_3DDistance` stays on the CPU: PostGIS' result differs from plain binary64 in 10,891 of 100,000 random pairs.

## Exact distances and lengths (2026-11-05, later)

The earlier A11 decision "no bit-exact emulation of PostGIS' distance" is reversed: the arithmetic is deterministic and known.
- **Probe** (`postgis/dist_probe.{sql,c,out}`, `len_probe.{sql,c,out}`): the installed PostGIS (3.7, arm64, contracting compiler) computes the
  distance of two points as `sqrt(fma(dz, dz, fma(dx, dx, dy*dy)))` (3D; the 2D form without dz) and the length of a line as the sum, left
  to right, of the same per-segment values: 0 differences in 200,000 point pairs and 60,000 lines (plain binary64: 11-22% differ).
  `ST_3DMaxDistance` of two points is the same value; an empty point gives NULL; a SRID mismatch raises; overflow/NaN give NULL or Infinity.
- **Soft fma:** `f64_sqr_add(a, c)` = RNE(a*a + c), c >= 0 (no cancellation, 128-bit frame), added to `f64_soft.inc`, checked bit for bit
  against the hardware `fma()` on 4,000,000 cases on the host and on the device (`f64soft_check`, op "sqr_add", index 31).
- **Ops:** `SOP_GEOMDIST` (138: ST_Distance, ST_3DDistance, ST_3DMaxDistance of two points, operands as ST_3DDWithin) and `SOP_GEOMLEN` (139:
  ST_Length, ST_Length2D, ST_3DLength of a LINESTRING; 0 for a point or polygon; multi-lines/collections/curves go back to the CPU).
- **Portability guard:** `vulkan_geom_dist_calibrated` / `vulkan_geom_len_calibrated` (codegen.c) call the installed PostGIS function on fixed
  point pairs / lines when the function is first planned and compare the bits with the host formula (`fma()` from libm); one difference
  and the function stays on the CPU for that backend (LOG line). A PostGIS built without contraction therefore keeps today's behaviour.
- **Possible next step:** ST_DWithin / ST_3DDWithin could use the exact distance instead of the 2^-47 band (no boundary rechecks).

## Distances, lengths and DWithin, exact (2026-11-05, evening)

- **ST_DWithin / ST_3DDWithin of two points** decide "exact distance <= tolerance" (`postgis/dwithin_probe.c`: 0 mismatches over 40,000 pairs at d and its float
  neighbours). The planner calls the installed PostGIS at d, nextafter(d, 0) and nextafter(d, inf) first (`vulkan_geom_dwithin_exact_calibrated`) and sets
  `KEXP_FLAG__GEOM_EXACT` on the expression; without it the kernel keeps the 2^-47 band (safe on any PostGIS build). The flag travels in `kexp->expflags`
  and `SOP_GDW_EXACT` (bit 30 of k1).
- **Lengths and perimeters** of multi-geometries and collections: `ST_Perimeter`, `ST_Perimeter2D`, `ST_3DPerimeter` and multi-parts for `ST_Length*`
  (`GEOMLEN` kinds 2-3). Each member's own total is added to its container's running total, a polygon's rings in order; 30,000 random geometries, 0 differences.
- **Distance of a point to a line, polygon, multi-geometry or collection** (2D, inside `GEOMDIST`): the minimum over the members of the distance to the first
  vertex and to each segment; a point in a polygon's exterior ring but in no hole is at 0, one in a hole at the distance to that hole's ring, one outside at the
  distance to the exterior ring. **The interior of a segment is PostGIS' `distance2d_pt_seg`, not the foot of the perpendicular**: `|s| * sqrt(L2)` with
  `s = fma(Ay-py, Bx-Ax, -((Ax-px)(By-Ay))) / L2`, `L2 = fma(Bx-Ax, Bx-Ax, (By-Ay)^2)` (`postgis/seg_probe.c`: 0 differences in 89,523 interior rows; the foot model
  failed the planner's calibration and the offline probe, but passed the first dev tests). A point whose projection `r` is within 2^-40 of 0 or 1 is re-checked
  (the fusing of `r` itself is not known to the last bit); a point near a polygon edge is re-checked by the winding test.
- **Software fma:** `f64_fma(a, b, c)` for any signs (the general case; `f64_sqr_add` is the cheap one for squares), exact against the hardware on 40 million host and
  16.7 million device cases including constructed cancellation.
- **Testing lesson:** a float8 in a projection can be computed by the CPU above the scan, so value tests compare in a **qual** against a value PostGIS stored when
  the table was built (`... where ST_Distance(g, pt) = dist`): any last-bit difference loses rows. Do this for every value-returning function.
- **Kernel size lesson:** the Slang compiler inlines every call; a heavy soft-float step written once but called from many places multiplies the kernel (the first
  point-to-geometry walker made every full scan kernel 28 MB instead of 5). Write walkers as single loops with one copy of each heavy step. The embedded SPIR-V is
  also no longer turned into C source (`gen_kspv.sh` uses `.incbin`): the C array had passed Clang's 2 GB source-location limit. Full kernels carry all geometry;
  a "no geometry" tier would shrink the 406 MB service binary (open).

**A14: rechecks in the aggregating join kernels (2026-11-06).** In `jagg` / `jgagg` (`JW_MODE` 1-3) an outer row whose scan quals returned a recheck (`g_recheck`: float4 denormal / underflow, numeric division by zero or beyond 64 bits, ...) was `hit = false` and silently omitted (measured: a float4 qual over a table with denormals gave 376732 rows against 377074; a recheck in the projection, hash key or join qual stopped the query with a kernel error). Two mechanisms, chosen per program by `scan_prog_build_join` from the opcodes (`op_may_recheck`: numeric, jsonb, geometry groups, `SOP_FARITH`, string compare / like / length): **`rck_outer`** (a recheck-capable instruction in the scan quals) and **`rck_walk`** (one after them: hash key, join qual, projection, aggregate arguments, FILTER; always for a GiST join). (1) Qual-only: the row has contributed nothing, so the kernel sets a bit (line pointers before the page + lp; Arrow: row of the pass) in a bitmap behind the results (`outb`, program header word 19 = its word offset, patched into the program copy, 0 = off) and the service hands the flagged rows to the backend (`joinagg_harvest_flags`, `arrow_exec.c`), no extra pass. (2) Walk / projection: an accumulator cannot retract, so the GiST scout pass is now generic: the VM join kernel (mode 0, `kparam.extra = 1`, poison records only) runs first, its poisoned rows go to the backend as `KDS_FORMAT_RECHECK` and into the skip bitmap (header word 18), which the aggregating pass honours (also in the specialized kernels and the lite variants: the `VM_NO_GEOM` guards are gone). The scout's record buffer starts at 4096 records and is rerun once with the exact count. Hash-key recheck is now a poison record in mode 0 (it was a kernel error). Programs without a recheck-capable instruction run no scout and write no flag: kernels cost only two header-word loads per outer row. The backend path is the one of the GiST case (`execCpuRecheckOneChunk` -> `execCpuFallbackBaseTuple`, hash depths through the hash fallback); RIGHT/FULL rows are flagged by the CPU join as for any rechecked row. Text and numeric *columns* are NULL-only in join programs, so a compressed or out-of-line outer string cannot recheck inside a join kernel (a text qual runs in a GpuScan below the join, which has its own recheck path); the tests still carry such strings. Tests: `joinagg_tests.inc` section "rows the device cannot decide" (float4 denormal qual ungrouped / grouped by inner and outer key, float4 in the projection and in a FILTER (scout), text qual over toasted strings, LEFT / RIGHT / FULL, numeric division by zero and overflow in a LEFT ON qual) and `arrow_tests.inc` (float4 underflow, qual and projection, LEFT). Timings: see the report of the commit; a scout pass roughly doubles the kernel time of the programs that need it.
