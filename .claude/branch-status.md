# Where the vulkan-gpu branch stands (moved out of CLAUDE.md)

Where the branch stands: GpuScan (heap, Arrow IPC, Parquet row groups), GpuJoin (inner/LEFT/RIGHT/FULL/semi/anti hash joins on integer, date/time and text/varchar/bpchar keys, up to four inner relations) and GpuPreAgg (also over RIGHT/FULL joins; with and without GROUP BY on up to two integer/date-time keys, up to four over a join (`jgagg` tables hold `SCAN_GROUP_KEYS_JOIN` keys; bool and float keys too: `x + 0.0`, so -0 prints as 0), also directly over a join; all three also with an Arrow/Parquet table as the scanned relation, `kernels_vm/arrow_load.inc` + `-DARROW_SRC`) run on the GPU. Types on the GPU: bool, int1-8, float4, date/time/timestamp, numeric (values that fit 64 bits, the rest re-checked on the CPU), text (equality, simple LIKE, C-collation ordering); a float8 comparison of small trees of columns and constants under `+ - * abs` and unary minus is first decided in double-float arithmetic with a proven error bound (`DFCMP`, `kernels_vm/df64.inc`, A10 part 6; the exact software binary64 runs for the undecided rows, so results never change; the service switches MoltenVK's fast math off and self-checks at start, `PGSTROM_GPUSERV_DF64`); strings and numerics that the kernel cannot read (compressed, out of line, too big) take the per-row CPU re-evaluation path (`KDS_FORMAT_RECHECK`). GpuPreAgg returns partial aggregate states that PostgreSQL's Agg node finalizes. GROUP BY is faster than PostgreSQL for few groups (shared-memory tables, `pg_strom.gpupreagg_max_groups`, default 128, over joins, which also hold two keys) and over a scan (heap, Arrow/Parquet, GPU-Cache; up to four keys) up to about a million groups through a session-wide hash table in device memory (`kernels_vm/gtab.slang`, `pg_strom.gpupreagg_max_groups_heap`, default 2,000,000; plan "A3, many groups": 1k groups ties PostgreSQL, 10k 1.1x, 100k 5x, 1M 3.3x faster). A query that runs more than one task gets a **specialized kernel** generated from its program, compiled by `slangc` in a background thread and cached on disk (A6; `pg_strom.gpu_specialize`, `PGSTROM_GPUSERV_SPECIALIZE`); everything else, and every host without `slangc`, runs on the interpreter. GPU-Sort of GpuPreAgg groups and GPU-Cache (A7: `gpu_cache.c` + `src/gpuserv/gcache.c`, scan/aggregate/join over a cached table through the Arrow kernels with a row filter) work; numeric and jsonb columns are read from the cache and numeric expressions over Arrow/Parquet columns run on the GPU, both with the A12 per-row recheck, and `gpucache_info()->>'scans'` shows whether the cache served a query; PostGIS measures and accessors run on the GPU on heap and GPU-Cache tables (`ST_Area` bit for bit with PostGIS 3.7's adaptive `ptarray_signed_area`, reproduced by `kernels_vm/area_ring.inc`; `ST_NPoints`/`ST_NRings`/`ST_NumGeometries`/`ST_IsEmpty`/`ST_SRID`/`ST_X`/`ST_Y`; R3/R4 in the plan; Arrow_Fdw has no geometry column; `ST_GeometryType`, `ST_StartPoint`/`ST_EndPoint` stay on the CPU); jsonb quals run on the GPU (`->`, `->>`, `?`, `jsonb_typeof`, `@>` against a constant, `(->>)::numeric/int`; a jsonb or text value *computed* in the target list stays on the CPU, A8); PostGIS: the exact distance of a point to a line, polygon or multi-geometry (`ST_Distance`, `ST_DWithin`, and `ST_3DDistance` / `ST_3DDWithin` for lines with a Z) runs on the GPU in scan quals, aggregation, Arrow, Parquet and GPU-Cache, but NOT inside a join kernel: Metal cannot compile a join kernel with the walker (294 s for today's, >900 s with it), so a GiST join over inner lines/polygons joins them on the CPU through poison records (plan, A13 slice 4; keep the `WITH_INNER` kernels byte-identical unless `test/gpuserv/metal_compile_probe.sh` says the compile survives). First use after an install (A9 part 3, `kprewarm.c`): the service compiles the common kernels in a background thread (`pg_strom.gpu_prewarm`, `pgstrom-gpuserv --prewarm-all`), a task whose kernel is not compiled yet is refused after `pg_strom.gpu_kernel_wait` and the node continues on the CPU; `locked_test.sh` turns both off for the other tests (`PGSTROM_GPUSERV_KERNEL_WAIT_MS=-1`, `PGSTROM_GPUSERV_PREWARM=off`), `test/gpuserv/firstuse_dev.sh` tests them. `parquet_cache.c` is a stub. `README.md` and `doc/features.md` carry the user-facing list; the plan's status sections are authoritative. A node whose GPU session is refused or dies (a program the service cannot translate, an error reply, a lost device, a service that is not ready or restarts) continues on the CPU and returns the CPU plan's rows (A14, `pg_strom.gpu_error_fallback`, `fallback.c`; not for GPU-Sort and pinned buffers).
